# Deterministic mapping and hybrid structure+geometry approaches for Typst to DOCX

Scope: documented patterns where source constructs map deterministically to Word constructs, fidelity techniques in OOXML, hybrid designs that use semantic structure plus rendered geometry, and fixed-layout alternatives. Researched 2026-09-29.

## 1. Template-provided mappings (pandoc, Quarto, DITA, HTML-to-DOCX)

### Takeaway
The mature deterministic pipelines (pandoc, Quarto, DITA-OT) all use the same contract: a fixed, small vocabulary of named Word styles, supplied by a reference/template .docx that owns fonts, spacing, page size, margins, headers and footers, plus an escape hatch (`custom-style`) that maps an arbitrary source block or span to a named paragraph or character style. None of them try to reproduce arbitrary template geometry; visual fidelity is delegated to whoever authors the reference .docx. HTML/CSS-to-DOCX libraries preserve even less, because CSS layout has no Word equivalent.

### Cited Findings
- Pandoc: "The contents of the reference docx are ignored, but its stylesheets and document properties (including margins, page size, header, and footer) are used in the new docx." The manual advises making the reference doc by modifying pandoc's default one and changing nothing except the styles pandoc uses. [pandoc MANUAL.txt](https://raw.githubusercontent.com/jgm/pandoc/main/MANUAL.txt) (also rendered at [pandoc.org/MANUAL.html](https://pandoc.org/MANUAL.html))
- Pandoc's fixed style vocabulary for docx: paragraph styles Normal, Body Text, First Paragraph, Compact, Title, Subtitle, Author, Date, Abstract, AbstractTitle, Bibliography, Heading 1 to 9, Block Text, Footnote Block Text, Source Code, Footnote Text, Definition Term, Definition, Caption, Table Caption, Image Caption, Figure, Captioned Figure, TOC Heading; character styles Default Paragraph Font, Verbatim Char, Footnote Reference, Hyperlink, Section Number; table style Table. [pandoc MANUAL.txt](https://raw.githubusercontent.com/jgm/pandoc/main/MANUAL.txt)
- Pandoc `custom-style`: a Div, Span or Table with attribute `custom-style` gets that named style applied "with the exception of elements whose function depends on a style, like headings, code blocks, block quotes, or links". Undefined styles are created "as inheriting from normal text (docx)"; if already defined in the reference doc "pandoc will not alter the definition". No extension needs enabling for docx output. [pandoc MANUAL.txt](https://raw.githubusercontent.com/jgm/pandoc/main/MANUAL.txt)
- The manual recommends pairing custom styles with filters (for example turning every italic inline into an `Emphasis` custom-style span), i.e. the mapping is an AST transform, not a layout transform. [pandoc MANUAL.txt](https://raw.githubusercontent.com/jgm/pandoc/main/MANUAL.txt)
- Pandoc's docx reader with `-f docx+styles` does the reverse mapping: it adds a `custom-style` attribute for every docx style, creating Divs for paragraph styles and Spans for character styles; table styles go on the Table. [pandoc MANUAL.txt](https://raw.githubusercontent.com/jgm/pandoc/main/MANUAL.txt)
- Pandoc `--toc` for docx emits "an instruction to create" a TOC (a field), not a rendered TOC. [pandoc MANUAL.txt](https://raw.githubusercontent.com/jgm/pandoc/main/MANUAL.txt)
- Pandoc `native_numbering` (docx/odt): "Enables numbering of figures and tables via counter fields specific to the target format"; without it tables and figures are not numbered. Cross-reference numbers "are only visible in the final document once it has been refreshed." [pandoc MANUAL.txt](https://raw.githubusercontent.com/jgm/pandoc/main/MANUAL.txt)
- Raw OOXML can be injected with the `openxml` raw format for docx, and the docx writer's template is `default.openxml`. [pandoc MANUAL.txt](https://raw.githubusercontent.com/jgm/pandoc/main/MANUAL.txt)
- Quarto passes the same mechanism through: `reference-doc`, custom styles "defined using divs for blocks and spans for text", template generated with `quarto pandoc -o custom-reference-doc.docx --print-default-data-file reference.docx`, and missing styles "added to the output file with standard text as their base style." [Quarto Word Templates](https://quarto.org/docs/output-formats/ms-word-templates.html)
- Quarto's docx page documents `toc`, `toc-depth`, `number-sections`, `number-depth`, `.unnumbered`/`.unlisted`, and syntax highlighting; it says nothing about page-layout fidelity. [Quarto MS Word](https://quarto.org/docs/output-formats/ms-word.html)
- DITA-OT (com.elovirta.ooxml plugin): a DOCX/DOTX/DOCM template supplies the styles; the plugin requires specific style IDs (BodyText for body, List Paragraph for list items, TableNormal for borderless tables, TableGrid for bordered ones, Normal inside table cells), and style names must be English. [oXygen DITA Map to Word](https://www.oxygenxml.com/doc/versions/27.1/ug-developer/topics/ditamap-ms-word.html); [com.elovirta.ooxml README](https://github.com/jelovirt/com.elovirta.ooxml/blob/master/README.md); [Templates wiki](https://github.com/jelovirt/com.elovirta.ooxml/wiki/Templates)
- html-docx-js wraps HTML as an `altChunk`, which only Microsoft Word renders; LibreOffice Writer, OpenOffice and Google Docs show a blank document, and Word for Mac 2008 did not support it. Images must be inline base64 data URIs. [html-docx-js README](https://github.com/evidenceprime/html-docx-js/blob/master/README.md); [docx-templates issue #201](https://github.com/guigrpa/docx-templates/issues/201)
- Line-height mapping from CSS is error-prone in practice: html-to-docx emitted a wrong `w:line` (under 1.0) for unitless CSS `line-height` with `lineRule=auto`. [TurboDocx/html-to-docx #237](https://github.com/TurboDocx/html-to-docx/issues/237). docx.js users reported `LineRuleType.EXACTLY` not behaving as expected. [dolanmiu/docx #1773](https://github.com/dolanmiu/docx/issues/1773)

### Inferences
- For "any template", the deterministic route has to derive the reference .docx from the Typst template itself (page size, margins, fonts, heading show rules resolved to concrete sizes/spacing) rather than asking the user to maintain one, since pandoc/Quarto/DITA all assume a hand-built reference doc.
- A small fixed style vocabulary (Heading 1..n, Body Text, Caption, Table, Source Code) plus generated custom styles for template-specific constructs mirrors pandoc's proven contract and keeps the output editable.
- Pandoc can already read Typst (`-f typst`) but only at the AST level; show rules and template geometry are not evaluated, so it cannot give "near-identical visuals" on its own (see gaps).

### Gaps
- I found no documentation of how faithfully Aspose.Words or LibreOffice HTML import preserve CSS layout (floats, flex, grid, absolute positioning); only the generic statement that web layout constructs have no Word equivalent, which came from a search summary, not a primary source.
- Pandoc Typst reader limitations: search surfaced only issue-level evidence (e.g. `#highlight` around block content losing the mark, [jgm/pandoc #11908](https://github.com/jgm/pandoc/issues/11908)); I did not find an official list of unsupported Typst constructs.
- Microsoft does not document a DOCX "custom-style" equivalent for XSL-FO based DocBook-to-Word; I did not find a current (2026) maintained DocBook-to-DOCX pipeline worth citing.

## 2. Round-trip fidelity techniques in OOXML (line heights, fields, fonts, page drift)

### Takeaway
OOXML has the primitives to pin most vertical metrics (exact line spacing in twips, explicit paragraph spacing, section page setup, embedded fonts, PAGE/TOC fields), but it cannot pin line breaks: Word re-breaks paragraphs with its own first-fit algorithm while Typst uses whole-paragraph optimized (Knuth-Plass style) breaking and hyphenation for justified text. That mismatch is the main source of page-count drift, and fields such as TOC and PAGEREF need a refresh in Word to show correct numbers.

### Cited Findings
- `w:spacing/@w:lineRule` is `auto`, `exact` or `atLeast`. With `auto`, `w:line` is in 240ths of a line (240 = single); with `exact`/`atLeast` it is in twentieths of a point (twips). When an exact/atLeast height is too small the text is clipped from the top; when too large it is centered. [officeopenxml.com spacing](http://officeopenxml.com/WPspacing.php); [ST_LineSpacingRule](https://c-rex.net/samples/ooxml/e1/Part4/OOXML_P4_DOCX_ST_LineSpacingRule_topic_ID0ERZ42.html); [datypic w:lineRule](http://www.datypic.com/sc/ooxml/a-w_lineRule-1.html); [SpacingBetweenLines.Line](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.spacingbetweenlines.line?view=openxml-3.0.1)
- Viewers that ignore style-inherited `w:spacing` or guess font line height do not paginate like Word, which shows how sensitive pagination is to exact line metrics. [office-open-xml-viewer #1507](https://github.com/yukiyokotani/office-open-xml-viewer/issues/1507)
- Typst defaults: `par.leading` 0.65em (bottom edge of one line to top of next), `par.spacing` 1.2em; `linebreaks: auto` uses optimized breaks for justified paragraphs, "considering the whole paragraph"; hyphenation turns on for justified paragraphs when the language is known. [Typst par reference](https://typst.app/docs/reference/model/par/)
- Knuth-Plass minimizes badness over the whole paragraph; first-fit algorithms (typical of word processors and browsers) consider one line at a time and produce looser lines and more hyphens. [Knuth-Plass, Wikipedia](https://en.wikipedia.org/wiki/Knuth%E2%80%93Plass_line-breaking_algorithm); [tex-linebreak README](https://github.com/robertknight/tex-linebreak); [Knuth and Plass 1981](https://gwern.net/doc/design/typography/tex/1981-knuth.pdf)
- Note on Typst leading: because Typst measures leading edge-to-edge while OOXML `exact` measures baseline pitch, a mapping needs `line = font line height + leading` in twips (inference from the two definitions above, not a documented formula).
- `w:updateFields` in settings.xml makes Word recalculate all fields on open, prompting the user to update the TOC. [updateFields spec](https://c-rex.net/samples/ooxml/e1/Part4/OOXML_P4_DOCX_updateFields_topic_ID0EXFLY.html); [Eric White on TOCs](https://www.ericwhite.com/blog/exploring-tables-of-contents-in-open-xml-wordprocessingml-documents-part-2/); [UpdateFieldsOnOpen class](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.updatefieldsonopen?view=openxml-3.0.1)
- Generated PAGEREF fields can show "1" in Word 365 even with update-on-open; `dirty="true"` did not update TOC page numbers for another user. [MS Q&A PAGEREF](https://learn.microsoft.com/en-us/answers/questions/605245/generated-docx-in-word-365-pageref-fields-not-work); [MS Q&A dirty=true](https://learn.microsoft.com/en-us/answers/questions/491304/openxml-the-dirty-true-attribute-does-not-update-t)
- Font embedding: `EmbedTrueTypeFonts` (default false) embeds fonts for DOC/DOCX/RTF; `SaveSubsetFonts` stores only used glyphs and works only when embedding is on. [Aspose EmbedTrueTypeFonts](https://reference.aspose.com/words/net/aspose.words.fonts/fontinfocollection/embedtruetypefonts/); [Aspose SaveSubsetFonts](https://reference.aspose.com/words/net/aspose.words.fonts/fontinfocollection/savesubsetfonts/); [Microsoft SaveSubsetFonts](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.tools.word.documentbase.savesubsetfonts?view=vsto-2017)
- Pandoc emits TOC and figure/table numbering as fields and states the numbers appear only after refresh, i.e. the mainstream tools accept field staleness rather than baking numbers. [pandoc MANUAL.txt](https://raw.githubusercontent.com/jgm/pandoc/main/MANUAL.txt)

### Inferences
- The strongest drift control available in OOXML is to force Typst's line breaks: emit each rendered line's break explicitly (a `w:br` or a per-line paragraph) with `lineRule="exact"` spacing and non-justified-by-Word alignment. This buys page identity at the cost of reflow editability; the BTCT converter already has a "forced line breaks" pass, which is this technique.
- A softer option is to keep Word's breaking but pin vertical metrics (exact line pitch, explicit before/after spacing, `keepNext`/`keepLines`, explicit `w:br w:type="page"` at every Typst page boundary). Explicit page breaks stop drift from accumulating across pages even when lines inside a page differ.
- For TOC and page numbers: emit real TOC/PAGE/NUMPAGES fields but fill their cached result with the numbers Typst computed, so the document is correct before any refresh and still updatable.

### Gaps
- I found no published measurement of page-count drift between TeX/Typst and Word for identical content.
- I did not find a primary Microsoft statement of Word's exact line-breaking algorithm (the "first fit" characterization is from secondary sources).
- Cell margins (`w:tblCellMar`), `w:keepNext`, anchored vs inline images (`wp:anchor` vs `wp:inline`) were not individually researched with sources in this pass.

## 3. Hybrid structure + geometry (tagged PDF, source-to-PDF alignment)

### Takeaway
Commercial converters mostly infer structure from geometry by rules (Word's PDF Reflow says so explicitly), and Adobe says standard tags give the best Word conversion. Typst now writes tagged PDF by default (0.14, Oct 2025) and exposes element positions through introspection (`location.position()`, `typst eval 'query(...)' --in`), so a Typst exporter can get a SyncTeX-like bridge natively: semantic elements from the structure tree or from queries, geometry from the PDF. Research datasets (DocBank) validate the idea of instrumenting source to label rendered geometry.

### Cited Findings
- Word 2013 PDF Reflow "uses a system of complex rules to figure out what Word objects (like headings, lists, tables, etc.) would best represent the original PDF"; "Most PDFs don't have a notion of content structure elements"; results "are best with documents that are mostly textual". The post does not say Reflow reads tags. [Microsoft 365 blog, Unlock PDFs with Word 2013](https://www.microsoft.com/en-us/microsoft-365/blog/2012/08/09/unlock-pdfs-with-word-2013/)
- Adobe: standard element tag types "provide the best results when tagged content is converted to a different format, including HTML, Microsoft Word"; tagging at authoring time lets the app build the structure tree from its own styles. [Adobe, Content and Tags panels](https://helpx.adobe.com/acrobat/using/editing-document-structure-content-tags.html); [Adobe, Creating accessible PDFs](https://helpx.adobe.com/acrobat/using/creating-accessible-pdfs.html)
- Typst 0.14 (2025-10-24): "PDF files created with Typst 0.14 are tagged by default"; built-in elements (headings, strong text, figures, and more) are tagged automatically; PDF/UA-1 export checks titles, heading hierarchy and alt text. [Typst 0.14 blog](https://typst.app/blog/2025/typst-0.14/); [0.14.0 changelog](https://typst.app/docs/changelog/0.14.0/); [Typst Accessibility Guide](https://typst.app/docs/guides/accessibility/)
- Typst 0.15 (2026-06-15) allows PDF/A and PDF/UA together, adds a `within` selector for scoped introspection, and adds convergence diagnostics for layout iterations. [Typst 0.15 blog](https://typst.app/blog/2026/typst-0.15/); [v0.15.0 release](https://github.com/typst/typst/releases/tag/v0.15.0)
- Typst `location.position()` returns "a dictionary with the page number and the x, y position for this location", coordinates from the page's top-left; `location.page()` gives the physical page number. [Typst location](https://typst.app/docs/reference/introspection/location/)
- Queries run from the command line with `typst eval 'query(<note>)' --in example.typ`, with `.map()` to pick fields and `--target paged|html`. [Typst query](https://typst.app/docs/reference/introspection/query/)
- Typst HTML export is still experimental behind `--features html`; 0.14 added semantic HTML for most model elements but "visualization-focused features remain unsupported"; 0.15 added MathML and an experimental bundle export. [Typst 0.14 blog](https://typst.app/blog/2025/typst-0.14/); [Typst 0.15 blog](https://typst.app/blog/2026/typst-0.15/); [Typst HTML docs](https://typst.app/docs/reference/html/)
- SyncTeX (Laurens, TUGboat 29(3), 2008) has TeX engines write geometric information to a `.synctex` file during typesetting, linking input locations to page positions. [TUGboat PDF](https://tug.org/TUGboat/tb29-3/tb93laurens.pdf); [jlaurens/synctex](https://github.com/jlaurens/synctex)
- DocBank built 500K labeled pages by editing arXiv LaTeX sources to color each semantic unit (abstract, caption, equation, figure, footer, list, paragraph, section, table, title...) and reading the colored tokens back from the rendered PDF. [DocBank, COLING 2020](https://aclanthology.org/2020.coling-main.82.pdf); [arXiv 2006.01038](https://arxiv.org/abs/2006.01038v1)

### Inferences
- A Typst-specific hybrid needs no ML: compile once to PDF (geometry, glyphs, line breaks, page boundaries) and read semantics either from the PDF's own structure tree (H1..Hn, Table/TR/TH/TD, Figure, L/LI, Artifact for running headers and footers) or from `typst eval 'query(heading)'`/`query(table)` with `.location().position()`. Joining the two on page + position gives each PDF block a source element, the same idea as SyncTeX and DocBank's color trick.
- The structure tree answers exactly the questions that pdf2docx-style geometry heuristics get wrong: is this a running header (Artifact), is this a table vs a panel, which rows are header rows, what heading level is this. Using it would replace detectors with lookups.
- A DocBank-style instrumentation is also available in Typst: a show rule that wraps each element kind in `metadata` or a distinctive invisible marker at compile time for the export build only, then reads positions via query.

### Gaps
- I found no documentation that Aspose, ABBYY or Adobe's PDF-to-Word explicitly consumes the tag tree during conversion (Adobe says tags give best results, without describing the mechanism). Word PDF Reflow's post does not mention tags.
- I could not open the SyncTeX paper (HTTP 403), so SyncTeX's granularity (box/line level) is not confirmed from the primary source.
- I found no paper or tool that aligns a Typst AST with PDF glyphs; the approach above is an inference.
- Whether Typst tags table header cells, footnotes, and page header/footer artifacts in all templates was not confirmed element by element.

## 4. Fixed-layout alternatives and flowing vs exact modes

### Takeaway
Every major converter offers the same trade-off as a user switch: an exact mode that places text in text boxes/frames (looks right, hard to edit) and a flowing mode (editable, looks different). Aspose.PDF defaults to Textbox; Adobe and ABBYY name the modes Retain Page Layout / Retain Flowing Text and Exact Copy / Editable Copy.

### Cited Findings
- Aspose.PDF DocSaveOptions recognition modes: Textbox (default) "is fast and good for preserving the original look... but the editability of the resulting document could be limited", every grouped text block becomes a text box; Flow is "full recognition mode" that groups and analyzes to restore author intent as an editable document; EnhancedFlow additionally recognizes bordered and borderless tables "as real tables, not as text with a picture in the background". [Aspose.PDF for .NET, Convert PDF to Word](https://docs.aspose.com/pdf/net/convert-pdf-to-word/); [Aspose.PDF for Python](https://docs.aspose.com/pdf/python-net/convert-pdf-to-word/)
- Adobe Acrobat export to Word offers "Retain Flowing Text" and "Retain Page Layout"; the latter may split text into text-box groups to keep positions. [Microsoft Q&A on the two options](https://learn.microsoft.com/en-us/answers/questions/f91ea184-004c-4784-b577-3c1003ce158e/getting-the-best-pdf-import-retain-page-layout-or?forum=msoffice-msoffice_word-mso_windows8); [Erin Wright, Acrobat to Word](https://erinwrightwriting.com/pdfs-to-microsoft-word-files-in-adobe-acrobat/); users ask for export "without putting every piece of text in a text box" ([Acrobat UserVoice](https://acrobat.uservoice.com/forums/590923-acrobat-for-windows-and-mac/suggestions/20393680-export-to-ms-word-without-putting-every-piece))
- ABBYY FineReader: Exact copy (matches original, "limits your ability to change the text"), Editable copy (formatting "may differ slightly", easy to edit), Formatted text (keeps fonts, sizes, paragraphs but not exact spacing or object positions), Plain text. [ABBYY FineReader 15 DOCX settings](https://help.abbyy.com/en-us/finereader/15/user_guide/docx_settings/); [ABBYY Saving editable documents](https://help.abbyy.com/en-us/finereader/12/savetoedit/); ABBYY also publishes a help article on removing the text boxes afterwards ([ABBYY Help Center](https://support.abbyy.com/hc/en-us/articles/360021869519-How-to-remove-the-text-boxes-once-the-document-is-converted-to-MS-Word-document-via-FineReader-PDF))
- LibreOffice opens PDFs in Draw, where each text box, image and shape is a separate object, better suited to minor edits than restructuring. [GeeksforGeeks, Edit PDF in LibreOffice](https://www.geeksforgeeks.org/techtips/how-to-edit-pdf-in-libreoffice/) (secondary source)

### Inferences
- The industry default for "looks identical" is text boxes; for "editable" it is flow. A Typst exporter that claims both needs the hybrid of sections 2 and 3: flowing paragraphs and real tables for body content, with anchored frames reserved for elements that are genuinely absolutely positioned in Typst (`place`, page backgrounds, cover pages).
- Offering the switch explicitly (as Aspose/Adobe/ABBYY do) is a reasonable escape hatch for templates the flowing path cannot reproduce.

### Gaps
- No vendor publishes fidelity metrics for its flowing vs exact modes.
- I did not verify Aspose.Words `PdfLoadOptions` behavior against Aspose.PDF's modes; the search summary indicated the modes belong to Aspose.PDF's `DocSaveOptions`.
