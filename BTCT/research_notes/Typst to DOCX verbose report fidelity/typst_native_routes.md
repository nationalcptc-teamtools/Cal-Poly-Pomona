## 1. Typst HTML export: status per release, what it carries, and the HTML-to-DOCX chain

### Takeaway
HTML export exists since 0.13.0 (2025-02-19), is still behind `--features html` in 0.15.1, and the maintainers have said it "will stay behind a feature flag" with no timeline. It evaluates the whole program (show rules, context, counters) and emits semantic tags for headings, lists, tables (with `colspan`/`rowspan`, `thead`/`tbody`/`tfoot`), figures, captions, `pre`/`code` with `data-lang`, images as base64 `img`, footnotes, outline and (since 0.15) MathML. It emits no CSS and drops every layout element: `place`, `page`, `columns`, `grid`, `stack`, `align` and `pad` are discarded with a generic "was ignored during HTML export" warning, and `box`/`block`/`text` fills are silently dropped. So an HTML-based chain can carry the report's structure but not its page breaks, header/footer, panel fills or row fills; those must come from the paged layout or from template-emitted markers.

### Cited Findings
- 0.13.0 (2025-02-19) introduced HTML export "under active development", enabled with `--features` or `TYPST_FEATURES`, the only feature being `html`; "still very incomplete"; `html.elem` outputs an arbitrary element, `html.frame` "embeds content that requires layout as an SVG", `target()` returns `"paged"` or `"html"`; `typst::compile` became generic over `PagedDocument` or `HtmlDocument`. [Changelog 0.13.0](https://typst.app/docs/changelog/0.13.0/)
- 0.14.0 (2025-10-24): the Model category is "fully covered" (image, footnote, outline, bibliography, smartquote, sub/super, underline/overline/strike/highlight, smallcaps, lower/upper); typed `html.*` API; intra-document `link` targets; `raw` gets syntax highlighting, block `raw` emits `<pre>` and `<code>` with the language in `data-lang`; `html.elem` accepts custom element names; `html.frame` encoding, sizing and nesting fixes; `typst query` gained `--target`. [Changelog 0.14.0](https://typst.app/docs/changelog/0.14.0/)
- 0.15.0 (2026-06-15): equations exported as MathML; `box`/`block` now behave as in paged export (breaking); paragraph grouping revised (text, boxes and phrasing content inline; `block` block-level; other HTML elements neutral; breaking); `html.script`/`html.style` strings only; output minified by default (`--pretty` to pretty-print); `<img>` always gets `width`/`height`; `target` usable without the flag "but the rest of HTML export remains behind it"; new experimental `bundle` target and `asset` element. [Changelog 0.15.0](https://typst.app/docs/changelog/0.15.0/)
- 0.15.1 (2026-07-17): inline SVGs from `html.frame` now respect pretty printing; nothing else for HTML, tagging or query. [Changelog 0.15.1](https://typst.app/docs/changelog/0.15.1/)
- Current docs (0.15.1): HTML export is "still very incomplete and only available for experimentation behind a feature flag", not for production; enable with `--features html` or `TYPST_FEATURES=html` plus `--format html` or a `.html` output name; `typst watch` serves a live-reload server; `html` and `bundle` both emit standalone files, fragments are planned; "Typst does not output CSS yet. Automatic CSS generation is planned." [Typst docs: HTML](https://typst.app/docs/reference/html/)
- `html.elem(tag, attrs: (:), body: none)`: "An HTML element that can contain Typst content"; tag and attributes must be valid HTML; tags like `meta` take no body; user-made `html`/`head`/`body` suppress Typst's own. [Typst docs: html.elem](https://typst.app/docs/reference/html/elem/)
- `html.frame(body)`: "lays out its content as an inline SVG", for plots or "content that depends on precise positioning and styling", using "the same layout engine as PDF, SVG, and PNG export". [Typst docs: html.frame](https://typst.app/docs/reference/html/frame/)
- Tracking issue #5512 (opened 2024-12-03 by laurmaedje, locked to collaborators the same day): support levels are Level 2 (handled semantically) for most Model and Text elements and Image, Level 1 (partial) for Box and Block, Level 0 (not working) for Circle, Curve, Ellipse, Line, Polygon, Rectangle, Square; CSS and EPUB are "future work"; multi-file output is in scope; the author wrote that HTML export "will stay behind a feature flag", is "not intended for production use", and "There is not yet a timeline for when we'll move things out of the feature flag." [typst/typst#5512](https://github.com/typst/typst/issues/5512)
- The HTML show rules (`crates/typst-html/src/rules.rs`, main branch): `title` → `h1`; `heading` levels 1 to 5 → `h2` to `h6`, level 6+ → `div role="heading" aria-level=...` with a warning, numbering prepended as text; `list` → `ul`/`li`; `enum` → `ol`/`li` with `reversed`/`start`/`value`; `terms` → `dl`/`dt`/`dd`; `figure` → `figure` with `figcaption` before or after the body by its position setting; `quote` → `blockquote`; `table` → `table` with leading header rows in `thead`, body in `tbody`, footer rows in `tfoot`, cells `td` or `th`, `colspan`/`rowspan` only when not 1; "Table fills, strokes, column widths: not emitted"; `raw` inline → `code data-lang`, block → `pre` wrapping `code`; `image` → `img` with a base64 data URL, `width`, `height`, `alt`; `math.equation` → MathML `math` (`display="block"` for block); `outline` → `nav role="doc-toc"` with nested `ol`; footnotes → superscript `doc-noteref` links plus `section role="doc-endnotes"`; `link` → `a href`, positional destinations dropped with a warning. Text colour reaches HTML only through a temporary `html_span_filled` helper whose comment says `TextElem::fill` is not supported in HTML export; size and font are not handled. [typst-html rules.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-html/src/rules.rs)
- The converter (`crates/typst-html/src/convert.rs`, main): any content element without a handler is dropped with the single generic warning `"{name} was ignored during HTML export"`; `place`, `page`, `columns`, `grid`, `stack`, `align`, `pad` have no handler in this file; `BoxElem` and `BlockElem` bodies are converted and their `fill` is "never read, so it's silently ignored"; `TextElem` applies only `case`, its fill is silently ignored; `html.frame` lays its body out with `routines.layout_frame` under `Target::Paged` in an unbounded region and is made `display: block`. [typst-html convert.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-html/src/convert.rs)
- Exporter module layout: `crates/typst-html/src/` holds `convert.rs`, `dom.rs`, `encode.rs`, `mathml.rs`, `typed.rs`, `tag.rs`, `introspect.rs`, `css/`, `fragment.rs`. [typst-html src tree](https://github.com/typst/typst/tree/main/crates/typst-html/src)
- HTML-to-DOCX libraries: `html-to-docx` (npm) makes a page break from a `div.page-break` or `page-break-after` style, takes header and footer as separate HTML strings (page numbers only when the footer flag is set, with a skip-first-page flag), documents `list-style-type` on `ol` as its one named CSS feature, and does not publish a full CSS support list. [html-to-docx README](https://cdn.jsdelivr.net/npm/html-to-docx@1.8.0/README.md); [npm: html-to-docx](https://npmjs.com/package/html-to-docx)
- docx4j-ImportXHTML maps `h1`..`h6` to Word heading styles only when `docx4j-ImportXHTML.Element.Heading.MapToStyle` is true (added in 3.2.0-beta2, default false), with `CLASS_TO_STYLE_ONLY` / `CLASS_PLUS_OTHER` options for class-to-style mapping; a forum user reported lists disappearing under `CLASS_TO_STYLE_ONLY`. [docx4j forum: 3.2.0-beta2](https://www.docx4java.org/forums/xhtml-import-f28/docx4j-importxhtml-3-2-0-beta2-t1961.html); [docx4j forum: formatting options](https://docx4java.org/forums/docx-java-f6/relationship-between-lists-and-formattingoptions-t1866.html)
- pandoc's docx writer accepts raw OOXML (`{=openxml}` fenced block, e.g. a `w:br w:type="page"`) as the escape hatch for page breaks. [pandoc MANUAL, raw_attribute](https://pandoc.org/MANUAL.html)

### Inferences
- The HTML DOM is the cleanest semantic source typst offers: numbering is already resolved into text, tables carry spans and header/footer rows, code carries its language, and figures carry captions. A template can use `target() == "html"` branches to emit `html.elem("div", attrs: (data-kind: "panel", data-fill: "#eee"))` markers for anything the default mapping loses (panel fills, row fills, page breaks, header/footer content), since `html.elem` accepts arbitrary attributes.
- No HTML-first chain can recover page breaks, header/footer or page numbers on its own; the paged frames must be consulted (section 3) or the template must emit markers. A pandoc or html-to-docx step would also discard the typst-specific markers unless the chain reads the DOM itself (as typort and typlite do in Rust).
- Because `place` and `page` are dropped with only a generic warning, any header or footer built with `#place` inside `page(header: ...)` leaves no trace in the HTML at all.

### Gaps
- I did not find how `grid` is handled when it is realized into a table-like structure; `rules.rs` has no grid rule and `convert.rs` has no handler, so it appears to be dropped, but I did not execute a test.
- No date or version for HTML export leaving the feature flag; #5512 has no later activity visible since 2024-12-03.
- No primary source quantifies which CSS pandoc's HTML reader keeps when going HTML → DOCX; I only confirmed the raw-openxml page-break route.

## 2. Introspection and `typst query`: can a script emit every element's page and position?

### Takeaway
Positions are available, but only from inside the document: `location.position()` returns `(page, x, y)` measured from the page's top-left and `location.page()` the physical page, and since 0.14 `par`, `table`, `list`, `enum`, `raw`, `image`, `figure.caption` and others are locatable without a label. `typst query` (and in 0.15 `typst eval`) serializes elements, not frames: the documented output carries `func`, fields and `label`, so a position dump requires the template (or a wrapper file) to write `metadata` records inside `context`, then `--field value` to pull them out. Each query is a separate full compile of the document in a new process.

### Cited Findings
- `query(target)` "Finds elements in the document", must be inside `context`, accepts an element function, a label, a refined selector (`heading.where(level: 1)`) or a relative selector (`selector(heading).before(here())`); only locatable element functions; returns an array of elements with fields like `.body`, `.value` and the method `.location()`; a self-referential query "simply gives up after a few attempts". CLI: `typst eval 'query(<note>)' --in example.typ` prints a JSON array with `func`, `value`, `label`; `--target paged|html`. [Typst docs: query](https://typst.app/docs/reference/introspection/query/)
- `typst query` man page (package 0.15.1): positional `INPUT` (or `-` for stdin) and `SELECTOR` ("Defines which elements to retrieve"); `--field <FIELD>` "Extracts just one field from all retrieved elements"; `--one` "Expects and retrieves exactly one element"; `--format json|yaml` (default json); `--pretty`; `--target paged|html|bundle` (default paged); `--root`, `--input key=value`, `--font-path`, `--ignore-system-fonts`, `--ignore-embedded-fonts`, `--package-path`, `--package-cache-path`, `--creation-timestamp`, `--jobs`, `--features html|bundle|a11y-extras`, `--diagnostic-format`. [typst-query(1), Arch](https://man.archlinux.org/man/typst-query.1.en)
- `location.page()` returns the "true page number (starting from one)" (use `counter(page).at(loc)` for the counter value); `location.position()` "Returns a dictionary with the page number and the x, y position for this location", "coordinates are measured from the top-left of the page"; `location.page-numbering()` returns the local numbering or `none`; locations come from `here()` or `element.location()`. [Typst docs: location](https://typst.app/docs/reference/introspection/location/)
- 0.12.0: "Added a new system for tracking where elements end up on pages" (breaking); fixed an incorrect `here().position()` when `place` is used in a context expression; `measure` gained `width`/`height`; deprecated `query` with a location second argument, `locate` with a callback, `measure` with styles, `style`. [Changelog 0.12.0](https://typst.app/docs/changelog/0.12.0/)
- 0.13.0 removed those compatibility paths: the `location` argument of `state.at`, `counter.at` and `query`, `state.display`, `style`, the `styles` argument of `measure`, and the old `locate` behaviour. [Changelog 0.13.0](https://typst.app/docs/changelog/0.13.0/)
- 0.14.0: newly locatable without a label: `par`, `table`, `enum`, `list`, `terms`, `title`, `figure.caption`, `footnote.entry`, `outline.entry`, `image`, `emph`, `strong`, `link`, `cite`, `raw`, `underline`, `overline`, `strike`, `highlight`; logical-order fixes for bidi text, RTL grid cells and multi-page grid cells; inline elements at paragraph start now have correct introspection positions; a new incremental algorithm removes "very slow compilation with heavy `context` usage". [Changelog 0.14.0](https://typst.app/docs/changelog/0.14.0/)
- 0.15.0: `within` selector (elements contained in an ancestor match); layout convergence problems now produce detailed diagnostics; `counter.display` gained `at`; "`typst eval` supersedes `typst query`". 0.15.1: `typst eval` exits 1 when the expression fails. [Changelog 0.15.0](https://typst.app/docs/changelog/0.15.0/); [Changelog 0.15.1](https://typst.app/docs/changelog/0.15.1/)
- On the Rust side the same data is the `Introspector` trait: `query`, `query_first`, `query_unique`, `query_label`, `page(location) -> Option<NonZeroUsize>`, `position(location) -> Option<DocumentPosition>`, `page_numbering`, `pages`; the concrete `ElementIntrospector<P>` exposes `all()` ("Iterates over all locatable elements"), `get_by_loc` and a target-specific `position`; it is built by `ElementIntrospectorBuilder::discover_tag(&Tag, position)`. [typst-library introspector.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-library/src/introspection/introspector.rs)
- Python bindings mirror the CLI: `typst.query(selector, field=None, one=False, format=None, root=None)`. [typst-py docs](https://typst-py.readthedocs.io/en/latest/)

### Inferences
- A 0.14.2-compatible position dump: wrap each heading/figure/table/raw show rule in `context metadata((kind: ..., page: here().page(), pos: here().position(), number: counter(...).display()))` with a label, then `typst query main.typ "<docx>" --field value`. That yields the start position and page of every element but not its extent (no height/width) and not the glyph runs; `measure` could add sizes but only for content measured in isolation, not its laid-out box.
- The query CLI is a separate compile. It cannot share the compile that produced the PDF, so a wrapper that calls `typst compile` and then `typst query` runs the layout twice and has to trust that both converge identically (same fonts, same inputs, same timestamp). Only the Rust route (section 3) reads positions and frames from the one compile that made the PDF.
- Since the documented JSON shows `func`, `value` and `label`, a serialized `content` value is the evaluated element tree, not the realized layout; it is good for anchors and numbering, not as a body source.

### Gaps
- I found no documentation of how `typst query` serializes arbitrary styled `content` (post show-rule) or whether `location` fields appear in the JSON; the docs example only shows `metadata`.
- No published figure for the cost of a second compile on a report-sized document; the 0.14 context-performance fix suggests heavy `context` use was once pathological but gives no numbers.

## 3. The compiler's Rust API: frames, tags, the PDF tag tree, crate stability, and the `World`

### Takeaway
`typst::compile::<PagedDocument>` returns pages whose `Frame` holds `Group`, `Text`, `Shape`, `Image`, `Link` and `Tag` items; `Tag::Start`/`Tag::End` bracket every locatable element, and since 0.14 that includes paragraphs, tables, lists, raw blocks and images, so a walker can attribute every glyph run, fill rectangle and image to the element that produced it. Page layout wraps the header and footer marginals in `ArtifactKind::Header`/`Footer` (background in `ArtifactKind::Page` at v0.14.2) before composing the page, so header/footer separation is explicit, not geometric. `typst-pdf` already walks exactly these tags to build a krilla tag tree (Hn, L/LI/Lbl/LBody, Table/TR/TH/TD with spans and scope, Figure/Caption, Code, TOC/TOCI, Note). The crates are an explicitly low-level toolkit with no high-level stable API planned: the crate set was split between 0.12 and 0.13, `compile` became generic in 0.13, `Library::default` went in 0.14, and the MSRV moved 1.80 → 1.88 → 1.92, so a tool pins one version and is rebuilt per release. A custom binary must copy what `typst-cli`'s `SystemWorld` does: canonicalized root, virtual paths that cannot escape it, `typst-kit` font and package loaders, and a fixed `today`.

### Cited Findings

[tag.rs](https://github.com/typst/typst/blob/main/crates/typst-library/src/introspection/tag.rs); [typst-layout document.rs](https://github.com/typst/typst/blob/main/crates/typst-layout/src/document.rs) (both as read by the sibling note; I did not re-fetch them)

[Typst docs: pdf.artifact](https://typst.app/docs/reference/pdf/artifact/)

### Inferences
- The frame walk a DOCX writer needs is the walk `typst-pdf` already performs to tag the PDF: iterate `Frame::items()`, keep a stack of open `Tag::Start` elements, accumulate `Group` transforms for absolute coordinates, and attribute each `Text`, `Shape` and `Image` to the innermost open element. The cell fill of a table row is a `Shape` inside that cell's tag; the panel fill of a `raw` block is a `Shape` inside the surrounding `block`'s tag (the `raw` itself is tagged since 0.14); the caption glyphs are `Text` inside `FigureCaption`; header/footer glyphs sit inside `ArtifactKind::Header`/`Footer` tags. Since the tagging walk is on by default from 0.14, an extra walk costs the same order as tagging already does, but I found no measurement.
- Page numbers are a real problem for an editable DOCX: by the time the frame exists the number is a `Text` run ("3") inside the footer artifact. The walker can recognise the `CounterDisplayElem` over `CounterKey::Page` in the tag's `Content` and substitute a Word `PAGE` field, which is the only way to keep the footer editable rather than frozen per page.
- A crate-based tool is a second compiler unless the app's CLI is replaced by that same binary. With the app on 0.14.2 and the crates at 0.15.1, the PDF and DOCX would come from different compilers; the fix is to build one binary on one version that emits both PDF (via `typst_pdf::pdf`) and DOCX from the same `PagedDocument`, which restores the "one compile, both formats" guarantee but makes the app own a Rust build and a `World` with the sandboxing above.
- Breakage to expect per release: at least the MSRV bump each time, plus a changed `Library` constructor (0.14), a generic `compile` (0.13), a `World` signature (0.12), and tag/artifact kinds (0.15). None of these are announced as semver-breaking because the crates make no such promise.

### Gaps
- No primary source gives memory or time for a frame walk; the only related datum is that tagging is default since 0.14 without a changelog note on cost.
- I did not read `typst-pdf`'s frame walker (`handle_start`/`handle_end`) to confirm how it derives absolute positions from `Group` transforms, nor the `TagFlags.tagged` semantics for list items (the builder emits `ListItemLabel`/`Body`, so item tags exist, but I did not confirm which element carries them).
- `PdfOptions.tagged` as a new field in 0.14 was the summarizer's inference, not changelog text.
- The exact 0.15 `ArtifactKind` set used for the foreground and background was not read.

## 4. Community exporters: typlite, typort, typ2docx, tinymist, pandoc/typst-hs, Quarto

### Takeaway
Two Rust projects already drive DOCX from typst's own structures: typort (dianzuan, 2026, typst 0.15.1) walks the `HtmlDocument` tag stream for semantics, reads `PagedDocument` for fonts, sizes, colours, page geometry, headers/footers and section breaks, and reads the source AST for `set` rules, emitting OOXML with `quick-xml`; typlite (tinymist) parses the HTML export to an AST and writes DOCX with `docx-rs`, rendering any `context` content as SVG. Both are young and single-maintainer. typ2docx (PDF route plus pandoc math) is archived. Pandoc's typst reader (typst-hs 0.12, 2026-09-24, "targets typst 0.15.0 ... only partial support") evaluates expressions but has only "minimal" `context` and no location or numbering, and fails on common styling such as table strokes. Quarto only compiles typst to PDF and produces Word through pandoc's reference-doc.

### Inferences
- typort is the closest existing implementation of the "typst structures in, editable DOCX out" brief, and its three-source design (HTML tags for semantics, paged frames for geometry, AST for set rules) is the architecture a BTCT-native exporter would need. - typlite is maintained inside tinymist and tracks typst releases quickly (crate versions mirror typst minor versions), but its DOCX path is HTML-only, so panel fills, row fills and page furniture are lost by construction, and `context` content becomes pictures.

## 5. The reverse direction's lessons: DOCX style mapping and "faithful" vs "editable" modes

### Takeaway
Every mature semantic-to-DOCX writer maps block kinds to a fixed named-style vocabulary and lets a reference document restyle it: pandoc's set is `Heading 1..9`, `Body Text`/`First Paragraph`/`Compact`, `Source Code` with `Verbatim Char`, `Caption`/`Table Caption`/`Image Caption`, `Figure`/`Captioned Figure`, `Block Text`, `Footnote Text`, `TOC Heading`, `Hyperlink` and a `Table` table style, with `custom-style` divs/spans for anything else and raw OOXML for page breaks. The PDF-to-Word tools expose the fidelity trade-off as two or more explicit modes: Acrobat's "Retain Flowing Text" vs "Retain Page Layout" (the latter splits text into text-box groups), ABBYY's "Exact copy" / "Editable copy" / "Formatted text" / "Plain text" (plus "Flexible layout" for HTML). A typst-to-DOCX exporter has the same choice and can make it per element: styles and fields for flow, anchored frames only where the frame tree shows absolute placement.

### Cited Findings
- pandoc docx writer paragraph styles: Normal, Body Text, First Paragraph, Compact, Title, Subtitle, Author, Date, Abstract, AbstractTitle, Bibliography, Heading 1 to Heading 9, Block Text, Footnote Block Text, Source Code, Footnote Text, Definition Term, Definition, Caption, Table Caption, Image Caption, Figure, Captioned Figure, TOC Heading; character styles Default Paragraph Font, Verbatim Char, Footnote Reference, Hyperlink, Section Number; table style Table. [pandoc MANUAL, --reference-doc](https://pandoc.org/MANUAL.html)
- pandoc `custom-style` on spans and divs maps to Word character/paragraph styles; a style absent from the reference file "is added with standard text as its base"; the `styles` extension does the reverse when reading docx (styles become `custom-style` attributes on Divs/Spans). [Quarto: Word templates](https://quarto.org/docs/output-formats/ms-word-templates.html); [pandoc MANUAL, styles extension](https://pandoc.org/MANUAL.html)
- pandoc page break: a `{=openxml}` raw block containing `<w:p><w:r><w:br w:type="page"/></w:r></w:p>`. [pandoc MANUAL, raw_attribute](https://pandoc.org/MANUAL.html)
- pandoc's `native_numbering` extension numbers figures and tables for docx; headers/footers and page numbers are not covered by the writer options (they come from the reference document). [pandoc MANUAL](https://pandoc.org/MANUAL.html)
- docx4j-ImportXHTML: heading-to-style mapping is opt-in (`Element.Heading.MapToStyle`), class-to-style mapping is a separate option, and headings can still carry direct formatting on top of the style. [docx4j forum: 3.2.0-beta2](https://www.docx4java.org/forums/xhtml-import-f28/docx4j-importxhtml-3-2-0-beta2-t1961.html); [docx4j forum: heading formatting](https://www.docx4java.org/forums/post10389.html)
- Acrobat: "Retain Flowing Text" prioritizes text that wraps and flows through the document; "Retain Page Layout" keeps the look of the PDF and "may split the text into different text box groups to retain the original design". [Adobe: Export PDFs and retain layout](https://www.adobe.com/learn/acrobat/web/convert-pdf-retain-page-layout); a third-party guide describes the same: flowing text keeps a continuous sequence, page layout "create[s] an output file with individual text boxes". [Chron: Convert PDF to Word with Acrobat Pro](https://smallbusiness.chron.com/convert-pdf-word-using-acrobat-pro-54097.html)
- ABBYY FineReader 14/15 save modes: Exact copy (matches original formatting, for complex layouts such as booklets, limits later editing), Editable copy (may differ slightly, easy to edit), Formatted text (keeps fonts, sizes and paragraphs, not exact spacing or object placement, text left-aligned), Plain text, Flexible layout (HTML "with object positions as close to the original as is technically possible"). [ABBYY FineReader 15: saving](https://help.abbyy.com/en-us/finereader/15/user_guide/stepsave); FineReader 12 called it "Document layout" with the same four modes. [ABBYY FineReader 12](https://help.abbyy.com/en-us/finereader/12/stepsave); the Engine API enumerates `FormatParagraphs`, `PlainText`, `ExactCopy`, `EditableCopy`. [ABBYY Engine: TextEditorModeEnum](https://docs.abbyy.com/fine-reader/engine/visual-components-reference/enumerations/texteditormodeenum.md)
- Upstream typst's own framing of why DOCX is hard: "it is difficult to export already fully formatted, laid out and typeset documents to it". [Discussion #2561](https://github.com/typst/typst/discussions/2561) (sibling note's reading)

### Inferences
- "Editable" for a typst report means: headings as `Heading N` (with numbering as text or as Word list numbering), `raw` blocks as `Source Code` paragraphs with paragraph shading and `Verbatim Char` runs, tables as real `w:tbl` with `Table Grid` plus per-row `w:shd`, figures as inline pictures with `Caption`, lists as `w:numPr` numbering (nested levels), header/footer as section header/footer parts with a `PAGE` field, TOC as a `TOC` field (typort does exactly this). "Faithful" means absolute-positioned text boxes per page, which Acrobat and ABBYY both document as the price of fidelity. Because typst's tag tree and frames give both the semantic element and its laid-out box, an exporter can choose per element rather than per document: flow for everything the tag tree names, an anchored frame only for `place`d content that the tag tree marks as non-progressing.
- Page breaks are the one layout fact worth carrying from the frames into an otherwise flowing DOCX: insert `w:br type="page"` (or `pageBreakBefore`) where the frame tree shows an element starting a new page, accepting that Word's own line breaking will drift within the page.

### Gaps
- I found no documentation of distinct modes for Google Docs' PDF import; it appears to offer a single conversion. Not researched further.
- No source quantifies how pandoc's HTML reader treats CSS when used in an HTML-to-DOCX chain.

## 6. The five pentest-report structures across the four surfaces

### Takeaway
For a `raw` block in a filled panel, a `table` with per-row fill, a `figure` with `image` and `caption`, nested `enum`/`list`, and a `page` header/footer built with `place`: the frame tree carries everything (glyphs, fill rectangles, image bytes and size, absolute positions, header/footer artifacts) but as geometry attributed to elements through tags; the PDF tag tree carries the semantics (Code lines, Table/TR/TH/TD with spans, Figure/Caption with alt, L/LI/Lbl/LBody with numbering kind, Header/Footer artifacts) but no fills or positions; HTML export carries the semantics without fills and drops `place`/`page` entirely; `typst query` carries the element fields and, via `metadata`, start positions. Only the frame tree knows a row is grey or a panel has a background, and only the tag tree and HTML know what a run of text is.

### Cited Findings
Raw block with a fill/panel
- Frame tree: `raw` is locatable since 0.14, so its glyphs sit between its `Tag::Start`/`End`; the panel background is a `Shape` ("A geometric shape with optional fill and stroke") emitted by the wrapping `block`. [Changelog 0.14.0](https://typst.app/docs/changelog/0.14.0/); [docs.rs: FrameItem](https://docs.rs/typst-library/latest/typst_library/layout/enum.FrameItem.html)
- Tag tree: block `raw` → `CodeBlock` with one `CodeBlockLine` per line, inline `raw` → `Tag::Code`; "Paths and shapes are also marked automatically" as artifacts, so the fill is an artifact, not structure. [typst-pdf build.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-pdf/src/tags/tree/build.rs); [Typst docs: pdf.artifact](https://typst.app/docs/reference/pdf/artifact/)
- HTML: `pre` wrapping `code` with `data-lang`, syntax highlighting since 0.14; the block fill is "never read, so it's silently ignored". [typst-html rules.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-html/src/rules.rs); [typst-html convert.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-html/src/convert.rs)
- Query: `raw` is queryable without a label since 0.14. [Changelog 0.14.0](https://typst.app/docs/changelog/0.14.0/)

Table with per-row fill
- Frame tree: `table` locatable since 0.14; the PDF tag context resolves a `CellGrid` with per-cell `rowspan`/`colspan`, header scope and stroke priority, which means the cell geometry is recoverable from the same tags. [Changelog 0.14.0](https://typst.app/docs/changelog/0.14.0/); [typst-pdf context/table.rs](https://github.com/typst/typst/blob/main/crates/typst-pdf/src/tags/context/table.rs)
- Tag tree: `Table` group, cells `TD` (TH/TR and spans set in the table context), krilla `TH` carries `scope()`/`headers()`, `TD` carries `row_span()`/`col_span()`; repeated header/footer cells on later pages are `Artifact(PaginationOther)`; `pdf.header-cell`/`pdf.data-cell`/`pdf.table-summary` are experimental behind `a11y-extras`. Fills are shapes, hence artifacts. [typst-pdf build.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-pdf/src/tags/tree/build.rs); [docs.rs: krilla TagKind](https://docs.rs/krilla/latest/krilla/tagging/enum.TagKind.html); [Changelog 0.14.0](https://typst.app/docs/changelog/0.14.0/)
- HTML: `table`/`thead`/`tbody`/`tfoot`, `td`/`th`, `colspan`/`rowspan` when not 1; "Table fills, strokes, column widths: not emitted". [typst-html rules.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-html/src/rules.rs)
- Query: `table` queryable without a label since 0.14. [Changelog 0.14.0](https://typst.app/docs/changelog/0.14.0/)

Figure with image and caption
- Frame tree: `Image(Image, Size, Span)` "An image and its size" plus caption `Text` runs; `figure.caption` and `image` locatable since 0.14. [docs.rs: FrameItem](https://docs.rs/typst-library/latest/typst_library/layout/enum.FrameItem.html); [Changelog 0.14.0](https://typst.app/docs/changelog/0.14.0/)
- Tag tree: `Figure` group with locale, `FigureCaption`, `Image` group; krilla `Figure` carries `alt_text()` (required under PDF/UA-1). [typst-pdf build.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-pdf/src/tags/tree/build.rs); [docs.rs: krilla TagKind](https://docs.rs/krilla/latest/krilla/tagging/enum.TagKind.html)
- HTML: `figure` with `figcaption` before or after by position, `img` with base64 data URL, `width`, `height`, `alt`. [typst-html rules.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-html/src/rules.rs)

Nested enum/list
- Tag tree: `list` → `List` with `ListNumbering::Circle`, `enum` → `Decimal`, `terms` → `None`; items → `ListItemLabel`/`ListItemBody`; 0.15.0 fixed list marker errors. [typst-pdf build.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-pdf/src/tags/tree/build.rs); [Changelog 0.15.0](https://typst.app/docs/changelog/0.15.0/)
- HTML: `ul`/`ol`/`li` (with `start`/`reversed`/`value`), `dl`/`dt`/`dd`; non-tight lists add paragraph breaks. [typst-html rules.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-html/src/rules.rs)
- Query: `list`, `enum`, `terms` queryable without a label since 0.14. [Changelog 0.14.0](https://typst.app/docs/changelog/0.14.0/)

Page header/footer built with `place`
- Frame tree (v0.14.2): header and footer are laid out as separate frames in regions of width `inner.width()` and height `margin.top - header_ascent` / `margin.bottom - footer_descent`, wrapped in `ArtifactKind::Header`/`Footer`; the default page-number marginal is a `CounterDisplayElem` over the page counter that becomes the header or footer by `number_align.y()`. [typst-layout pages/run.rs @ v0.14.2](https://raw.githubusercontent.com/typst/typst/v0.14.2/crates/typst-layout/src/pages/run.rs)
- Tag tree: headers, footers, backgrounds and foregrounds are automatically artifacts; `pdf.artifact` offers `header`, `footer`, `page-number` kinds; non-floating `place` makes no progression in the tree (its content stays in the enclosing group), floating `place` is a `LogicalParent`. [Typst docs: pdf.artifact](https://typst.app/docs/reference/pdf/artifact/); [typst-pdf build.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-pdf/src/tags/tree/build.rs)
- HTML: `page` and `place` have no handler and are dropped with "{name} was ignored during HTML export". [typst-html convert.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-html/src/convert.rs)
- Query: 0.12 fixed `here().position()` inside `place` within `context`, so a `metadata` dropped from a header's `place` reports its page and position. [Changelog 0.12.0](https://typst.app/docs/changelog/0.12.0/)

### Inferences
- The minimum viable native route for this report style is a Rust binary on one pinned typst version that (1) compiles once to `PagedDocument`, (2) writes the PDF with `typst_pdf::pdf`, (3) walks each page's frame with a tag stack to produce an element-attributed geometry stream, and (4) emits DOCX from that stream using the pandoc style vocabulary: `Heading N`, `Source Code` + paragraph shading from the panel `Shape` colour, `w:tbl` rows with `w:shd` from the row `Shape` colours, inline picture + `Caption`, `w:numPr` from `List`/`Decimal` numbering kinds, section header/footer from the `Header`/`Footer` artifact frames with the page-counter run swapped for a `PAGE` field, and a `TOC` field where the `Outline` group starts. The HTML export is optional in that design; typort uses it because the HTML DOM gives paragraph grouping for free, but since 0.14 `par` is tagged in the frames too.
- On the app's current 0.14.2 CLI, none of this is reachable from outside the compiler except through `typst query` metadata (start positions, numbers, page) and the tagged PDF's structure tree, both of which are already produced or cheap to add to the existing pdf2docx pipeline.

### Gaps
- I did not compile a sample document to dump the actual frame items, tag tree or HTML for these five structures; the findings above are from source reading and docs, not execution.
- Whether the `raw` panel fill is emitted by `block` or by `raw`'s own show rule depends on the template; the attribution rule (innermost open tag) is my inference.
- The HTML handling of `grid` cells inside a table-like layout is unconfirmed (see section 1).
