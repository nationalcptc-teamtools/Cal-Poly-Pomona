# PDF to DOCX conversion and PDF layout reconstruction: state of the art as of October 2026

Scope: tools, libraries and techniques for turning a technically generated PDF (typst or LaTeX, tagged, embedded fonts, code panels, shaded tables, screenshots, running header and footer, dot-leader contents page) into a Word document that keeps the page layout. Dates and versions are as found on 2026-10-10. Local evidence from this repository is cited by relative path; everything else is a URL.

## Key question 1: pdf2docx (dothinking): version, maintenance, issues, internal model, forks

### Takeaway
pdf2docx is at 0.5.13 (1 May 2026), now lives under the ArtifexSoftware GitHub organisation, was relicensed AGPL to MIT in 0.5.12 (March 2026), and is declared "no longer actively maintained by Artifex". Its model is rule based: PyMuPDF text dict plus drawings in, one Word section per PDF page out, paragraphs with exact line heights computed from line bboxes, tables from stroke/fill geometry or from text alignment, and no notion of a running header or footer at all.

Internal model (from source)
- Page.make_docx creates one Word section per PDF page: `doc.add_section(WD_SECTION.NEW_PAGE)` once the document has content, else it reuses the default section, then sets `section.page_width/page_height` and the four margins in points and delegates to `self.sections.make_docx(doc)` (hierarchy Section > Column > Blocks). `self.header` and `self.footer` are stored but never written; float images are a separate collection not emitted by this method. [Page.py](https://raw.githubusercontent.com/ArtifexSoftware/pdf2docx/master/pdf2docx/page/Page.py)
- TextBlock line spacing: exact mode writes `pf.line_spacing = Pt(round(self.line_space, 1))` where `line_space = (block_height - first_line_height)/(count-1)` (average top-to-top distance of rows); relative mode writes a multiplier `block_height/standard_height`, floored at a default because "overlap may exist when multi-rows". In exact mode the first line's extra height is moved into spacing before (`before_space += first_line_height - line_space`), and a negative result zeroes before_space and reduces line_space. Negative before/after spacing is clamped to 0. [TextBlock.py](https://raw.githubusercontent.com/ArtifexSoftware/pdf2docx/master/pdf2docx/text/TextBlock.py)
- Alignment: JUSTIFY only when both left and right edges align over three or more rows; CENTER by midpoint; mixed rows get NONE then LEFT plus tab stops ("ensure exact position of each line by TAB stop"); the indent on the opposite side is rounded down to whole inches "so it saves more space to avoid unexpected line break". [TextBlock.py](https://raw.githubusercontent.com/ArtifexSoftware/pdf2docx/master/pdf2docx/text/TextBlock.py)
- Tables: lattice tables come from stroke groups connected within `connected_border_tolerance`, with fills inside the group's bbox taken as shading; stream tables come from text-line alignment (`collect_stream_lines`), a candidate is skipped when it has no explicit strokes or shadings and `_is_simple_structure` is true, vertical borders define structure and horizontal ones are reference only up to two columns, a nested 1x1 table is kept only if it has a background colour, and a comment says "shading with any intersections should be counted to avoid missing any candidates". [TablesConstructor.py](https://raw.githubusercontent.com/ArtifexSoftware/pdf2docx/master/pdf2docx/table/TablesConstructor.py)

Measured behaviour on a typst pentest report (this repository)
- The 23-page reference report converted raw through pdf2docx came back as 44 Word pages, "near-identical to the PDF, but 21 pages too many and a scrambled contents page"; the footer "overflowed every page" because pdf2docx "has no idea that the band at the bottom of each page is a running footer; it converts it as body content"; deleting the two bands from the PDF before converting gave "23 in, 23 out". [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 866 to 886)
- The same document put the contents page "inside a table with merged cells", with dot leaders as literal runs of periods; a paragraph inside a table cell clips its dot leader at the cell's width. [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 881 to 983)
- "What pdf2docx gets systematically wrong": the exact line height is "its own guess at the font's line box, not the distance the PDF put between two lines" (17.0 pt pitch written as 19.6); spacing before is measured from the previous row's ink while Word measures from the previous line box; the same gap is written as spacing after and spacing before and both apply; a paragraph Word wraps differently shifts everything under it. [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 1619 to 1632)
- pdf2docx writes a sub-heading and the paragraph under it as one paragraph with a line break, so one exact line height has to serve two leadings (19.7 and 14.8 pt). [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 2247 to 2255)
- It writes a section break "every time its two-column detection changes its mind down a page" (15 sections for 2 PDF pages on an IEEE-style document); on a sparse page it merges a whole list and its heading into one paragraph; it drops the spaces between right-to-left words. [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 1316 to 1321, 2819 to 2829)
- Scorecard: a 120-page stress report converts raw to 238 Word pages at mean structural similarity 0.6400, and to 120 pages at 0.7723 once the tagged Header and Footer artifacts are lifted and the contents page rebuilt; the reference report goes from 44 pages at 0.7684 (raw) to 23 pages at 0.9215. [server/typst/pdf-to-docx/corpus/SCORECARD.md](../../server/typst/pdf-to-docx/corpus/SCORECARD.md)

### Inferences
- The project is in caretaker mode: the 2026 releases are a relicence, a version bump, two narrow bug fixes and a dependency pin, with 87 issues open, several of them PyMuPDF API drift (#360, #329). Anyone depending on it should pin PyMuPDF and expect to carry fixes themselves.
- Page growth is structural, not a bug: per-page sections plus body-flowed running bands plus exact heights derived from line bboxes means any mismatch between pdf2docx's line box and Word's pushes content off the page, with nowhere for it to go but a new page.
- The absence of header/footer, list and code-block concepts in the source is why those three are the main repair targets for any wrapper.

### Gaps
- No notable fork or successor was identified; the 501 forks were not individually inspected and no search result named one. The nixpkgs commit that re-points the source to ArtifexSoftware was surfaced by search but not read.
- The Chinese technical document linked from the README (the only narrative description of the pipeline) redirects to a blog shell and was not readable; the internal model above comes from the source files directly.
- Line-spacing issue #130 is closed, but what shipped (which of the "two kinds" became the default) was not determined.

## Key question 2: alternatives and how they handle fixed layout

### Takeaway
Every converter that preserves page layout does it one of two ways: a "flow" mode that rebuilds paragraphs, tables, columns and (sometimes) Word headers and footers and accepts drift, or an "exact/textbox/frames" mode that puts each text group in an absolutely positioned Word text box and gives up editability. Adobe Acrobat's export is licensed Solid Documents technology. The document-AI parsers (Docling, marker, MinerU, Nougat, Unstructured) output Markdown/JSON and are built for RAG, not layout-faithful DOCX; MinerU is the only one listing DOCX as a render target.

### Cited Findings

- Acrobat's export offers "Retain Flowing Text", which "prioritizes the ability for text to wrap and flow seamlessly throughout the exported document", and "Retain Page Layout" for when "you would like your newly-exported document to stay in the same layout as your PDF", which "may split the text into different text box groups to retain the original design". [Adobe](https://www.adobe.com/learn/acrobat/web/convert-pdf-retain-page-layout)
- "Adobe Systems Incorporated (Adobe) has licensed the Solid Framework SDK for Adobe Acrobat X" (2010) for PDF-to-Word and Excel; a May 2013 announcement covered Acrobat XI. [Solid Documents](https://www.soliddocuments.com/pdf/_solidframework_adobe_x/300); Wikipedia says the partnership continued with Acrobat DC. [Wikipedia: Solid Documents](https://en.wikipedia.org/wiki/Solid_Documents)

### Inferences
- For a 1 to 2 GB Linux container the viable self-hosted options are pdf2docx (Python, PyMuPDF + python-docx), Apryse's Structured Output (commercial, Linux x64/ARM64, 4 GB recommended), Solid Framework (commercial .NET SDK), or ONLYOFFICE's x2t (AGPL). The document-AI parsers either need a GPU for acceptable throughput or emit Markdown, not a laid-out DOCX; MinerU's DOCX target is a rendering of its Markdown-level content model, not a layout-preserving reconstruction.
- Commercial "exact" modes solve page fidelity by abandoning flow (text boxes), which is the opposite of what an editable pentest report needs; the flow modes all document that layout may change.

## Key question 3: techniques (layout preservation, headers/footers, tables, justified text, fonts, fidelity measurement)

### Takeaway
Layout is kept either by per-paragraph exact spacing inside flowing sections (pdf2docx, the flow modes) or by text boxes/frames (Exact, Textbox, Frames, "Retain Page Layout"). Running bands are found by repetition across pages (Lin 2003 page association, Levenshtein on first/last lines, page-number sequence tests) unless the PDF is tagged, in which case the Header/Footer artifacts say it outright. Tables come from rulings (strokes, OpenCV line morphology) or from text alignment heuristics, with learned models (TableFormer) for borderless cases. Word only embeds TrueType-outline fonts, so CFF faces must be redrawn. No paper measuring PDF-to-DOCX fidelity was found; OmniDocBench's metrics (edit distance, TEDS, reading-order edit distance) are the nearest published standard.

### Cited Findings

Keeping a page's layout
- Per-paragraph exact spacing in flowing sections: pdf2docx writes `pf.line_spacing = Pt(...)` from measured row pitch, moves first-line excess into space-before, and rounds the opposite indent down to whole inches "to avoid unexpected line break". [TextBlock.py](https://raw.githubusercontent.com/ArtifexSoftware/pdf2docx/master/pdf2docx/text/TextBlock.py)
- Text boxes: Adobe "may split the text into different text box groups"; Solid Exact "Uses Word text boxes"; Aspose Textbox "each visually grouped text block becomes a textbox"; Able2Extract Frames puts text "into individual Word text boxes". [Adobe](https://www.adobe.com/learn/acrobat/web/convert-pdf-retain-page-layout); [Solid](https://www.soliddocuments.com/pdf/_conversion_output/259/1); [Aspose](https://docs.aspose.com/pdf/net/convert-pdf-to-word/); [Able2Extract](https://support.investintech.com/hc/en-us/articles/200947457-What-is-the-Frames-conversion-to-Word-option-in-Able2Extract)
- Fit-to-page adjustment: Apryse says "fonts and formatting are adjusted so page content fits on a single page". [Apryse PDF2Word CLI](https://docs.apryse.com/cli/guides/pdf2word)
- Word-side constraints a converter has to work around (measured here): Word places the body at `max(topMargin, headerDistance + headerHeight)`, so adding a header to pdf2docx output pushed 23 pages to 28 until the top margin was reduced by the same amount; Word merges a paragraph's tab stops with the Header style's own (centre at 4.5", right at 9") unless each inherited stop is cleared; WordprocessingML child order is validated, so appending `w:shd`/`w:pBdr` out of sequence yields "the file appears to be corrupted". [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 945 to 966)
- One Word paragraph has one exact line height for all its lines, so a heading and body line written into one paragraph cannot both keep their leading. [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 2247 to 2255)
- Dot leaders: Word repeats the leader glyph at the font's advance width only, so leaders set at 4.8 pt came back at 3.1 pt until the difference was added as character spacing on the run carrying the tab. [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 1652 to 1659)

Detecting running headers and footers
- dedoc implements Xiaofan Lin, "Header and footer extraction by page association" (Document Recognition and Retrieval X, SPIE 2003): compare the first and last few lines of each page across pages using Levenshtein similarity, with even and odd pages compared separately for documents of six or more pages. [dedoc source](https://dedoc.readthedocs.io/en/latest/_modules/dedoc/readers/pdf_reader/utils/header_footers_analysis.html)
- Microsoft's "Pattern Matching Engine" patent application (US 2013/0191366) matches content across pages to find repeating patterns, classifies them as headers, footers or watermarks, and detects page numbers by checking that a number on one page increases by one on the next. [Justia](https://patents.justia.com/patent/20130191366)
- Solid converts detected bands to Word headers/footers, text boxes, or removes them, and only in Flowing mode. [Solid](https://www.soliddocuments.com/pdf/_conversion_output/259/1)
- marker removes "headers/footers/other artifacts" by default via its layout model. [marker](https://github.com/datalab-to/marker)
- all2md "can detect repeating header/footer patterns automatically and set trim heights". [all2md](https://all2md.readthedocs.io/en/latest/api/all2md.options.pdf.html)
- Local repetition heuristic: rows in the top or bottom 12% of a page, normalised (digits to `#`), counted as a band when the key appears on at least 60% of pages that have anything in the zone, kept only if within about 1.6 row heights of the outermost repeating row (so a repeating body heading is not deleted), with repeating vector drawings within 30 pt joining the band; page numbers found as a digit slot equal to page index plus a constant and written as a real `PAGE` field. [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 894 to 932)
- With a tagged PDF the same tool reads the Header and Footer artifacts instead ("the rows that disappear when the PDF's Header and Footer artifacts are removed"), keeping the heuristic for untagged PDFs. [SCORECARD.md](../../server/typst/pdf-to-docx/corpus/SCORECARD.md); [server/typst/pdf-to-docx/tagged.py](../../server/typst/pdf-to-docx/tagged.py)

Rebuilding tables
- Camelot Lattice renders the page and applies "morphological transformations (erosion and dilation) using OpenCV" to isolate horizontal and vertical segments, finds intersections and assigns words to cells by coordinates; Stream groups words into rows "based on their y axis overlaps", estimates table areas from text edges and infers columns from the typical number of words per row. [Camelot](https://camelot-py.readthedocs.io/en/latest/user/how-it-works.html)
- pdfplumber's `vertical_strategy`/`horizontal_strategy` accept "lines" (default; graphical lines including rectangle sides), "lines_strict" (no rectangle sides), "text" (imaginary lines from word-edge alignment) and "explicit". [pdfplumber](https://github.com/jsvine/pdfplumber)
- pdf2docx: lattice from connected strokes plus fills as shading; stream from text alignment with a "simple structure" veto; 1x1 nested tables only kept when shaded. [TablesConstructor.py](https://raw.githubusercontent.com/ArtifexSoftware/pdf2docx/master/pdf2docx/table/TablesConstructor.py)
- Aspose EnhancedFlow recognises borderless tables; Solid detects tables only in flow modes; Docling uses the learned TableFormer model. [Aspose](https://docs.aspose.com/pdf/net/convert-pdf-to-word/); [Solid](https://www.soliddocuments.com/pdf/_conversion_output/259/1); [arXiv 2408.09869](https://arxiv.org/abs/2408.09869)
- Measured: pdf2docx reads a table's top off the PDF's grid lines and sizes rows from them, so its rules land on the PDF's; it also renders four rounded severity boxes as one table with a rule above and below, and puts a contents page into a merged-cell table. [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 1641 to 1648, 2828 to 2829, 977 to 984)

Reading order
- LayoutReader (EMNLP 2021) is a seq2seq model over text and layout trained on ReadingBank (500,000 document images). [LayoutReader](https://preview.aclanthology.org/setup/2021.emnlp-main.389)
- A 2026 paper describes recursive XY-cut as alternating projection-profile splits that fail "on pages where one or more boxes intersect every candidate vertical cut", and notes LayoutReader's word-level supervision may not transfer to line or paragraph inputs. [arXiv 2607.01018](https://arxiv.org/pdf/2607.01018)
- MuPDF's structured text can carry the PDF structure tree as STRUCT blocks to be walked depth-first, which gives tagged order rather than drawing order. [MuPDF stext details](https://mupdf.readthedocs.io/en/latest/_static/generated/c/html/structfz__stext__page__details.html)

Justified text
- pdf2docx infers JUSTIFY only from both edges aligning over three or more rows, and otherwise LEFT with tab stops per line; the inch-rounding of the opposite indent exists so Word does not re-wrap. [TextBlock.py](https://raw.githubusercontent.com/ArtifexSoftware/pdf2docx/master/pdf2docx/text/TextBlock.py)
- Measured: the last line of a justified paragraph is the one pdf2docx "gets right on some paragraphs", and a paragraph Word wraps differently moves everything under it. [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 1430 to 1436, 1630 to 1632)

Fonts
- Microsoft: "Not all TrueType fonts can be embedded"; embeddability levels are "Non-embeddable, Preview/Print, Editable, and Installable"; it recommends OTF or TTF and says to "Avoid PostScript fonts (.PFB, .PFM)". [Microsoft](https://support.microsoft.com/en-us/office/embed-fonts-in-word-powerpoint-or-excel-cb3982aa-ea76-4323-b008-86670f222dbc)
- A former Adobe type scientist on the Adobe forum: Microsoft "only allows embedding of TrueType fonts and OpenType TrueType-flavored fonts" in Office documents; CFF-flavoured .otf and Type 1 are not embeddable. [Adobe community](https://community.adobe.com/t5/type-typography-discussions/adobe-opentype-fonts-with-truetype-outlines-for-microsoft-office/m-p/6108234)
- A Print/Preview-only embedded font produces a read-only document; a Restricted font cannot be embedded. [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/a/11434862)
- CFF to TrueType redrawing: fontTools' `Snippets/otf2ttf.py` builds a `glyf` table through the cu2qu pen and drops the CFF table, default approximation error 1.0 font units. [fontTools snippet](https://fuchsia.googlesource.com/third_party/fonttools/+/refs/tags/4.4.1/Snippets/otf2ttf.py); a CTAN variant uses `Cu2QuPen` with tolerance 0.6 scaled by UPEM/1000. [CTAN otf2ttf.py](https://ctan.uib.no/fonts/utilities/mtp2otf/tools/otf2ttf.py)
- pdf2docx font failures: "Replace font ... with Times New Roman due to lack of data" (#131) and "cannot find builtin font" (#216, #235). [Issues](https://github.com/dothinking/pdf2docx/issues?q=is%3Aissue+sort%3Acomments-desc)
- pdf2htmlEX sidesteps substitution by extracting the PDF's fonts to @font-face. [pdf2htmlEX](https://github.com/pdf2htmlEX/pdf2htmlEX/wiki/Limitations)

Measuring fidelity
- OmniDocBench (CVPR 2025) scores text by Normalized Edit Distance, tables by TEDS, formulas by CDM, reading order by edit distance, overall = ((1 - text edit) x 100 + TEDS + CDM)/3; 1,651 pages, 10 document types; layout categories include `header`, `footer`, `page_number`, `code_txt`, `figure_caption`, `table_caption`, `code_txt_caption`; there is no list category. [OmniDocBench](https://github.com/opendatalab/OmniDocBench); [arXiv 2412.07626](https://arxiv.org/abs/2412.07626)
- DocLayNet: 80,863 manually annotated pages, 11 classes, a double/triple-annotated subset to measure agreement, and current models "approximately 10%" behind human agreement. [arXiv 2206.01062](https://arxiv.org/abs/2206.01062)
- Local scorecard method: mean structural similarity per page between the PDF and the DOCX rendered through Word, plus Word page count against PDF page count, blank pages, "band in body", ink past the right margin, converter seconds, Word render seconds, and a text-retention rule; Word's run-to-run noise measured at 0.00000 on means in one session but up to 0.0155 across sessions when Word laid out a page 0.19 pt narrower. [SCORECARD.md](../../server/typst/pdf-to-docx/corpus/SCORECARD.md)

### Inferences
- Converters that keep page count without text boxes all end up writing exact line heights and exact gaps; the open question is where the numbers come from. pdf2docx derives them from glyph boxes (and drifts); a compiler-side exporter could derive them from the layout engine's own leading.
- The header/footer problem has two solutions with different reliability: repetition heuristics need several pages and a rule to avoid eating repeating body headings; the tagged route is exact but only exists for PDFs whose producer tags artifacts (typst 0.14+, Word's own export, LaTeX with tagpdf).
- Fonts are the one place a converter must change bytes rather than describe them: a typst report set in a CFF face has to be redrawn to TrueType or Word will silently substitute.

### Gaps
- No peer-reviewed paper or vendor white paper measuring PDF-to-DOCX fidelity (page count, text retention, structural similarity) was found; OmniDocBench and olmocr-bench measure Markdown/HTML output, not DOCX.
- No vendor documents how it handles justified text so it does not re-wrap; the only concrete technique found is pdf2docx's indent rounding.
- Solid's quality-improvement PDF could not be read and may contain their test method.

## Key question 4: tagged PDF: what typst emits and which tools read structure tags

### Takeaway
Typst 0.14.0 (24 Oct 2025) made every PDF tagged by default with opt-in PDF/UA-1; the exporter maps paragraphs to P, lists to L/Lbl/LBody, code blocks to Code with one P per line, figures to Figure plus Caption, outlines to TOC/TOCI, and automatically marks page headers, footers, backgrounds and hyphens as artifacts (with specific artifact kinds such as header, footer, page-number since 0.15.0). No PDF-to-Word converter documents using the structure tree. The libraries that expose both the tag tree and glyph positions are MuPDF/PyMuPDF (STRUCT blocks, `TEXT_COLLECT_STRUCTURE`, still undocumented), playa-pdf (MIT, MCIDs on every content object), pdfplumber (experimental `mcid`/`tag` on chars), pdfium (fpdf_structtree.h, MCIDs per element) and Poppler's GLib structure API.

### Cited Findings

What typst emits
- Typst 0.14.0 (24 Oct 2025): "Typst PDFs are now tagged by default"; PDF/UA-1 is opt-in and "PDF/UA-2 is not yet supported, but planned"; `--no-pdf-tags` turns tagging off; `pdf.artifact` was added "for marking content as not semantically meaningful"; experimental `pdf.header-cell`, `pdf.data-cell`, `pdf.table-summary` behind the `a11y-extras` feature; `figure.alt` added; supported PDF versions 1.4, 1.5, 1.6, 1.7 and 2.0; "PDF heading bookmarks now contain the heading's numbering". [Typst 0.14.0 changelog](https://www.typst.app/docs/changelog/0.14.0)
- The 0.14 release post: "If you are using the built-in markup and elements, Typst will automatically select the right tags!"; PDF/UA-1 checks "find issues such as missing document titles, wrong heading hierarchies, and missing alternative descriptions". [Typst 0.14 blog](https://typst.app/blog/2025/typst-0.14)
- Typst 0.15.0 (15 Jun 2026): "Added support for more specific artifact kinds in pdf.artifact; these are now internally used when appropriate"; "Fixed 'invalid document structure' errors with complex list markers"; "Fixed wrong PDF tagging order for inline content outside of paragraphs"; "Fixed bounding box computations for stroked shapes in tagged PDFs"; "Typst can now target multiple (compatible) PDF standards at once, e.g. PDF/UA-1 and PDF/A-2a"; footnote links moved inside the superscript "improving PDF tagging"; variable fonts supported. [resolve/mod.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-pdf/src/tags/resolve/mod.rs)

- Content-level tagging in `tags/mod.rs`: text runs get a Span tag carrying the language; images a Span with alt text; shapes become `ContentTag::Artifact` of type Layout unless given an alt; tilings are `ArtifactType::Background` (Other on PDF 1.7); page content is wrapped in an artifact when `parent_artifact()` returns a type; link annotations are tagged only when `LinkAnnotationKind::Tagged`. [tags/mod.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-pdf/src/tags/mod.rs)
- Observed here: the converter reads typst's `/Artifact` marked content with Header and Footer types and gates the contents-page rebuild on a `/TOC` node in the tag tree. [server/typst/pdf-to-docx/tagged.py](../../server/typst/pdf-to-docx/tagged.py); [CLAUDE.md](../../CLAUDE.md)
- The PDF Association's Tagged PDF Best Practice Guide defines a tagged PDF as one meeting ISO 32000 clause 14.8. [PDF Association](https://pdfa.org/wp-content/uploads/2023/07/Tagged-PDF-Best-Practice-Guide.pdf); the Code tag "is used to encapsulate programming code or code snippets". Converters and tags
- None of Adobe, Solid, Aspose or Apryse's pages fetched state that PDF-to-Word reads the structure tree. [Adobe community](https://community.adobe.com/t5/acrobat-discussions/how-to-convert-pdf-to-word/m-p/2620585/highlight/true)
- Tag quality varies by producer: "tag generation is, to put it mildly, highly variable across different PDF authoring tools". [pdfplumber issue 909](https://github.com/jsvine/pdfplumber/issues/909)

Libraries that read the tag tree with glyph positions
- MuPDF: the structured-text page gained "a new type of block, STRUCT, that turns this into a tree"; a STRUCT block carries an index and a type (DOC, TOC, TOC_ITEM, STORY, SECTION, HEADING, PARAGRAPH as examples); MuPDF converts the PDF structure tree (via MCIDs) into nested begin/end structure calls, and callers "must do a depth-first traversal". [MuPDF stext details](https://mupdf.readthedocs.io/en/latest/_static/generated/c/html/structfz__stext__page__details.html); `fz_stext_struct` has `up`, `parent`, `first_block`, `last_block`, `standard` (fz_structure) and `raw`. [fz_stext_struct](https://mupdf.readthedocs.io/en/latest/_static/generated/c/html/structfz__stext__struct.html)
- PyMuPDF (docs up to 1.28.2): `TEXT_COLLECT_STRUCTURE` (256) "Extracts or generates the Document structure" with documentation "still pending"; `TEXT_IGNORE_ACTUALTEXT` (2048) uses displayed text instead of ActualText; `TEXT_SEGMENT` (4096) page segmentation, also pending; `TEXT_COLLECT_VECTORS`, `TEXT_COLLECT_STYLES` (fake bold detection), `TEXT_ACCURATE_BBOXES`. [PyMuPDF constants](https://pymupdf.readthedocs.io/en/latest/vars.html)
- MuPDF substitutes ActualText for visible text during extraction (Ghostscript bug 708005), which is the mechanism behind pdf2docx #379's glued words. [Ghostscript bug 708005](https://bugs.ghostscript.com/show_bug.cgi?id=708005); [pdf2docx issue search](https://github.com/ArtifexSoftware/pdf2docx/issues?q=is%3Aissue+spacing+OR+overflow+OR+blank+OR+shading+OR+background)
- playa-pdf 1.1.0 (9 Mar 2026, MIT, David Huggins-Daines, no dependencies, Python >= 3.8): `pdf.structure` and `page.structure` expose the logical structure tree with `find`/`find_all`; every content object exposes marked-content sections `obj.mcs` (mcid, tag, props), `mcstack` and nearest `obj.mcid`; glyph `bbox` computed lazily; page-level parallelism via `max_workers`; it "includes code from pdfminer.six" and implements its layout analysis. [playa-pdf on PyPI](https://pypi.org/project/playa-pdf/)
- pdfplumber (MIT): chars, lines, rects, curves and images carry `mcid` and `tag` ("The marked content section ID ... Experimental attribute"); no structure-tree accessor is documented in the README. [pdfplumber](https://github.com/jsvine/pdfplumber); Poppler's `pdfinfo -struct` / `-struct-text` print the tree. [pdfplumber issue 909](https://github.com/jsvine/pdfplumber/issues/909)
- pdfium `fpdf_structtree.h`: `FPDF_StructTree_GetForPage`, `FPDF_StructElement_GetType/GetRawType/GetActualText/GetAltText/GetTitle/GetParent`, attribute accessors, `FPDF_StructElement_GetMarkedContentID` (may be deprecated), `GetMarkedContentIdCount`/`GetMarkedContentIdAtIndex` (experimental); the header does not map MCIDs to glyph positions. [pdfium](https://pdfium.googlesource.com/pdfium/+/refs/heads/main/public/fpdf_structtree.h)
- Poppler's GLib `PopplerStructureElement` API (headings, lists, tables, figures, alt text, reading order) has existed since Poppler 0.26, navigated with `poppler_structure_element_iter_new()`. [Poppler source (codebrowser)](https://codebrowser.dev/kde/poppler/glib/poppler-structure-element.cc.html); Okular opened bug 522026 in June 2026 to add UA-1/UA-2 support on top of it. [okular-devel](https://mail.kde.org/pipermail/okular-devel/2026-June/049485.html)
- Commercial SDKs expose the tree as `StructElement`s and `ContentItem` leaves keyed by MCID (Apryse) and as "tagged content" (Aspose). [Apryse LogicalStructureTest](https://docs.apryse.com/samples/py/LogicalStructureTest); [Aspose tagged content](https://docs.aspose.com/pdf/python-net/extract-tagged-content-from-tagged-pdfs)

### Inferences
- Since 0.14 "now" tags by default, typst 0.13 output was untagged; a converter cannot rely on artifacts for PDFs compiled before October 2025.
- Typst's mapping covers every structure a pentest report needs to identify (Code for panels, L/LBody for nested lists, Table cells, Figure plus Caption, TOC/TOCI, Header/Footer artifacts), which is exactly the information PDF-side heuristics struggle to recover; a tag-aware converter can skip the detection step for typst 0.14+ output.
- PyMuPDF is the only one of the Python libraries that can give both the structure tree and the drawing/shading geometry pdf2docx already consumes, but its structure flag is undocumented; playa-pdf is the cleanest documented route from MCIDs to glyph boxes and is pure Python, so it fits a small container.

### Gaps
- The constructors for heading tags (`Hn`) and table tags (Table/TR/TH/TD/THead) live in files not fetched (`tags/tree/build.rs` and the table context); the mapping above is partial.
- Whether Acrobat, Solid, Aspose or Apryse consult the structure tree during PDF-to-Word was not documented anywhere found; the Adobe community statement is anecdotal.
- Typst 0.13's changelog was not fetched, so the exact PDF features in 0.13 (PDF/A substandards, embedding) are not recorded here.
- pypdf and pikepdf: no source on structure-tree helpers; both give raw object access, which is not confirmed here.

## Key question 5: limits of the PDF-side approach

### Takeaway
Producers, vendors and converters agree in writing that paragraph flow, list nesting, table cells without rulings, code-versus-prose and caption attachment are not in a PDF and have to be inferred; typeset output makes the inference harder, not easier, because justified columns, shaded panels and tables all look like aligned rectangles. The measured gap here (a 120-page report converting raw to 238 Word pages, fixed to 120 only by reading typst's own tags) is the argument for taking structure from the source or compiler rather than guessing it from glyph boxes.

### Cited Findings
- LibreOffice developers: "Most text flow and paragraph structure is not described in the PDF and can not magically be recreated when the PDF is read for import." [LibreOffice bug 105274](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=105274)
- Aspose: conversion from a fixed-page structure to a flow model "does not guarantee 100% fidelity". [Aspose forum](https://forum.aspose.com/t/lost-of-fidelity-when-converting-pdf-to-docx/268995)
- A developer asking about PDF-to-DOCX in Rust notes PDFs "don't store structured content like DOCX", so reconstructing everything is "quite challenging". [Rust users forum](https://users.rust-lang.org/t/pdf-to-docx-conversion-in-rust-high-accuracy/139517)
- Vendors expose the trade-off as a user choice: flowing text versus page layout (Adobe, Foxit), Flowing/Continuous/Exact (Solid), Textbox/Flow (Aspose), Standard/Frames/Text (Able2Extract). [Adobe](https://www.adobe.com/learn/acrobat/web/convert-pdf-retain-page-layout); [Foxit](https://www.foxit.com/resource-hub/user-guide/foxit-pdf-editor-for-windows/export-pdfs-to-word-powerpoint-rtf-or-plain-text-files); [Solid](https://www.soliddocuments.com/pdf/_conversion_output/259/1); [Aspose](https://reference.aspose.com/pdf/net/aspose.pdf/docsaveoptions.recognitionmode/); [Able2Extract](https://support.investintech.com/hc/en-us/articles/200947447-How-many-different-PDF-to-Word-conversion-options-are-available-using-Able2Extract)
- Headers and footers: pdf2docx's page writer never emits a header or footer, so bands become body text and each page grows until it spills (23 pages to 44; 120 to 238). [Page.py](https://raw.githubusercontent.com/ArtifexSoftware/pdf2docx/master/pdf2docx/page/Page.py); [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 877 to 880); [SCORECARD.md](../../server/typst/pdf-to-docx/corpus/SCORECARD.md)
- Repetition heuristics have a known failure mode: a report whose every page opens with a heading of the same shape has a repeating row in the header zone and "without this rule the heading would be detected as a header and deleted out of the document". [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 901 to 907)
- Table cells without rulings: Camelot's Stream and pdfplumber's "text" strategy infer "imaginary lines" from word-edge alignment; pdf2docx vetoes stream candidates that look like simple text flow and, conversely, admits any shading that intersects a candidate; Aspose needed a separate EnhancedFlow mode to turn borderless tables into tables instead of "text with a picture in the background". [Camelot](https://camelot-py.readthedocs.io/en/latest/user/how-it-works.html); [pdfplumber](https://github.com/jsvine/pdfplumber); [TablesConstructor.py](https://raw.githubusercontent.com/ArtifexSoftware/pdf2docx/master/pdf2docx/table/TablesConstructor.py); [Aspose](https://docs.aspose.com/pdf/net/convert-pdf-to-word/)
- Table false positives on typeset reports: pdf2docx put a contents page in a merged-cell table, and rendered four rounded severity boxes as a single table. [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 977 to 984, 2828 to 2829)
- Lists: pdf2docx on a sparse page "merges the whole list, and the heading above it, into one paragraph", and loses the space after a list marker. [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 1316 to 1321, 1431 to 1432); OmniDocBench defines no list category at all, so even the parsing benchmark does not score list recovery. [OmniDocBench](https://github.com/opendatalab/OmniDocBench)
- Code versus prose: the benchmarks treat code as a visual layout class (`code_txt` in OmniDocBench, CodeSnippet in Unstructured, fenced output from marker's layout model), i.e. something to be classified from appearance; in a tagged typst PDF it is a `Code` structure element with one P per line. [OmniDocBench](https://github.com/opendatalab/OmniDocBench); [Unstructured](https://docs.unstructured.io/open-source/concepts/document-elements); [marker](https://github.com/datalab-to/marker); [resolve/mod.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-pdf/src/tags/resolve/mod.rs)
- Captions: layout parsers carry caption classes (`figure_caption`, `table_caption`, FigureCaption) because attachment to a figure is a layout decision; typst tags Caption inside a Figure wrapper. [OmniDocBench](https://github.com/opendatalab/OmniDocBench); [Unstructured](https://docs.unstructured.io/open-source/concepts/document-elements); [tree/mod.rs](https://raw.githubusercontent.com/typst/typst/main/crates/typst-pdf/src/tags/tree/mod.rs)
- Layout classification is ambiguous even for humans: DocLayNet double-annotated a subset to measure agreement and models trail it by about 10%. [arXiv 2206.01062](https://arxiv.org/abs/2206.01062)
- Reading order from geometry fails on layouts where a box intersects every candidate cut. [arXiv 2607.01018](https://arxiv.org/pdf/2607.01018)
- Text layer traps: a PDF printed by Chrome/Skia marks spaces with ActualText U+200B and pdf2docx glues the words (#379); MuPDF replaces visible text with ActualText by design. [pdf2docx issue search](https://github.com/ArtifexSoftware/pdf2docx/issues?q=is%3Aissue+spacing+OR+overflow+OR+blank+OR+shading+OR+background); [Ghostscript bug 708005](https://bugs.ghostscript.com/show_bug.cgi?id=708005)
- Right-to-left text: pdf2docx drops spaces between RTL words and cuts a Hebrew line into fragments interleaved with the heading, leaving "no whole line left to repair". [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 2812 to 2821)
- Even the compiler side has a limit the PDF cannot reveal: typst "never splits a figure", so a 50-row figure overprints rows 27 to 50 at the foot of a page "with no warning", and every converter rung loses the same three lines. [SCORECARD.md](../../server/typst/pdf-to-docx/corpus/SCORECARD.md)
- Source-side routes tried here: pandoc from Typst source gave 15 pages with "no cover, headings numbered '0', no colour, no tables fills, no header"; `typst --features html` then pandoc gave 23 pages with "every word present, every piece of styling gone"; typst 0.15's HTML export now supports equations via MathML. [docs/typst-tab-2026-09.md](../../docs/typst-tab-2026-09.md) (lines 866 to 870); [Typst 0.15 blog](https://typst.app/blog/2026/typst-0.15)
- Tag-driven repairs still delete content on a wrong guess: lifting a running band or rebuilding a contents page "deletes part of the document", so the local converter verifies that every PDF text line survives and climbs down to plainer output rather than lose one. [CLAUDE.md](../../CLAUDE.md)

### Inferences
- The recoverable set from a PDF alone is: glyph positions, fonts, rulings, fills, images, and (if tagged) the structure tree. Everything a Word document needs beyond that (paragraph boundaries, leading, list nesting, which rectangles are cells, which panels are code, what a caption belongs to, what is a running band) is inferred, and each inference has a documented failure on typeset reports.
- For typst 0.14+ output the tag tree closes most of the gap for structure (bands, lists, code, tables, captions, TOC) but not for metrics: leading, paragraph spacing, column widths and dot-leader pitch still have to be measured from glyphs, which is where pdf2docx drifts. That is the case for a compiler-side exporter (typst's own HTML export plus a DOCX writer, or a typst-to-DOCX backend) that can emit both the structure and the exact dimensions.
- A hybrid remains the practical ceiling today: compile once, convert the PDF for appearance, and read the tags for structure, with a text-retention check so a wrong guess costs fidelity rather than content.

### Gaps
- No vendor or paper quantifies how often each inference (list nesting, borderless cells, caption attachment) fails; the only numbers found are this repository's scorecard and the Markdown-level benchmarks.
- Whether typst's tag tree can carry enough geometry (it does not record leading or paragraph spacing) was not researched beyond the exporter source; the Code and L tags carry no metrics by design.
