# Word's page and line layout model, and the OOXML controls that pin content to a position

Scope: how Microsoft Word (Windows, Mac, web) turns WordprocessingML into pages and lines, which `w:` constructs decide where content lands, what cannot be controlled, and where LibreOffice Writer and Google Docs diverge. Written for an engineer generating `.docx` that must match a PDF page for page and line for line while staying editable. Date of research: 2026-10-10. Items marked "community observation" are not documented by Microsoft or the standard; items marked "spec" are the ISO/IEC 29500 (ECMA-376) text as reproduced on Microsoft Learn's Open XML SDK pages; items marked "[MS-OI29500]" are Microsoft's own published notes on where Word deviates from the standard.

Citation convention in this file: each bullet ends with "Source:" and a link, because the usual dash separator is not allowed in these notes.

## Key question 1: Pagination (page breaks, widow/orphan, keep rules, table rows, section breaks, and the body area given header and footer)

### Takeaway
Word paginates on the fly from installed font and printer metrics, so page breaks are a derived result, not stored data; the only hard guarantees come from paragraph-level flags (`widowControl`, `keepNext`, `keepLines`, `pageBreakBefore`), row-level flags (`cantSplit`, `tblHeader`) and section breaks. The body area is per section: its top edge is the larger of the top margin and (header distance plus the laid-out height of the header's in-flow content), with no extra gap added; this is documented by Microsoft moderators and Word MVPs rather than by the standard, which only defines the margin and header distances.

### Cited Findings

Pagination is dynamic, not stored
- A long-running word-processing support forum explains that Word builds pages when it displays or prints, from the installed fonts and printer driver, so "it is almost impossible to get two machines so exactly similar that a document will paginate with exactly the same page breaks on each." Source: [Atlantis forum, Pagination differences between Windows 7 and Windows 8](https://www.atlantiswordprocessor.com/en/forum/viewtopic.php?p=8706)
- Word MVP site: "Any difference in font or printer driver from one machine to another has the potential to affect spacing, breaks, widows & orphans, paragraphs, etc." and the advice is to avoid hard page breaks and use paragraph properties (keep-with-next, page-break-before) for pagination. Source: [wordmvp.com, Differences Between Win & Mac Word](https://wordmvp.com/Mac/Differences.html)
- One of the compatibility options Word exposes is "Use printer metrics to lay out document" (`wdUsePrinterMetrics`, value 26), which means layout can depend on the printer driver when it is on. Source: [WdCompatibility enum, Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)

Widow and orphan control
- Spec text for `widowControl`: "This element specifies whether a consumer shall prevent a single line of this paragraph from being displayed on a separate page from the remaining content at display time by moving the line onto the following page." Both the first-line-alone-at-bottom and last-line-alone-at-top cases are moved. "If this setting is never specified in the style hierarchy, then this paragraph shall prevent a single line from being shown on a separate page whenever it would normally occur." Turning it off is `<w:widowControl w:val="off"/>`. Source: [WidowControl class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.widowcontrol?view=openxml-3.0.1)
- Word's Normal style ships with widow/orphan control enabled, visible in Paragraph > Line and Page Breaks. Source: [Susan Daffron, Making Text Stay Together](https://www.susandaffron.com/?p=2478)
- LibreOffice has an open request to enable widow/orphan control by default in all paragraph styles, which implies its default differs from Word's. Source: [LibreOffice bug 89714](https://bugs.libreoffice.org/show_bug.cgi?id=89714)
- The two-line minimum is the smallest meaningful setting: a LibreOffice answer explains it cannot go below 2 "because you need at least 2 lines to decide whether to split or not the paragraph across a page break." Source: [Ask LibreOffice, Widow and Orphan control is locked](https://ask.libreoffice.org/t/widow-and-orphan-control-is-locked/37843)

Keep-with-next, keep-lines-together, page-break-before
- `keepNext` "tells the renderer to keep the paragraph's contents on the same page as the following paragraph whenever possible" (spec wording as mirrored by docx4java). Source: [docx4java ECMA-376 mirror, keepNext](https://webapp.docx4java.org/OnlineDemo/ecma376/WordML/keepNext.html)
- Microsoft's Word 2003 XML reference describes keepNext as "Prevents a page break between this paragraph and the next" and keepLines as preventing a page break within the paragraph. Source: [pPr element, Word 2003 XML Reference](https://learn.microsoft.com/en-us/previous-versions/office/developer/office-2003/ee364434(v=office.11))
- The object model property `Paragraph.KeepWithNext` is "True if the specified paragraph remains on the same page as the paragraph that follows it when Microsoft Word repaginates the document." Source: [Paragraph.KeepWithNext, Microsoft Learn](https://learn.microsoft.com/en-us/previous-versions/office/developer/office-2007/bb255931(v=office.12))

Table rows across pages
- Spec text for `cantSplit`: "If this property is set, then all contents of a table row shall be rendered on the same page by moving the start of the current row to the start of a new page if necessary. If the contents of this table row cannot fit on a single page, then this row shall start on a new page and flow onto multiple pages as necessary." Default when unspecified anywhere: the row may split. Source: [CantSplit class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.cantsplit?view=openxml-3.0.1)
- Observed Word behaviour contradicts the spec for the oversize case: a UniOffice guide says a row taller than a page "has nowhere to move to" and both Word and its own renderer truncate it; an Aspose thread states "truncating a row, while contents are greater than a page size and AllowBreakAcrossPages property set to false, is expected behavior of MS Word." Community observation, two independent vendors. Sources: [UniOffice, Keeping a row together](https://docs.unidoc.io/unioffice/guides/document/tables/keeping-a-row-together/); [Aspose forum](https://forum.aspose.com/t/setallowbreakacrosspages-false-truncates-row-content/53212)
- Microsoft's own description of the `doNotBreakConstrainedForcedTable` compat element mentions rows taller than a page being kept whole "even if that means that part of the table row is clipped by the edge of the page." Source: [DoNotBreakConstrainedForcedTable class, Microsoft Learn](https://msdn2.microsoft.com/en-us/library/cc820823(v=office.14))
- An AskWoody thread notes Word treats a row as unsplittable if any cell in it is prevented from breaking (community observation). Source: [AskWoody, Disabling "Allow row to break across pages"](https://askwoody.com/forums/topic/disabling-allow-row-to-break-across-pages)
- Header rows: `tblHeader` repeats the row "at the top of each new page on which part of this table is displayed"; it "can be applied to any number of rows at the top of the table structure"; and "if this row is not contiguously connected with the first row of the table ... then this property shall be ignored." Source: [TableHeader class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.tableheader?view=openxml-3.0.1)

Section breaks
- Spec text for `w:type` in `sectPr`: next page (the default when `type` is omitted) "begin[s] the new section on the following page"; odd page and even page begin on the next odd-numbered or even-numbered page; continuous breaks "begin the new section on the following paragraph. This means that continuous section breaks might not specify certain page-level section properties, since they shall be inherited from the following section"; column breaks begin in the next column. Source: [SectionType class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.sectiontype?view=openxml-3.0.1)
- A continuous break that changes orientation does not stay on the same page in Word: "the whole content following the continuous section break is displayed on a new page" (observation recorded in an OpenOffice bug about matching Word). Source: [Apache OpenOffice issue 68514](https://bz.apache.org/ooo/show_bug.cgi?id=68514)
- `pgMar` "specifies the page margins for all pages in this section", so header distance, footer distance and margins are per section. Source: [PageMargin class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.pagemargin?view=openxml-3.0.1)

Body area given `pgMar` top/bottom/header/footer and header content height
- The schema attributes are `top` (Top Margin Spacing), `bottom`, `left`, `right`, `header` (Spacing to Top of Header), `footer` (Spacing to Bottom of Footer) and `gutter`, all in twentieths of a point; the example writes `w:header="720" w:top="1440"`. Source: [PageMargin class, Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.pagemargin?view=openxml-3.0.1)
- The standard allows a negative margin: "A negative value indicates that the contents of the main document shall be measured from the bottom of the page extent regardless of the footer for that document, and therefore shall overlap the footer text" (bottom margin wording; the mirror shows the same pattern for top). Source: [docx4java ECMA-376 mirror, pgMar](https://webapp.docx4java.org/OnlineDemo/ecma376/WordML/pgMar.html)
- Microsoft moderator (Hung-Chun Yu), quoting an earlier Microsoft Answers post: "When a header exceeds the space between header margin and top margin (that is, the distance between 0.5" and 1" in a normal Blank Document), it will push the document text down, but there will be no space between the header and document unless you build some in." The accepted answer in the same thread, citing the developer team, adds that a shape set to "In Front of Text" does not push the body; "If you set it to a different wrapping, like 'Square', then the shapes push the text below them." Source: [Microsoft Q&A, Why is an inline textbox in the header not pushing down the header margin?](https://learn.microsoft.com/en-us/answers/questions/216612/why-is-an-inline-textbox-in-the-header-not-pushing)
- Word MVP HansV: if the header takes a lot of vertical space "the body text will be pushed down as far as needed to display the header"; treat the Top margin "as the minimum distance between the top of the page to the top of the body text." Source: [Microsoft Q&A answer by HansV](https://learn.microsoft.com/en-us/answers/a/9819208)
- Word MVP Doug Robbins: if the header's content plus its distance from the page edge exceeds the margin, "the margins will be increased to accommodate the content of the header\footer." Source: [Microsoft Q&A answer by Doug Robbins](https://learn.microsoft.com/en-us/answers/a/11115723)
- Aspose documents the same relationship for its Word-compatible engine: to add distance between header and body you "either decrease HeaderDistance or increase TopMargin." Source: [Aspose forum, Words Header margins](https://forum.aspose.com/t/words-header-margins/119003)
- Conflicting evidence on negative margins in Word: a LibreOffice bug reporter who attached a DOCX with top and bottom margins of -2" and -1.5" wrote "As far as I can see Word treats this as the non-negative value", while an older OpenOffice issue says a Word document with a negative top margin "results in an overlapping of the page header with the page body." Sources: [LibreOffice bug 119952](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=119952); [Apache OpenOffice issue 48832](https://bz.apache.org/ooo/show_bug.cgi?id=48832)
- A MathWorks note (third party) states that for Word documents "the top margin and header expand to prevent overlapping of the header and the body text." Source: [MathWorks Answers, report margin](https://ch.mathworks.com/matlabcentral/answers/627068-how-to-set-up-report-margin-correctly)

Page break character and the paragraph mark
- Spec text for `splitPgBreakAndParaMark`: normally a `w:br w:type="page"` "is treated as run-level content, which means that although it delimits the end of the page, if there is no content after it within the current paragraph, that the paragraph shall also end on that page." With the compat element on, the break "shall always immediately end the current page, moving the paragraph mark ... to a new line on the next page." Source: [SplitPageBreakAndParagraphMark class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.splitpagebreakandparagraphmark?view=openxml-3.0.1)

### Inferences
- Body-area formula that is consistent with every source above (the standard does not state it; the MVP and moderator descriptions do): body_top = max(pgMar.top, pgMar.header + H_header) and body_bottom = page_height minus max(pgMar.bottom, pgMar.footer + H_footer), where H_header and H_footer are the laid-out heights of each story's in-flow content (inline content plus floating objects whose wrapping is anything other than "in front of text" or "behind text"). No gap is inserted between header and body when the header wins, so an exact header height must include its own space-after.
- Because `pgMar` is a section property, a section with a taller header, or a different header distance, changes the body area only for that section's pages; a generator that needs a constant body box across sections should give every section the same `top`, `header` and header content height, or make `top` larger than any header could grow.
- For page-for-page fidelity, pagination must be forced rather than hoped for: a `pageBreakBefore` or `w:br w:type="page"` at each PDF page boundary, with `widowControl` off and `keepNext`/`keepLines` cleared on the content, so Word's own pagination heuristics cannot move a line onto another page. Even then line count per page is only reproduced if the line heights are also pinned (see question 2).
- `cantSplit` on a row taller than the body area is dangerous in Word (clipping, not flow), despite the spec's wording. Tables that straddle pages should either be split into rows that each fit, or left splittable with `tblHeader` on the heading rows.
- Negative margins are not a reliable way to pin the body box: the standard defines them, Word's handling is reported both ways, and LibreOffice did not render the header/footer at all in the reported case.

### Gaps
- I found no Microsoft document that states the body-top rule as a formula; the max() form above is reconstructed from the moderator and MVP descriptions and from Aspose's equivalent behaviour.
- I could not retrieve the [MS-OI29500] implementer notes for `keepNext`, `keepLines`, `pageBreakBefore`, `widowControl` or `sectPr/type`; only the `trHeight` and `ST_DocGrid` notes were reachable in this session.
- Whether current Word (365, 2026 builds) honours a negative `pgMar` top value as "fixed body position" or clamps it to positive remains unresolved; the two bug-tracker reports disagree and I found no Microsoft statement.
- No source was found for how Word handles a `keepNext` chain longer than one page beyond the spec's "whenever possible" wording.

## Key question 2: Line layout (lineRule exact/atLeast/auto, baseline placement in an exact line, raised/lowered text, space before/after, contextual spacing, suppression at top of page, compatibility settings and modes, document grid)

### Takeaway
`w:spacing w:line` is in 240ths of a line for `auto` and in twentieths of a point for `atLeast` and `exact`; in an `exact` line that is too small the standard says text sits at the bottom and is clipped from the top, and when too large it is centred (Word's "Don't center 'exact line height' lines" option turns that off). Inter-paragraph space is the maximum of after and before, not the sum, `contextualSpacing` subtracts it between same-style paragraphs, and Word drops space-before at the top of a page except on pages that start a section (an MVP statement, with a compat option extending the suppression to hard breaks). The widely quoted "baseline at 0.8 of the exact line height" has no documented source that I could find.

### Cited Findings

lineRule and units
- `ST_LineSpacingRule` has three values: `auto` (line height determined by content, value in 240ths of a line), `atLeast` (minimum height, may grow) and `exact` (fixed height, oversize content clipped); for `atLeast` and `exact` the `line` value is in twentieths of a point, for `auto` in 240ths of a line, so `line="240" lineRule="auto"` is single spacing. Source: [docx4java ECMA-376 mirror, ST_LineSpacingRule](https://webapp.docx4java.org/OnlineDemo/ecma376/WordML/ST_LineSpacingRule.html)
- Spec example on the `spacing` element: `w:after="200" w:line="276" w:lineRule="auto"` means 200 twentieths of a point after the paragraph and line spacing of 1.15 times single (276 divided by 240). "If this setting is never specified in the style hierarchy, then the paragraph shall have no spacing applied to its lines, or above and below its contents." Source: [SpacingBetweenLines class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.spacingbetweenlines?view=openxml-3.0.1)

Where text sits inside an exact or at-least line
- ISO SC34 WG4 defect report DR 12-0007 (John Haug, December 2012) quotes and corrects the spec text for the `line` attribute: when lineRule is atLeast or exact, "When the line height is too small, the text shall be positioned at the bottom of the line (i.e. clipped from the top down)" and "When the line height is too large, the text shall be centered in the available space." The DR only fixes "exactly" to "exact" and a missing phrase. Source: [SC34 WG4 mailing list, DR 12-0007](https://mailman.vse.cz/pipermail/sc34wg4/2012-December/002783.html)
- Word has a compatibility option whose dialog label is "Don't center 'exact line height' lines" (`wdExactOnTop`, value 28), which implies the default is to centre text in an exact line that is taller than the text. Source: [WdCompatibility enum, Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)
- Microsoft support: "When you set the line spacing to Exactly and select a measurement that is equal to or less than the height of the font, underscore characters may not be displayed and characters that have an ascender, descender, or an umlaut may be cut off." The remedy offered is a larger "At" value or "At least". Source: [Microsoft support KB 291353](https://support.microsoft.com/kb/291353)
- A separate Microsoft support article attributes some on-screen clipping to zoom level rather than layout: adjusting zoom "from 75 percent to 100 percent in most cases" corrects it visually. Source: [Microsoft support, Some characters missing or cut off when displayed on screen in Word](https://support.microsoft.com/en-gb/topic/some-characters-missing-or-cut-off-when-displayed-on-screen-in-word-f25ed208-3a5e-85a2-88e7-2c33470350f1)
- A font vendor's explanation of the clipping: "Microsoft's products, like Word and Publisher, are real sticklers for obeying those lines. If that's where the font designer said the top and bottom boundaries are ... It will only show you what's between those boundary lines, and ignore anything outside of them." (community observation, font-maker blog). Source: [FontBundles, Let's talk about cut-off text in Microsoft products](https://fontbundles.net/blog/ask-a-font-creator-lets-talk-about-cut-off-text-in-microsoft-products)
- MathType support notice: if a paragraph's line spacing is "Exactly" a value too small for an equation, "this causes Word to place the equation behind lines of text, thus obscuring parts of the equation." Source: [Wiris MathType TN151](https://docs.wiris.com/ca/mathtype/office_tools/support_notices/tn151)

Raised and lowered text (`w:position`)
- Spec: `w:position` raises (positive) or lowers (negative) the run by the given number of half-points relative to the surrounding baseline "without altering the font size of the contents." Source: [Position class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.position?view=openxml-3.0.1)
- By default the line grows to fit raised or lowered text; the compat element `noSpaceRaiseLower` ("Do Not Increase Line Height for Raised/Lowered Text") makes "the height of the line ... determined solely by the spacing settings on the parent paragraph", so raised text that exceeds the line is clipped. Source: [docx4java ECMA-376 mirror, noSpaceRaiseLower](https://webapp.docx4java.org/OnlineDemo/ecma376/WordML/noSpaceRaiseLower.html); the matching Word option is "Don't add extra space for raised/lowered characters" (`wdNoSpaceRaiseLower`, value 2) in the [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)

Space before and after, and contextual spacing
- Spec: "When determining the spacing between any two paragraphs, a consumer shall use the maximum of the inter-line spacing in each paragraph, the spacing after the first paragraph and the spacing before the second paragraph to determine the net spacing between the paragraphs." Example: after=240 and before=80 gives 12 points, not 16. Source: [SpacingBetweenLines class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.spacingbetweenlines?view=openxml-3.0.1)
- `contextualSpacing` ("Ignore Spacing Above and Below When Using Identical Styles"): the paragraph's before or after "should not be applied when the preceding and following paragraphs are of the same paragraph style"; the value "is subtracted from the spacing which would have been present if contextual spacing was off, never going below zero." In the spec example 10 pt after with contextual spacing and 12 pt before on the next same-style paragraph nets 2 pt. Source: [ContextualSpacing class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.contextualspacing?view=openxml-3.0.1)
- `beforeAutospacing` / `afterAutospacing` ask the consumer to mimic HTML's default `p` spacing; the compat element `doNotUseHTMLParagraphAutoSpacing` fixes them to "beforeAutospacing = 5 points of spacing before" and "afterAutospacing = 10 points of spacing after." Source: [DoNotUseHTMLParagraphAutoSpacing class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.donotusehtmlparagraphautospacing?view=openxml-3.0.1)
- LibreOffice developers note the HTML-matching rule is loosely defined and that browsers use roughly one line of text, not the HTML 4.01 default. Source: [LibreOffice bug 53551](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=53551)

Space before at the top of a page
- Word MVP Stefan Blom (2021): "Spacing Before will be suppressed at the top of a page, unless that page also starts a new section." Source: [Microsoft Tech Community, Novel formatting chapters in Word](https://techcommunity.microsoft.com/discussions/word/novel-formatting-chapters-in-word/2031190)
- The compatibility option "Suppress Space Before after a hard page or column break" (`wdSuppressSpBfAfterPgBrk`, value 7) extends suppression to pages that begin with a hard page or column break; Word 2003 XML spelled it `suppressSpBfAfterPgBrk`. Sources: [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia); [compat element, Word 2003 XML Reference](https://learn.microsoft.com/en-us/previous-versions/office/developer/office-2003/aa196182(v=office.11)); SoftArtisans describes the same setting as controlling whether Word "suppresses paragraph space before and space after options after a page break" ([SoftArtisans wiki](https://wiki.softartisans.com/display/WW12/CompatibilitySettings.SuppressSpaceAfterPageBreak))
- Related labelled options in the same enum: "Suppress extra line spacing at top of page" (`wdSuppressTopSpacing`, 8), "Suppress extra line spacing at bottom of page" (`wdSuppressBottomSpacing`, 29), "Suppress extra line spacing like WordPerfect 5.x" (`wdNoExtraLineSpacing`, 23), "Don't add leading (extra space) between rows of text" (`wdNoLeading`, 20), and "Add space for underline" (`wdNoSpaceForUL`, 21). Source: [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)
- Conflicting community claims about `pageBreakBefore`: an AskWoody reply says space before "is automatically suppressed" when a paragraph starts a page via PageBreakBefore, while a third-party DOCX-to-PDF converter's docs say such a paragraph "retains its 24pt offset." Sources: [AskWoody, Top-of-page space before paragraphs](https://askwoody.com/forums/topic/top-of-page-space-before-paragraphs); [dxpdf paragraph-spacing notes](https://docs.rs/crate/dxpdf/0.4.0/source/docs/paragraph-spacing.md)

Compatibility modes 11/12/14/15
- Microsoft's VBA reference lists `wdWord2013` (15) as the default, "all Word 2013 features enabled", and `wdWord2010` (14) as matching Word 2010 with features new in 2013 turned off; 12 is Word 2007 and 11 is Word 2003. Source: [WdCompatibilityMode enum, Microsoft Learn](https://learn.microsoft.com/en-ca/office/vba/api/word.wdcompatibilitymode)
- LibreOffice's tracking bug for Word 2013 compatibility notes that some Word 2013 compatibility changes "have no official documentation" and must be inferred, and lists: a "smart justify" that can shrink as well as expand spaces; negative vertical positions of floating images handled differently in mode 15 (images that overlapped the margin in older modes are pulled back); table text wrapping around floating shapes; and a changed treatment of how a shape affects a column's virtual left edge ("in CompatibilityMode15, ... the size of the image does not shift the columns virtual left edge, only the page edge counts"). Sources: [LibreOffice bug 131304 (meta)](https://bugs.documentfoundation.org/show_bug.cgi?id=131304); [LibreOffice bug 143899](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=143899); [LibreOffice bug 148578](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=148578)
- Table edge placement differs by mode: Word 2013 files "place the table border by offsetting it by the cell margin, so the text lines up with the page margin"; "For MSO the table begins at page borders, not where the table content begins." A Microsoft community answer confirms "by default, Word adjusts for cell margins when placing the table borders/edges." Sources: [LibreOffice bug 106742](https://bugs.libreoffice.org/show_bug.cgi?id=106742); [Microsoft Q&A answer](https://learn.microsoft.com/en-us/answers/a/9799792)

Document grid
- Spec: `docGrid` "specifies the settings for the document grid, which enables precise layout of full-width East Asian language characters within a document by specifying the desired number of characters per line and lines per page"; Latin text is "placed across the number of grid units needed to fit the content." Source: [DocGrid class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.docgrid?view=openxml-3.0.1)
- `linePitch` is in twentieths of a point (a 20-line grid on Letter is `w:linePitch="684"`, 34.2 pt); the pitch is not applied inside table cells unless the `adjustLineHeightInTable` compat setting is present; a paragraph opts out with exact line spacing or with `snapToGrid` off; `type` values are `default` (no grid), `lines`, `linesAndChars` and `snapToChars`. Source: [docx4java ECMA-376 mirror, docGrid](https://webapp.docx4java.org/OnlineDemo/ecma376/WordML/docGrid.html) and [ST_DocGrid](https://webapp.docx4java.org/OnlineDemo/ecma376/WordML/ST_DocGrid.html)
- [MS-OI29500] on `ST_DocGrid`: with `snapToChars` each line is divided into units of the character pitch; East Asian characters get one unit each, centred; ascii/hAnsi runs are "centered in as many grid units as are necessary"; cs runs are left-aligned in their units; and "The additional line pitch on the docGrid element is also added in order to maintain a specific number of lines per page." Source: [MS-OI29500 2.1.534 ST_DocGrid](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/ad4d9201-2051-4b7d-8f9c-ba019f0ae7a6)
- Word option "Adjust line height to grid height in the table" is `wdDontAdjustLineHeightInTable` (36) and "Don't snap text to grid inside table with inline objects" is `wdDontSnapTextToGridInTableWithObjects` (44). Source: [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)
- LibreOffice has a Word-compatibility option "Use Word-compatible font metrics for text grid and Asian text", described as applying "Word's extra line-height multiplier to CJK fonts" that report certain code pages, and "Make whitespace character height not affect line height", which is "On by default for Word document formats." Source: [LibreOffice help, Compatibility options](https://help.libreoffice.org/latest/en-US/text/shared/optionen/01041000.html)

### Inferences
- For line-for-line fidelity the only line height Word will not recompute from font metrics is `lineRule="exact"`. Set it per paragraph to the PDF's baseline-to-baseline distance (twentieths of a point) and expect two consequences: ascenders or accents taller than the box are clipped from the top, and raised text no longer grows the line only if `noSpaceRaiseLower` is on.
- Baseline placement inside an exact line is not a fixed 0.8 ratio in any document I found. The standard's rule is: text block bottom-aligned (clipped at the top) when the box is smaller than the font's natural height, centred when larger. The font's natural height here is what Word derives from the font (question 4), so the baseline offset within an exact line depends on the font's ascent/descent split, which is why reports differ per font. A generator that wants the baseline at a known offset should make the exact height equal to the font's natural line height (then neither clipping nor centring moves anything), and carry the PDF's extra leading as paragraph space instead.
- Inter-paragraph spacing collapses (maximum, not sum) and is further reduced by `contextualSpacing`; a generator should emit either space-after only or space-before only, never both, and avoid `contextualSpacing` unless the PDF's spacing was itself style-dependent.
- Space-before is dropped at the top of every automatically paginated page and (with the compat option) after hard breaks; a layout that depends on top-of-page offsets should express them as section top margins or as an exact-height empty paragraph with zero before/after, not as space-before.
- A `docGrid` of type `lines` snaps every non-exact paragraph to the pitch, which is a way to force a constant baseline rhythm, but paragraphs with exact spacing ignore it and table cells ignore it unless the compat flag is set; it is of limited use for reproducing a PDF whose leading varies.

### Gaps
- No Microsoft or standards document states a "0.8" (or any) fixed ratio for baseline position inside an exact line; the value circulating in community posts is unsourced and I could not confirm or refute it.
- I could not reach [MS-OI29500] notes for `spacing` (17.3.1.33) to learn Word's deviations for `line`, `lineRule`, or autospacing.
- The LibreOffice 24.2 release notes page was blocked by bot protection; the Word 2013 "shrink up to 20 percent" figure is taken from secondary coverage and bug entries (question 6).
- No primary source was found for the exact top-of-page behaviour of `pageBreakBefore` versus `w:br type=page` in current Word; community sources conflict.

## Key question 3: Fixed positioning (frames, text boxes, anchored drawings) and the trade-offs

### Takeaway
Three constructs can place a block at an absolute position while the rest of the document flows: `w:framePr` (a paragraph-level frame in the document layer, anchored to the next non-frame paragraph), a DrawingML text box (`wps:txbx` inside `wp:anchor`, drawing layer) and any anchored drawing with `wp:positionV relativeFrom="page"`. Frames keep text in the main story (fields, footnotes, TOC and Navigation Pane all work) but cannot link or rotate; text boxes can link and float above or below text but are placeholders in Word for the web and are re-mapped by LibreOffice; all three depend on an anchor paragraph that determines the page.

### Cited Findings

Frames (`w:framePr`)
- Spec: text frames "are paragraphs of text in a document which are positioned in a separate region or frame in the document, and can be positioned with a specific size and position relative to non-frame paragraphs"; presence of `framePr` makes the paragraph part of a frame; adjacent paragraphs with identical attribute sets are "part of the same text frame"; a differing `h` (810 vs 811) splits them; and "The positioning of the frame ... shall be calculated relative to the next paragraphs in the document which is itself not part of a text frame." Attributes include `w`, `h`, `hRule`, `x`, `y`, `xAlign`, `yAlign`, `hAnchor`, `vAnchor`, `wrap`, `hSpace`, `vSpace`, `anchorLock`, `dropCap`, `lines`. The spec example uses `w:vAnchor="text" w:hAnchor="page" w:x="1921"`. Source: [FrameProperties class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.frameproperties?view=openxml-3.0.1)
- Word deviates from the standard's default for `hAnchor`: "the standard's default for hAnchor is page, but Word uses a default value of text" (LibreOffice developer report). Source: [LibreOffice bug 154129](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=154129)
- Word MVP Charles Kenyon's comparison (page updated January 2025): frames are "in the document level - text must wrap around a Frame", text boxes are drawing-layer objects that "can float in front of text (occluding it) or behind text as well as have text wrap around it"; "Frames cannot break across pages" and "Textboxes cannot break across pages (but can be linked)"; text boxes "can be linked, with text flowing from one to the next", frames "cannot be linked"; a frame "can be a part of a Paragraph Style definition", a text box cannot; frames can hold TOC, XE and STYLEREF fields, start footnotes, and their headings appear in the Navigation Pane and tables of contents, text-box headings do not; frames "cannot be rotated because they are not shapes"; text box printing is governed by "Print drawing objects", frames are not; frames are not easy to create in ribbon versions but work in native 2007 to 2019 format. Source: [Charles Kenyon, Frames and Textboxes in Microsoft Word](https://addbalance.com/word/frames_textboxes.htm)
- The compat option "Show hard page or column breaks in frames" (`wdShowBreaksInFrames`, 11) exists, which confirms breaks inside frames are otherwise not honoured as breaks. Source: [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)

Anchored drawings and text boxes
- Spec for `wp:positionV`: "This element specifies the vertical positioning of a floating DrawingML object"; `relativeFrom` names the base, and the child `align` or `posOffset` gives the position; the example centres a picture on the page with `relativeFrom="margin"` and `<wp:align>center</wp:align>`. Source: [VerticalPosition class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.wordprocessing.verticalposition?view=openxml-3.0.1)
- Word for the web: shapes, charts, text boxes, SmartArt and WordArt "may appear as placeholders and cannot be edited, moved, or resized"; page margins and orientation are "preserved but can't be edited"; headers and footers are preserved but not editable; line spacing "can't be adjusted". Source: [Microsoft support, Differences between using a document in the browser and in Word](https://support.microsoft.com/en-us/word/differences-between-using-a-document-in-the-browser-and-in-word)
- LibreOffice imports Word text boxes as Writer frames ("which is good because styles are preserved"); grouped text boxes become LibreOffice text boxes "with no style preservation"; a dedicated meta bug tracks DOCX text-box problems. Source: [LibreOffice bug 103494 (meta)](https://www.libreoffice.org/bugzilla/showdependencytree.cgi?id=103494)
- Positioning of anchored objects is fragile on the LibreOffice side: a meta bug collects DOCX anchor and wrap problems including "Image moves to different page after DOCX/DOC export" and layouts that differ between DOCX and ODT even with docx-compatible anchoring; another report says a text box nested in a frame is inserted by Word as separate objects and "the text box isn't adjusted with the anchor getting moved." Sources: [LibreOffice bug 120466 (meta)](https://www.libreoffice.org/bugzilla/showdependencytree.cgi?id=120466); [LibreOffice bug 126669](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=126669)
- Compat options affecting shapes and text boxes: "Lay out autoshapes like Word 97" (`wdShapeLayoutLikeWW8`, 33), "Don't break wrapped tables across pages" (`wdDontBreakWrappedTables`, 43), "Use Word 2003 indent rules for text next to wrapped objects" (`wdWW11IndentRules`, 55), "Do not autofit tables next to wrapped objects" (`wdDontAutofitConstrainedTables`, 56). Source: [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)

Acrobat's two export modes
- Adobe: "Retain Flowing Text" "prioritizes the ability for text to wrap and flow seamlessly throughout the exported document"; "Retain Page Layout" keeps "the same layout as your PDF" and "may split the text into different text box groups to retain the original design." Source: [Adobe, Export PDFs to common file types and retain layout](https://www.adobe.com/learn/acrobat/web/convert-pdf-retain-page-layout)
- A third-party guide describes the layout mode as producing "individual text boxes" and advises checking the result in Word and correcting flaws. Source: [Chron, How to Convert a PDF to Word Using Acrobat Pro](https://smallbusiness.chron.com/convert-pdf-word-using-acrobat-pro-54097.html)

### Inferences
- To place one block at an exact y on a known page while the body flows: a `framePr` paragraph with `vAnchor="page"` (and `hAnchor="page"`), `y`/`x` in twentieths of a point, `hRule="exact"` with `h` and `w`, `anchorLock` on, placed as the first paragraphs of that page's content so the "next non-frame paragraph" that anchors it is on the right page. The equivalent with a drawing is `wp:anchor` with `positionV relativeFrom="page"` and `posOffset` in EMU, `behindDoc`/`wrapNone` or square wrap as needed, in a run of a paragraph on that page. Either way the page is determined by the anchor paragraph, so if Word's own pagination moves that paragraph, the block moves with it.
- Frames are the better fit for an editable report: their text stays in the main story (searchable, TOC and fields work, no drawing-layer stacking), they can be styled, and Word for the web does not reduce them to placeholders the way it does text boxes (not verified; see gaps). Text boxes are the better fit when the content must sit above or below other content or must link across boxes.
- Acrobat's "Retain Page Layout" is the industry reference for the brute-force approach: every text group becomes a positioned text box. The result reproduces the page but is poor to edit (text split across boxes, no flow), which is the trade-off the question asks about.
- Nothing in these constructs changes how Word breaks lines inside the block; a frame of exact width will re-wrap its text with Word's metrics and justification (question 6).

### Gaps
- I found no Microsoft page listing how Word for the web treats `framePr` frames specifically; the differences page names text boxes and shapes but not frames.
- No Google documentation found on how Docs imports `framePr`, text boxes or `wp:anchor` positions (see question 7).
- The [MS-OI29500] notes for `framePr` (Word's deviations beyond the `hAnchor` default) were not retrievable.

## Key question 4: Fonts and metrics (how Word measures line height, why it differs from a PDF typesetter, embedding, PostScript outlines, missing fonts)

### Takeaway
Windows GDI historically derived line height from the OS/2 `usWinAscent`/`usWinDescent` values plus external leading computed from `hhea`, and used the win values as a clipping rectangle; the OpenType spec recommends `sTypo*` metrics and the `USE_TYPO_METRICS` flag, but warns that applications differ, which is why Word's "single" spacing does not equal a typesetter's ascent plus descent plus lineGap. Word embeds only TrueType-outline fonts (obfuscated `.odttf`), skipping CFF/PostScript-outline OpenType; a missing font is substituted on Windows and may simply not display on the Mac.

### Cited Findings

Which metrics set line height
- OpenType spec, Baseline to Baseline Distances: early implementations used different fields, "Macintosh: the ascender, descender and lineGap values in the 'hhea' table" and "Windows GDI: the usWinAscent and usWinDescent values in the OS/2 table." GDI TEXTMETRIC values for TrueType: tmHeight from usWinAscent and usWinDescent, tmAscent = usWinAscent, tmDescent = usWinDescent, tmInternalLeading = usWinAscent + usWinDescent - unitsPerEm, tmExternalLeading = MAX(0, (hhea.ascender - hhea.descender + hhea.lineGap) - (usWinAscent + usWinDescent)). "In addition, the usWinAscent and usWinDescent values were used to set a clip rectangle: in on-screen display, any portions of glyphs extending beyond these limits could be clipped." Source: [OpenType spec, Recommendations (Baseline to Baseline Distances)](https://learn.microsoft.com/en-us/typography/opentype/spec/recom)
- Same page: "different applications and text-layout engines (including newer Windows and Macintosh platforms) can use different logic to determine a default baseline-to-baseline distance ... This has made it challenging for font developers to create fonts with predictable behavior." Recommended: sTypoAscender minus sTypoDescender = unitsPerEm; set USE_TYPO_METRICS (fsSelection bit 7); set hhea equal to the typo values; set usWinAscent + usWinDescent equal to the typo line height. And: "if the font requires applications to use a larger clipping rectangle, then usWinAscent and usWinDescent values can be set to larger values, though different behavior will be seen in applications that set line spacing using sTypo* values (as recommended) versus applications that set line spacing using the usWin* values." Source: [OpenType spec, Recommendations](https://learn.microsoft.com/en-us/typography/opentype/spec/recom)
- The sTypo values define recommended single spacing as sTypoAscender - sTypoDescender + sTypoLineGap, often about 120 percent of the em (Minion Pro: 1000 upm, lineGap 200). Source: [OpenType spec, Recommendations (OS/2 table)](https://learn.microsoft.com/en-us/typography/opentype/spec/recom)
- OS/2 table spec: in variable fonts "default line metrics should always be set using the sTypoAscender, sTypoDescender and sTypoLineGap values, and the USE_TYPO_METRICS flag in the fsSelection field should be set ... The usWinAscent and usWinDescent fields should be used to specify a recommended clipping rectangle." Source: [OpenType spec, OS/2 table](https://learn.microsoft.com/en-us/typography/opentype/spec/os2)
- Glyphs tutorial (font-maker documentation): hhea values set default line spacing on Mac and iOS; Microsoft intended Typo for line spacing and Win "to define a vertical distance beyond which glyphs might get clipped"; some Windows software used Win metrics for spacing and could not switch "without breaking existing documents"; the USE_TYPO_METRICS flag exists so Typo values are used. Source: [Glyphs, Vertical metrics](https://glyphsapp.com/learn/vertical-metrics/)
- Browser behaviour for comparison: Chrome and Firefox on Windows pick Typo or Win values based on the flag (author notes the survey was not exhaustive). Source: [W3C css-archive, text-layout glyph-bounding-box thread](https://lists.w3.org/Archives/Public/public-css-archive/2020May/0547.html)
- Community test of Word (font forum): a user generated DOCX files with lines of 1000 "a" and 1000 "y" across every installed font, three spacings and several sizes, and found leading "varies greatly by font" and that Word's spacing changes between "a" lines and "y" lines by up to about 30 percent for some fonts; the "1.25 times (winAscent + winDescent)" formula offered by another poster did not match. LibreOffice showed no a/y difference. Community observation, unresolved. Source: [High-Logic forum, Docx: Matching Line Spacing of Word](https://forum.high-logic.com/t/docx-matching-line-spacing-of-word/5230)
- LibreOffice's compat option "Make whitespace character height not affect line height" is "On by default for Word document formats", and a separate option applies "Word's extra line-height multiplier to CJK fonts." Source: [LibreOffice help, Compatibility options](https://help.libreoffice.org/latest/en-US/text/shared/optionen/01041000.html)
- Word compat options that change metric handling: "Use printer metrics to lay out document" (26), "Truncate font height" (24), "Substitute fonts based on font size" (25), "Don't add leading (extra space) between rows of text" (20). Source: [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)

Embedding
- Microsoft support: Word for Microsoft 365 for Mac can embed fonts; "Use OpenType (.OTF) or TrueType (.TTF), if possible"; avoid PostScript fonts (.PFB, .PFM); "Not all TrueType fonts can be embedded"; embedding levels are Non-embeddable, Preview/Print, Editable, Installable; "Embed only the characters used" "reduces the file size but limits editing of the file using the same font"; if embedding is turned off "a different font is substituted for the font that had been embedded previously." Source: [Microsoft support, Benefits of embedding custom fonts](https://support.microsoft.com/en-us/office/benefits-of-embedding-custom-fonts-cb3982aa-ea76-4323-b008-86670f222dbc)
- Microsoft 2015 blog: "All TrueType and OpenType fonts have 'embedding permissions' encoded within them"; Print and preview embedding leaves the document "locked and cannot be edited" and "Most third-party fonts have this setting"; Installable fonts are treated like Editable by most applications; at that date embedding "is not supported on the Mac OS, iOS, Android or web versions of Word or PowerPoint." Source: [Microsoft 365 blog, Document font embedding demystified](https://www.microsoft.com/en-us/microsoft-365/blog/2015/07/06/document-font-embedding-demystified/)
- Word embeds only TrueType-outline fonts: "The 'Kind' must be 'TrueType', not 'OpenType PostScript'. Unfortunately the most common format for Mac OS fonts is OpenType PostScript, so these can't be embedded." Source: [Practical Typography, How to embed fonts in a Word document](https://practicaltypography.com/how-to-embed-fonts-in-a-word-document.html)
- Former Adobe principal scientist (Dov Isaacs) on Adobe's forum: "Microsoft only allows embedding of TrueType fonts and OpenType TrueType-flavored fonts to be embedded in their Office documents. There is nothing in OpenType CFF fonts ... from being embedded in Office documents other than a business decision by Microsoft." He also reports that Word's native Save as PDF rasterised text in CFF fonts at the time, a known bug. Sources: [Adobe community, Adobe OpenType fonts with TrueType outlines for Microsoft Office](https://community.adobe.com/t5/type-typography-discussions/adobe-opentype-fonts-with-truetype-outlines-for-microsoft-office/m-p/6108234); [Adobe community, Save as PDF does not embed fonts](https://community.adobe.com/t5/acrobat-discussions/save-as-pdf-does-not-embed-fonts/m-p/8955118)
- Obfuscation format: embedded fonts are stored as `.odttf`; the spec's algorithm takes the GUID in `fontKey`, reverses its byte order and XORs the first 32 bytes of the font with it (bytes 0 to 15 and again 16 to 31); "Embedded fonts are obfuscated to prevent them from being used outside of the document." The font parts are referenced from `word/fontTable.xml` via `w:embedRegular r:id` and `w:fontKey`. Sources: [docx4java ECMA-376 mirror, Font Embedding](https://webapp.docx4java.org/OnlineDemo/ecma376/WordML/Font%20Embedding.html); [Wikipedia, ODTTF](https://en.wikipedia.org/wiki/ODTTF); [goehte, Convert-Word-EmbeddedFont](https://github.com/goehte/Convert-Word-EmbeddedFont)
- Mac Word (per the MVP page, written in the Word 2011 era): "Mac Word can use ONLY TrueType fonts and OpenType fonts with TrueType outlines"; "Fonts embedded by Windows Word are ignored"; on Windows "Word substitutes the closest font when one is missing", on the Mac each character must exist in an installed font or it may not display; Microsoft's same-named fonts are hinted per platform and "The differences are tiny, but they account for the differences in the way the Mac places pixels on the screen." Source: [wordmvp.com, Differences Between Win & Mac Word](https://wordmvp.com/Mac/Differences.html)

Missing fonts
- Microsoft support (above): without the font, Word substitutes; with embedding, "special characters won't turn into meaningless rectangles." Source: [Microsoft support, Benefits of embedding custom fonts](https://support.microsoft.com/en-us/office/benefits-of-embedding-custom-fonts-cb3982aa-ea76-4323-b008-86670f222dbc)
- A third-party article (unverified) says Word checks the `Windows NT\CurrentVersion\Fonts` registry key rather than the Fonts folder, looks first for a font with the same PANOSE classification, and exposes a Font Substitution dialog under File > Options > Advanced. Source: [wisechecker.com, Fix Word font substitution](https://wisechecker.com/?p=24617)

### Inferences
- The reason Word's line height differs from a PDF typesetter's for the same font: typesetters (and Typst) use ascender + descender + lineGap from `hhea` or the `sTypo*` set, while Word's "single" is derived from the Windows metrics (usWinAscent + usWinDescent, with external leading from hhea when larger) and may also react to the glyphs present on the line (the a/y test). Fonts whose usWin values are larger than their typo values (common, because usWin is a clipping box) therefore look looser in Word. A generator cannot change this without exact line spacing, and exact line spacing clips anything taller than the box.
- Because usWin metrics are also Word's clipping box, an exact line height smaller than usWinAscent + usWinDescent at the font size will clip the top of tall glyphs (question 2); this matches the Microsoft support article and the font-maker's description.
- For the DOCX produced from a Typst PDF: embed the fonts (TrueType outlines only; CFF faces must be converted or substituted), name runs by the family name Word matches on, and keep the font's usWin and typo metrics consistent (or supply a font whose metrics you control) so Word's natural line height equals the PDF's leading; then `exact` spacing equal to that leading neither clips nor centres.
- "Preview/Print" embedding makes the whole document read-only; only Editable or Installable fonts keep the document editable, which matters for the "stay editable" requirement.

### Gaps
- No Microsoft document describes Word's single-spacing formula; the GDI mapping above is the only primary text, and the community test suggests additional, undocumented behaviour (content-dependent leading in some fonts).
- Whether current Word for Mac (2024 to 2026) still ignores Windows-embedded fonts is unclear: the MVP page is from the Word 2011 era, while Microsoft now lists Mac Word among apps that can embed fonts.
- No current Microsoft statement on CFF embedding was found; the exclusion is documented only by third parties and by a 2010 to 2014 Adobe forum.

## Key question 5: Tables (fixed vs autofit, exact row height, cell margins, why the rendered width differs from the column sum, borders and shading)

### Takeaway
Every width in a WordprocessingML table is a preference: `tblW`, `tblGrid/gridCol` and `tcW` can disagree and Word recomputes the grid, reducing columns proportionally when cells exceed the table width and growing for unbreakable content. `tblLayout fixed` stops content-driven resizing; `trHeight hRule="exact"` is honoured but Word adds the largest bottom cell padding (an [MS-OI29500] note). Default cell margins are 0.08 inch left and right, and Word 2013-mode places the table edge outside the margin by that amount so cell text aligns with body text.

### Cited Findings
- `tblLayout`: "it can either be displayed using a fixed width or autofit layout algorithm"; "If this element is omitted, then the value of this element shall be assumed to be auto." Source: [TableLayout class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.tablelayout?view=openxml-3.0.1)
- Fixed-layout algorithm (ST_TblLayoutType): the `tblGrid` defines the initial column widths, `tblW` the total; "if the preferred width requested for the cells exceeds the preferred width of the table, each grid column is proportionally reduced in size to fit the table width"; fixed layout "does not change that size based on cell contents." Source: [docx4java ECMA-376 mirror, ST_TblLayoutType](https://webapp.docx4java.org/OnlineDemo/ecma376/WordML/ST_TblLayoutType.html)
- "All widths in a table are considered preferred", two or more widths "may have conflicting values for the width of the same grid column", and in the `tblW` example a long non-breaking string in a cell "caused the table to be expanded, overriding the preferred width on the table"; `tcW` of type `pct` is relative to the overall table width. Source: [docx4java ECMA-376 mirror, tblW](https://webapp.docx4java.org/OnlineDemo/ecma376/WordML/tblW_2.html) and [tcW](https://webapp.docx4java.org/OnlineDemo/ecma376/WordML/tcW.html)
- `gridCol w` "does not solely determine the actual width of the resulting grid column"; when omitted "the last saved width of the grid column is assumed to be zero." Source: [GridColumn class, Microsoft Learn](https://technet.microsoft.com/en-au/library/cc865136(v=office.14))
- A vendor bug report notes "MS Word may ignore the widths specified in the tblGrid and compute new ones." Source: [Telerik feedback 1383590](https://feedback.telerik.com/wpf/1383590-richtextbox-layout-of-table-imported-from-docx-containing-tblgrid-element-with-incorrect-column-widths-is-unexpected)
- [MS-OI29500] on `trHeight`: (a) "In Word, if the hRule attribute is omitted, then its value is assumed to be atLeast" (the standard says auto); (b) `val` is unsignedInt with maximum 31680; (c) "Word requires that if the hRule attribute is set to exact, then the val attribute must not be 0"; (d) "In Word, if the hRule attribute is exact, Word sets the row height to the exact height plus the largest bottom cell padding of any cell in the row." Source: [MS-OI29500 2.1.180 trHeight](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/5919e0bd-e6ce-477e-8d66-0e5282f5c506)
- Default cell margins: "by default, Top and Bottom are set to 0", and "Left and Right are set to 0.08"" (SoftArtisans reference for its Word-compatible writer); a Telerik report states "the default left and right margins for a table in MS Word are 0.08"." Sources: [SoftArtisans wiki, table cell margins](https://wiki.softartisans.com/x/0IUy); [Telerik feedback 1546601](https://feedback.telerik.com/document-processing/1546601-wordsprocessing-docxformatprovider-table-default-cell-left-and-right-margin-values-are-changed-when-not-specified-in-the-document)
- `tblCellMar` is "a set of cell margins for all cells in the parent table row" and can be overridden per cell by `tcMar`. Source: [TableCellMarginDefault class, Microsoft Learn](https://learn.microsoft.com/ko-kr/previous-versions/office/developer/office-2010/cc818528(v=office.14))
- Table edge offset: "by default, Word adjusts for cell margins when placing the table borders/edges" (community answer), and LibreOffice's analysis of Word 2013 files found the border offset by the cell margin so text aligns with the page margin ("For MSO the table begins at page borders, not where the table content begins"); a rounding of a 0.19 cm padding to 0.20 cm changed a header from four lines to five. Sources: [Microsoft Q&A answer](https://learn.microsoft.com/en-us/answers/a/9799792); [LibreOffice bug 106742](https://bugs.libreoffice.org/show_bug.cgi?id=106742)
- Related compat options: "Lay out tables with raw width" (`wdLayoutRawTableWidth`, 40), "Allow table rows to lay out apart" (41), "Allow tables to extend into margins" (`wdGrowAutofit`, 50), "Use Word 2002 table style rules" (49), "Use Microsoft Office Word 2003 table autofit rules" (57), "Use Word 2010 table style rules" (69), "Align table rows independently" (39), "Allow space between paragraphs of the same style in a table" (54). Source: [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)
- Row-level `cantSplit` and `tblHeader` behaviour: see question 1.

### Inferences
- A rendered table is wider or narrower than the column sum for four separable reasons: the cell margins are inside the cells but the table edge is offset outward by the left cell margin in Word 2013 mode; `tblW` and the `gridCol` sum disagree and Word rebalances; autofit grows columns for unbreakable content; and `tblInd` (not covered above) shifts the left edge. For a PDF match: `tblLayout fixed`, explicit `tblW` in `dxa` equal to the `gridCol` sum, `tcW` on every cell equal to its `gridCol`, explicit `tblCellMar` (zero if the PDF's cell padding is drawn separately), and no content that cannot break.
- Exact row heights must be set to the PDF row height minus the largest bottom cell padding, since Word adds that padding back; with top and bottom cell margins at zero (the default) the correction is zero.
- Borders and shading are specified per table (`w:tblBorders` inside `tblPr`), per cell (`w:tcBorders`) and per paragraph, with fill via `w:shd` (`w:val`, `w:color`, `w:fill`); I did not fetch those spec pages in this session, so the details are not cited here (see gaps).

### Gaps
- Spec text for `tblBorders`, `tcBorders`, `shd`, `tblInd` and `tblpPr` (floating tables) was not fetched; the Open XML SDK pages exist under the same learn.microsoft.com naming pattern as those cited above.
- The [MS-OI29500] note for `tblLayout` and `tblGrid` was not found by search.
- The exact twips value Word writes for 0.08 inch (115) is arithmetic, not a cited figure.

## Key question 6: Justification and hyphenation (Word versus a typesetter, hyphenation settings, soft hyphens, character spacing and kerning)

### Takeaway
Word breaks lines greedily, one line at a time, and (since Word 2013 in compatibility mode 15) justifies by shrinking as well as expanding inter-word space, by up to roughly 20 percent according to LibreOffice's reimplementation; a Knuth-Plass typesetter optimises the whole paragraph and uses its own hyphenation, so a line that fit in the PDF can wrap differently in Word even with identical fonts. Automatic hyphenation is off unless `autoHyphenation` is set, the default zone is 0.25 inch, and `w:spacing` (twentieths of a point) plus `w:kern` (half-point threshold) are the per-run levers for matching a typeset line's width.

### Cited Findings
- Greedy versus optimal: a Microsoft-filed patent describes that "most word processing applications begin by formatting the first line from the first character of a paragraph and finding the best line break for the line", then each subsequent line the same way, while Knuth's method "considers all possible ways to break a paragraph into lines" with a penalty function and dynamic programming. Source: [US patent 7770111, Method and computer readable medium for optimized paragraph layout](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/7770111); the European counterpart [EP1672521](https://data.epo.org/publication-server/rest/v1.2/patents/EP1672521NWA2/document.html)
- A 2024 paper on score-based line breaking states the line-by-line approach "is the default algorithm for all current browsers" and that paragraph-level breaking (CSS `text-wrap: pretty`) gives better typography at a performance cost. Source: [Ishii 2024, score-based line breaking](https://Www.Gwern.net/doc/cs/css/2024-ishii.pdf)
- Word 2013 justification: LibreOffice's meta bug records "MS 2013 introduced a new 'smart justify' that can shrink as well as expand", and LibreOffice 24.2 added "justification by shrinking" for DOCX interoperability (tdf#119908, tdf#130088); secondary coverage of the 24.2 release says Writer now uses "the same line breaking algorithm that Word introduced as default in Word 2013 and later, which reduces spaces within justified lines by up to 20%." Sources: [LibreOffice bug 131304 (meta)](https://bugs.documentfoundation.org/show_bug.cgi?id=131304); [LibreOffice bug 119908](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=119908); [LibreOffice bug 130088](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=130088); [Ubuntu Handbook, LibreOffice 24.2.0 released](https://ubuntuhandbook.org/index.php/2024/02/libreoffice-24-2-0-released)
- A LibreOffice test note shows the dependence on mode: a test file "exported with compatibilityMode 12 instead of 15" could not exercise the shrinking fix. Source: [LibreOffice bug 159923](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=159923)
- Older Word justification only expands: "WordPerfect compresses the spaces between words while Word expands them. This often results in different line breaks and leads to different page breaks." The option "Do full justification like WordPerfect 6.x for Windows" (`wdWPJustification`, 31) is under File > Options > Advanced > Layout Options. Sources: [Microsoft Q&A answer](https://learn.microsoft.com/en-us/answers/a/9648719); [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)
- Soft returns in justified text: Word "will grossly expand short lines that end early using the Shift+Enter soft return character" unless the option "Don't expand character spaces on the line ending Shift+Return" (`wdExpandShiftReturn`, 14) is set; "Wrap trailing spaces to next line" (`wdWrapTrailSpaces`, 4) also affects breaks. Sources: [Microsoft Q&A, Full justification makes spaces uneven](https://learn.microsoft.com/en-us/answers/questions/4925643/full-justification-makes-spaces-between-words-unev?page=0); [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)
- Non-breaking spaces are treated inconsistently as fixed-width in justified text by popular word processors (Unicode list discussion). Source: [Unicode mailing list, U+00A0 as fixed-width](https://corp.unicode.org/pipermail/unicode/2018-January/005899.html)
- Hyphenation: `autoHyphenation` "specifies whether the content ... should automatically be hyphenated by the hosting application before it is displayed, if the application supports this functionality. If this element is omitted, then hyphenation shall not automatically be performed." Source: [AutoHyphenation class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.autohyphenation?view=openxml-3.0.1)
- `hyphenationZone` "is the amount of whitespace which can be left at the end of a line (or added to justified lines) before hyphenation should be attempted on the next word"; "If this element is omitted, then a default hyphenation zone of 360 twentieths of a point (0.25") shall be applied." Source: [HyphenationZone class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.hyphenationzone?view=openxml-3.0.1)
- `consecutiveHyphenLimit` "specifies the maximum number of consecutive lines of text that can end with a hyphen"; omitted or 0 means no limit. Source: [docx4java ECMA-376 mirror, consecutiveHyphenLimit](https://webapp.docx4java.org/OnlineDemo/ecma376/WordML/consecutiveHyphenLimit.html)
- Vendor defaults that mirror Word's: auto-hyphenation off, zone 360 twips, HyphenateCaps true. Source: [Aspose.Words HyphenationOptions](https://reference2.aspose.com/words/net/aspose.words.settings/hyphenationoptions)
- Character spacing: run-level `w:spacing` "specifies the amount of character pitch which shall be added or removed after each character in this run", in twentieths of a point, positive or negative (`val="200"` is 10 points added). Source: [Spacing class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.spacing?view=openxml-3.0.1)
- Kerning: `w:kern` turns on font kerning and "The val attribute specifies the smallest font size which shall have its kerning automatically adjusted" in half-points; never specified means no kerning. Source: [Kern class (spec text), Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.wordprocessing.kern?view=openxml-3.0.1)

### Inferences
- Why a PDF-justified line can run past the margin or wrap differently in Word: the typesetter chose the break with knowledge of the whole paragraph, its own hyphenation dictionary and its own advance widths (including kerning and possibly optical features Word does not apply); Word re-breaks greedily with its metrics and, in mode 15, with up to about 20 percent space compression, so the same words may fit one line in Word that took two in the PDF or vice versa. If the generator instead forces the PDF's breaks with explicit line breaks (`w:br`) in a justified paragraph, Word expands the short line unless `wdExpandShiftReturn` ("Don't expand character spaces on the line ending Shift+Return") is set in `w:compat`; a left-aligned paragraph avoids that but loses justification.
- A practical way to pin both breaks and widths: one paragraph per PDF line (left-aligned, exact line height, zero spacing), with per-run `w:spacing` adjustments carrying the typesetter's justification as condensed or expanded tracking; this keeps the text editable but turns re-flow into a per-line edit. Kerning should be switched on with a low `w:kern` threshold if the PDF was kerned, or left off if the PDF's advances were unkerned, because it changes line width.
- Soft hyphens inserted where the PDF hyphenated give Word the same break opportunity, but Word will only use them if its own line is too long at that point; they are not a command to break there.

### Gaps
- No Microsoft text documents the Word 2013 justification algorithm or its compression limit; "up to 20 percent" comes from LibreOffice's reverse-engineering as reported by secondary sources, and the 24.2 release-notes page itself was blocked during this session.
- The `w:softHyphen` and `w:suppressAutoHyphens` spec pages were not fetched; only their existence is known.
- No source was found describing Word for the web's hyphenation support.

## Key question 7: Differences between Word for Windows, Word for Mac, Word for the web, LibreOffice Writer and Google Docs

### Takeaway
Even two Windows machines can paginate the same file differently (fonts, printer driver, patch level); Mac Word reflows by "about half a per cent" per an MVP estimate and historically ignored embedded fonts; Word for the web preserves but cannot edit page layout and turns text boxes and shapes into placeholders; LibreOffice re-implements Word behaviours behind compatibility flags (several on by default for `.docx`) and has long bug lists for text boxes, anchors and compatibilityMode 15; Google Docs documents only that macros, embedded charts/videos and SmartArt are converted, and is silent on text boxes and frames.

### Cited Findings
- Windows versus Windows: pagination depends on installed fonts and printer driver (Atlantis forum, above); "Use printer metrics to lay out document" is an explicit compat switch. Sources: [Atlantis forum](https://www.atlantiswordprocessor.com/en/forum/viewtopic.php?p=8706); [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)
- Mac: "Assume that a Mac will reflow text by about half a per cent"; "The same physical printer will often produce different results from the same document" depending on whether the driver runs on Mac or PC; identical output requires the same Office-supplied fonts and versions on both machines and a printer driver that behaves identically; Word "is basically Word for Windows re-compiled to run on the Mac"; "Every patch Tuesday, something changes"; Advanced Typography settings made on the Mac display on Windows but Windows has no interface for them. Source: [wordmvp.com, Differences Between Win & Mac Word](https://wordmvp.com/Mac/Differences.html)
- Mac font handling (same source): only TrueType-outline fonts usable, Windows-embedded fonts ignored, no substitution of missing glyphs the way Windows does. Source: [wordmvp.com](https://wordmvp.com/Mac/Differences.html); contrast with the current support page listing Word for Microsoft 365 for Mac as able to embed fonts: [Microsoft support](https://support.microsoft.com/en-us/office/benefits-of-embedding-custom-fonts-cb3982aa-ea76-4323-b008-86670f222dbc)
- Word for the web: Outline, Draft, Web Layout and Full Screen Reading views are missing; rulers and gridlines not shown; Editing view hides margins, page breaks, cover pages, headers and footers; "Page layout is preserved but can't be edited"; headers and footers preserved, not editable; page breaks not indicated in Editing view; table styles, cell size and sort order "preserved in the document, but cannot be configured"; shapes, charts, text boxes, SmartArt, WordArt "may appear as placeholders and cannot be edited, moved, or resized"; fields and content controls are placeholders; footnotes, endnotes, TOC and index are placeholders; "Line spacing can't be adjusted"; styles cannot be created or modified; printing goes through a PDF reader and margin settings need the desktop app. Source: [Microsoft support, Differences between using a document in the browser and in Word](https://support.microsoft.com/en-us/word/differences-between-using-a-document-in-the-browser-and-in-word)
- A third-party (unverified) claim says the web version substitutes fonts that are not cloud-available and simplifies anchoring. Source: [ContractSafe, Why documents look different](https://www.contractsafe.com/support/why-documents-look-different)
- LibreOffice compat flags and their `.docx` defaults: "Add paragraph and table spacing at top of first page and page breaks" (spaces added automatically for Word imports); "Add paragraph and table spacing at bottom of table cells" (on for Word imports); "Use OpenOffice.org 1.1 line spacing" off (recent Word documents use the new method); "Use OpenOffice.org 1.1 text wrapping around objects" off, matching Word's no-wrap in header/footer/footnotes; "Word-compatible trailing blanks" on for .doc/.docx/.rtf; "Make whitespace character height not affect line height" on for Word formats; "Do not mirror drawing objects anchored in RTL paragraphs" intended for DOCX; "Render endnotes inline at end of document" as Word does; "Underline Word-compatible trailing blanks" matching Word's option, which Word has off by default; "Adjust spaces to half the width of ideographic spaces" enabled automatically for DOCX with the balance option. Source: [LibreOffice help, Compatibility options](https://help.libreoffice.org/latest/en-US/text/shared/optionen/01041000.html)
- LibreOffice gaps on DOCX: fixed 20 pt line height in a DOCX had no visible effect in 7.2.2.1 (report); borders follow character top/bottom rather than spacing in LibreOffice while "Apparently Word does things the other way"; text boxes imported as frames with style preservation but grouped ones lose styles; images moving to other pages on export; compatibilityMode 15 behaviours tracked as a meta bug. Sources: [LibreOffice bug 144865](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=144865); [LibreOffice bug 137111](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=137111); [LibreOffice bug 103494 (meta)](https://www.libreoffice.org/bugzilla/showdependencytree.cgi?id=103494); [LibreOffice bug 120466 (meta)](https://www.libreoffice.org/bugzilla/showdependencytree.cgi?id=120466); [LibreOffice bug 131304 (meta)](https://bugs.documentfoundation.org/show_bug.cgi?id=131304)
- LibreOffice follows the standard rather than Word where they differ, e.g. the `framePr hAnchor` default (page in the standard, text in Word), and the `trHeight` default (auto in the standard, atLeast in Word) is the kind of divergence [MS-OI29500] records. Sources: [LibreOffice bug 154129](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=154129); [MS-OI29500 trHeight](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/5919e0bd-e6ce-477e-8d66-0e5282f5c506)
- Google Docs, official: when working with Office files, "Macros" are not supported, "Embedded charts and videos in Word and PowerPoint files will be converted to images", "SmartArt images will be converted to Google Drawings", password-protected files open in a viewer only; the Drive page adds that some features are kept in the file and viewable in Word but not editable in Docs, others "may be lost or changed when you edit", with a notification shown, and that Apps Script, add-ons, Translate document and version-copy are unavailable in Office format. Sources: [Google Docs Help, Work with Office files](https://support.google.com/docs/answer/6055139?hl=en); [Google Drive Help, Work with Office files using Office editing](https://support.google.com/drive/answer/9276408)
- Google Docs, third party: a WPS guide says Docs "may not handle text boxes or embedded Office objects perfectly" and suggests removing text boxes before upload; a school IT note reports a missing text box became visible after File > Convert to Google Doc (unverified anecdotes). Sources: [WPS blog](https://www.wps.com/blog/how-to-convert-a-word-document-to-a-google-doc/); [Haverford SD support note](https://haverfordsd.freshservice.com/support/solutions/articles/11000082137-text-block-doesn-t-appear-on-word-document-assignment)

### Inferences
- Of the controls in questions 1 to 6, the ones Word for the web preserves without editing (page layout, headers, footers, text boxes as placeholders) are safe for viewing; nothing about its layout engine is documented, so page count parity in the browser cannot be assumed.
- LibreOffice is the most predictable non-Microsoft consumer because its deviations are enumerated as flags and bugs; a generator targeting both should avoid frames nested in text boxes, avoid relying on negative positions, write `hRule` and `hAnchor` explicitly rather than relying on defaults, and write `compatibilityMode` 15 explicitly so LibreOffice selects the Word 2013 justification.
- Google Docs should be treated as text-only fidelity: nothing official promises positioned objects, exact line heights or page-level geometry survive.

### Gaps
- No Google documentation on `framePr`, text boxes, anchored drawings, exact line spacing or page size handling was found.
- No Microsoft statement on which layout engine Word for the web uses or how it paginates.
- The claim that Mac Word reflows by half a percent is an MVP's rule of thumb from the Word 2011 era, not a measurement.

## Key question 8: Microsoft guidance and known writeups on fixed-layout or pixel-perfect DOCX, and how PDF-to-Word converters do it

### Takeaway
Microsoft publishes no "fixed layout DOCX" guidance; the closest things are the compatibility option table (what Word can be told not to recompute) and the MVP advice to avoid hard breaks because pagination is machine-dependent. The reference implementations of layout-preserving conversion are Acrobat's "Retain Page Layout" (positioned text box groups) and, on the open side, LibreOffice's DOCX compatibility work; python-docx and docx4j expose the same OOXML primitives (framePr, anchors, exact spacing) but do not add layout logic of their own.

### Cited Findings
- Adobe's documented modes: flowing text versus page layout with text split "into different text box groups." Source: [Adobe, Export PDFs to common file types and retain layout](https://www.adobe.com/learn/acrobat/web/convert-pdf-retain-page-layout)
- PDF-to-Word conversions commonly carry over fixed line spacing, which then clips or crowds in Word (the same mechanism as the MathType notice). Source: [ComPDF, Convert PDF to Word spacing problem](https://compdf.com/blog/convert-pdf-to-word-spacing-problem); [Wiris MathType TN151](https://docs.wiris.com/ca/mathtype/office_tools/support_notices/tn151)
- Microsoft's compatibility option table is the complete list of layout rules Word can be told to apply differently per document; the dialog labels are the enum descriptions. Source: [WdCompatibility enum](https://learn.microsoft.com/en-us/dotnet/api/microsoft.office.interop.word.wdcompatibility?view=word-pia)
- MVP guidance against relying on pagination: avoid hard page breaks, minimise section breaks, use paragraph properties for pagination, avoid floating text boxes and spacing tricks. Source: [wordmvp.com, Differences Between Win & Mac Word](https://wordmvp.com/Mac/Differences.html)
- LibreOffice's stated approach for Word layout parity is per-feature emulation behind document-scoped compatibility flags, some of which "apply only to the current document and must be set separately for each document." Source: [LibreOffice help, Compatibility options](https://help.libreoffice.org/latest/en-US/text/shared/optionen/01041000.html)

### Inferences
- There are two coherent strategies and the sources support both: (1) the Acrobat way, every text group an absolutely positioned frame or text box, which reproduces the page but degrades editing; (2) the flowing way, one paragraph per PDF line (or per paragraph with explicit breaks), exact line heights equal to the font's natural height plus leading carried as spacing, forced page breaks, embedded TrueType fonts, `widowControl` and keep rules off, `compat` entries for `splitPgBreakAndParaMark`, `doNotExpandShiftReturn`, `noSpaceRaiseLower` and `suppressSpBfAfterPgBrk` as needed, and tables with fixed layout and explicit widths. Strategy 2 keeps the text in the main story (editable, searchable, accessible) and matches the PDF only as far as Word's own line breaking agrees, which is why per-run `w:spacing` and explicit line breaks are needed to make it line-for-line.
- Frames (`framePr`) are the middle ground Acrobat does not use: positioned like text boxes but living in the document story, styleable, and usable for fields and TOC entries.

### Gaps
- No Microsoft article on "pixel-perfect" or fixed-layout DOCX generation exists in the sources searched; no Eric White, OOXML Hacking or docx4j writeup on the topic surfaced in this session, so those suggested sources remain unchecked.
- How Acrobat decides text-box grouping, and whether it uses frames, exact spacing or per-run spacing, is not documented beyond the two-mode description.
