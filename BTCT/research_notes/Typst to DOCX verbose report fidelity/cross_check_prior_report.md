# Cross-check of the earlier "Typst to DOCX export" report (claim by claim, as of 2026-10-10)

Scope: the report at `reports/Typst to DOCX export.md` and its four notes under `research_notes/Typst to DOCX export/`. The report recommends replacing the downloaded typst CLI with a Rust binary ("btct-typst") on the typst 0.14.2 crates that compiles once, writes the PDF through typst-pdf and walks the in-memory `PagedDocument` to emit a layout description for a DOCX writer. Each claim below carries a verdict (confirmed, partly confirmed with the correction, unconfirmed, or contradicted) and the source used. Source-code claims were checked against shallow clones of typst at the tags `v0.13.1`, `v0.14.2` and `v0.15.1` made on 2026-10-10; line numbers are from those tags, and the GitHub URLs point at the same tags. Where a verdict rests on a local measurement (a build, a download), the command is named so it can be repeated.

Method note on the BTCT pin: `Dockerfile` line 75 reads `ARG TYPST_VERSION=0.14.2` and fetches `typst-x86_64-unknown-linux-musl.tar.xz` with sha256 `a6044cba...996d`; the requirements file pins `pdf2docx==0.5.13`. The export runs `typst compile --root <staging> --ignore-system-fonts --package-path <root>/packages --package-cache-path <root>/packages --font-path <root>/fonts` (`server/typst/export.mjs` lines 175 to 187) and refuses any report that quotes a `@preview/` or `@local/` package spec before compiling (`server/typst/package-spec.mjs`).

## 1. Does typst wrap the header and footer in `ArtifactKind::Header` / `Footer` tags in typst-layout, and since which version?

### Takeaway
Confirmed for 0.14.2 and 0.15.1, contradicted for 0.13.1, with one correction: at 0.14.2 the page background is wrapped as `ArtifactKind::Page`, not `ArtifactKind::Background` as the report states; the `Background` variant only exists from 0.15. The report read `main`, not the pinned tag, and said so; the tag check it asked for comes out in its favour on the header and footer.

### Cited Findings
- v0.14.2 `crates/typst-layout/src/pages/run.rs` lines 207 to 209: `let header = header.clone().map(|h| h.artifact(ArtifactKind::Header)); let footer = footer.clone().map(|f| f.artifact(ArtifactKind::Footer)); let background = background.clone().map(|b| b.artifact(ArtifactKind::Page));` [typst v0.14.2 run.rs](https://github.com/typst/typst/blob/v0.14.2/crates/typst-layout/src/pages/run.rs)
- Same file, lines 169 to 174: when `page.header` or `page.footer` is unset, the automatic page-number marginal (`numbering_marginal`) takes its place via `unwrap_or`, so the bare page number is wrapped as Header or Footer too. [typst v0.14.2 run.rs](https://github.com/typst/typst/blob/v0.14.2/crates/typst-layout/src/pages/run.rs)
- v0.14.2 `ArtifactKind` has exactly four variants: `Header`, `Footer`, `Page`, `Other` (default). `crates/typst-library/src/pdf/accessibility.rs` lines 52 to 64. [typst v0.14.2 accessibility.rs](https://github.com/typst/typst/blob/v0.14.2/crates/typst-library/src/pdf/accessibility.rs)
- v0.15.1 `run.rs` lines 218 to 220 use `ArtifactKind::Header`, `Footer` and `Background`; `ArtifactKind` there has `Header, Footer, Watermark, PageNumber, LineNumber, Redaction, Bates, Page, PaginationOther, Layout, Background, ...`. [typst v0.15.1 run.rs](https://github.com/typst/typst/blob/v0.15.1/crates/typst-layout/src/pages/run.rs); [typst v0.15.1 accessibility.rs](https://github.com/typst/typst/blob/v0.15.1/crates/typst-library/src/pdf/accessibility.rs)
- v0.13.1: `grep -rn ArtifactKind crates/typst-layout/src/` returns nothing; `run.rs` lays out `header`, `footer`, `background` as plain `Option<Frame>` marginals with no artifact wrapping (lines 33 to 35, 213 to 215). [typst v0.13.1 run.rs](https://github.com/typst/typst/blob/v0.13.1/crates/typst-layout/src/pages/run.rs)
- `Content::artifact(kind)` wraps the content in an `ArtifactElem` (`crates/typst-library/src/foundations/content/mod.rs` lines 504 to 507), and `ArtifactElem` is declared `#[elem(Tagged)]` (accessibility.rs line 36), so it produces `Tag::Start`/`Tag::End` items in the laid-out frame. [typst v0.14.2 content/mod.rs](https://github.com/typst/typst/blob/v0.14.2/crates/typst-library/src/foundations/content/mod.rs)
- The 0.14.0 changelog (October 24, 2025) says "Typst PDFs are now tagged by default", "The PdfOptions struct has a new tagged field, which defaults to true", and "Added pdf.artifact function for marking content as not semantically meaningful". [Typst changelog 0.14.0](https://typst.app/docs/changelog/0.14.0/)
- The 0.15.0 changelog's exact wording is "Fixed wrong PDF tagging order for inline content outside of paragraphs" and "Added support for more specific artifact kinds in pdf.artifact; these are now internally used when appropriate". The report's quote "Fixed tagging order for inline content" is a paraphrase. [Typst changelog 0.15.0](https://typst.app/docs/changelog/0.15.0/)

### Inferences
- The header/footer artifact tags the design depends on exist at the version BTCT ships. The 0.15 move changes the enum (a `Page`-to-`Background` rename for the background marginal and seven new variants), so a walker that matches on `ArtifactKind` by name will need an edit at the upgrade the report already plans in stage 5.
- Because the automatic page number is also wrapped as Header or Footer, the "PAGE field inside a marginal" row of the report's mapping table has a concrete anchor at 0.14.2: the walker sees `Tag::Start(ArtifactElem{kind: Footer})` around the realized number. It does not see a `PageNumber` artifact until 0.15, where that variant exists but is not used by `typst-layout` itself (no `ArtifactKind::PageNumber` use in `crates/typst-layout/src` or `crates/typst-library/src` at v0.15.1).

### Gaps
- None for this claim.

## 2. Are `PagedDocument`, `Frame` and `FrameItem` public and usable from a dependent crate, and what changed across 0.13, 0.14 and 0.15?

### Takeaway
Confirmed: all three are public at every tag and reachable through `typst::compile::<PagedDocument>` plus `typst::layout::*`, and the crates are published on crates.io. Partly confirmed on stability: the report calls them internal APIs with no stability promise, which is right, but it understates the churn. Between 0.14.2 and 0.15.1 `PagedDocument` and `Page` moved from `typst-library` to `typst-layout`, `Page` gained a `bleed` field, `typst-pdf`'s `convert` signature changed, krilla went from 0.6.0 to 0.8.2, and the CLI's font feature was renamed. Between 0.13.1 and 0.14.2 `Tag` gained `TagFlags` on both variants.

### Inferences
- A dependent crate can be written today against 0.14.2 exactly as the report describes. The cost the report under-weights is that typst does not list crate API breaks in its changelog, so each upgrade is discovered by compiling: the 0.14.2 to 0.15.1 move alone touched the `PagedDocument` path, the `Page` struct, the `ArtifactKind` enum, the krilla major version and the font feature name.
- The frame and tag surfaces themselves were comparatively calm (2 lines in `tag.rs`, 61 in `frame.rs` across a seven-month release), so a walker's core loop is less exposed than its glue code.

### Gaps
- No upstream statement of an API stability policy for the crates was found in the changelogs or crate READMEs read here; absence of one is the finding.

## 3. Does the frame tree carry enough semantics (table cells, list items, line boundaries, show-rule output)?

### Takeaway
Partly confirmed. Table and grid cells, list items, paragraphs, headings, figures, captions, raw blocks, links, images, `place` and footnotes all produce `Tag::Start`/`Tag::End` pairs at 0.14.2, and typst-pdf's table context resolves rowspan, colspan and header kind from them. Two things the report asserts or assumes are not in the tree: paragraph lines are not delimited (line frames are soft and usually inlined, and per-line tags exist only when line numbering is on), and a cell that breaks across pages puts an empty Start/End pair in its first frame and attributes its content through a logical `FrameParent` instead, so a naive bracket walker would miss that content.

### Cited Findings
- Which elements carry `Locatable` or `Tagged` at v0.14.2 (hence get tags per `typst-realize`): `HeadingElem (Locatable, Tagged)`, `ParElem (Locatable, Tagged)`, `TableElem (Locatable, Tagged)`, `GridElem (Tagged)`, `ListElem/EnumElem/TermsElem (Locatable, Tagged)`, `ListItem/EnumItem/TermItem (Tagged)`, `FigureElem` and `FigureCaption (Locatable, Tagged)`, `RawElem (Locatable, Tagged)`, `RawLine (Tagged)`, `ImageElem (Locatable, Tagged)`, `PlaceElem (Unqueriable, Locatable, Tagged)`, `LinkElem (Locatable)`, `FootnoteElem` and `FootnoteEntry (Locatable, Tagged)`, `OutlineElem` and `OutlineEntry (Locatable, Tagged)`, `EquationElem (Locatable, Tagged)`, `ArtifactElem (Tagged)`, `PdfMarkerTag (Construct, Tagged)`. Not tagged: `TableCell`, `GridCell` (`#[elem(name = "cell", ...)]` only), `TableHeader`, `TextElem`, `RectElem`. [typst v0.14.2 typst-library src](https://github.com/typst/typst/tree/v0.14.2/crates/typst-library/src)
- `typst-realize` v0.14.2 `lib.rs` lines 536 to 542: `TagFlags { introspectable: elem.can::<dyn Locatable>() || elem.label().is_some() || elem.location().is_some(), tagged: elem.can::<dyn Tagged>() }`, and a location is assigned when `flags.any()`; lines 564 to 571 create `Tag::Start(elem.clone(), flags)` and `Tag::End(loc, key, flags)` in `prepare`, which `visit_show_rules` emits around the element's show-rule output (lines 342 to 418). - Newly locatable in 0.14 (the report's claim): at v0.13.1 `ParElem` is `#[elem(scope, title = "Paragraph")]`, `TableElem` is `(scope, Show, LocalName, Figurable)`, `ListElem`/`EnumElem`/`TermsElem` are `(scope, ..., Show)`, `FigureCaption` is `(name = "caption", Synthesize, Show)`, `OutlineEntry` is `(scope, name = "entry", ..., Show)`, `FootnoteEntry` is `(..., Show, ShowSet)`; none carries `Locatable`. At v0.14.2 all of them do. Confirmed. [typst v0.13.1 par.rs](https://github.com/typst/typst/blob/v0.13.1/crates/typst-library/src/model/par.rs)

### Inferences
- The report's sentence "a frame walker therefore gets, without inference, which table cell each glyph and fill rectangle belongs to" holds for cells that fit in one region and needs the `FrameParent` rule for cells that break across pages; typst-pdf implements that rule and the walker must copy it.
- "Because the frame walker knows every line's glyphs, the faithful mode can impose Typst's breaks" is only half true: glyph positions are known, line boundaries are not marked. The walker must reconstruct lines from baseline `y` and `TextItem` runs, or the custom binary must switch on an invisible `par.line` numbering to get `ParLineMarker` tags per line (an untested idea, and those tags are flagged neither introspectable nor tagged, so they are a layout-only hook).
- Hyphenation points and justification stretch are not recorded as such: a hyphen Typst inserted is a glyph in the run like any other, and the inter-word spacing is baked into `x_advance`. A faithful mode that forces breaks must detect the trailing hyphen itself.
- `box`, `block`, `rect`, `stack`, `columns` and `text` produce no tags, so panels built from them appear only as `Shape` and `Text` items; the report's "one-cell shaded table" fallback remains a geometric inference, the same kind of guess it criticises pdf2docx for, just on cleaner input.

### Gaps
- No upstream documentation describes the tag ordering guarantees a walker may rely on; typst-pdf's `tags/` module is the only reference implementation and it changed by 94 and 68 lines in its two main files between 0.14.2 and 0.15.1.
- Whether a show rule that returns `none` for an element, or moves its body into `place`, leaves an empty Start/End pair or none was not traced in `typst-realize`.

## 4. What would a custom typst binary cost (build, size, sandbox, fonts, packages)?

### Takeaway
Measured locally: a release build of `typst-cli` 0.14.2 from source compiles 328 crates in 6 min 19 s on a 24-thread Windows machine, produces a 46.4 MB stripped executable and leaves 1.1 GB of build artifacts; the Linux musl release binary BTCT ships today is 50.9 MB uncompressed (15.9 MB as the tarball). A custom binary is therefore not a new size class for the image, but it moves the build from a pinned download with a sha256 to a Rust toolchain stage in the Dockerfile. The sandbox the report says must be reproduced is small and explicit in the CLI source, and a custom binary can be built without the package-download feature at all, which is stricter than the CLI.

### Cited Findings
- Local build, 2026-10-10: `cargo build --release -p typst-cli` on the v0.14.2 checkout with cargo 1.98.1 / rustc 1.98.1: "Finished `release` profile [optimized] target(s) in 6m 19s", 328 `Compiling` lines, `target/release/typst.exe` 46,394,880 bytes, `target/` 1.1 GB, 24 logical processors. Release profile in the workspace `Cargo.toml` lines 155 to 160: `lto = "thin"`, `codegen-units = 1`, `strip = true` for typst-cli. (Local measurement; repeat with the command above.)
- `Cargo.lock` at v0.14.2 lists 418 package entries. (Local count: `grep -c '^name = ' Cargo.lock`.)
- Release asset `typst-x86_64-unknown-linux-musl.tar.xz` for v0.14.2 is 15,877,252 bytes; the extracted `typst` binary inside it is 50,889,504 bytes (`tar -tvJf`, local download whose sha256 matches the Dockerfile's `a6044cba...996d`). [v0.14.2 release assets](https://api.github.com/repos/typst/typst/releases/tags/v0.14.2)
- `typst-kit` v0.14.2 features: `default = ["fonts", "packages"]`; `packages = ["downloads", "dep:dirs", "dep:flate2", "dep:tar", "dep:fastrand"]`; `downloads = ["dep:env_proxy", "dep:native-tls", "dep:ureq", "dep:openssl"]`; `embed-fonts` adds Libertinus Serif, New Computer Modern, New Computer Modern Math and DejaVu Sans Mono to the binary. [typst v0.14.2 typst-kit Cargo.toml](https://github.com/typst/typst/blob/v0.14.2/crates/typst-kit/Cargo.toml)
- The CLI's `World` (`crates/typst-cli/src/world.rs` v0.14.2): paths resolve against `root` and `id.vpath().resolve(root).ok_or(FileError::AccessDenied)` denies escapes (line 411); a package spec triggers `package_storage.prepare_package(spec, &mut PrintDownload(&spec))` (line 405), which is the network path; fonts come from `Fonts::searcher()` with `include_system_fonts(!ignore_system_fonts)`, `include_embedded_fonts(!ignore_embedded_fonts)` and `search_with(font_paths)` (lines 127 to 131). [typst v0.14.2 world.rs](https://github.com/typst/typst/blob/v0.14.2/crates/typst-cli/src/world.rs)
- BTCT today: `export.mjs` passes `--ignore-system-fonts` but not `--ignore-embedded-fonts`, so the CLI's four embedded families are available to reports; `package-spec.mjs` refuses any source containing a quoted `@preview/` or `@local/` spec because "all were measured to fetch". (Repo files, lines cited in the method note.)
- The CLI only emits tags when exporting the whole document: `compile.rs` v0.14.2 line 141 `let tagged = !args.no_pdf_tags && pages.is_none();`. [typst v0.14.2 compile.rs](https://github.com/typst/typst/blob/v0.14.2/crates/typst-cli/src/compile.rs)

### Inferences
- The report's third risk ("a custom binary must reproduce that sandbox exactly") is tractable: the sandbox is about 15 lines of `world.rs`, and building `typst-kit` with `default-features = false, features = ["fonts", "embed-fonts"]` removes `ureq`, `native-tls` and the package downloader from the binary, so the network path the regex in `package-spec.mjs` guards against cannot exist. That is a stronger property than the CLI gives today and the report does not claim it.
- The image cost is dominated by what is already there (a 50.9 MB binary); the new cost is a Rust build stage of several minutes with about 1 GB of scratch, on every image build unless the binary is prebuilt and pinned by hash the way the CLI is now. On the 1 to 2 GB target box the build must not run there at all.

## 12. Could a tagged PDF plus a better reader deliver most of the same structure without a custom compiler?

### Takeaway
Yes for structure, no for layout internals. BTCT's current `tagged.py` already reads typst's Header and Footer artifacts, but through PyMuPDF, which "cannot say which marked-content block a text span came from", so it strips artifact blocks from the content stream by hand and diffs the text. pdfplumber has exposed `mcid` and `tag` on every char since 0.10.3 (2023-10-26) and `Page.structure_tree` since 0.10.4 (2024-02-10), and pdfium's public API returns marked-content IDs per structure element, so the join the report calls "unproven work" is available off the shelf in two libraries. That route gives headings, table cells with spans, list items, figures, footnotes, TOC and running bands from the tree typst-pdf already writes; it does not give line boundaries (which the frame tree does not give either), resolved `Content` fields such as a figure's numbering pattern, or the page `numbering` template.

### Cited Findings
- BTCT `server/typst/pdf-to-docx/tagged.py` docstring: "Read what typst tagged in its PDF: the Header/Footer artifacts and the structure tree. PyMuPDF cannot say which marked-content block a text span came from, so the running band is found by removing the Header and Footer artifact blocks from each page's content stream and diffing the page's text before and after."; it tokenises the content stream itself (`tokenize`, `remove_artifacts`), reads `MarkInfo` and `StructTreeRoot` through `doc.xref_get_key` (`is_tagged`), and scans every xref for `/StructElem` types (`struct_types`); 246 lines. ### Inferences
- The report's Stage 1 is larger than it allows: with a reader that exposes `mcid` per char, the structure tree can replace band detection, panel-versus-table detection, header-row detection and heading-level detection in the existing pipeline, which is most of the semantic gain the frame walker promises. What remains unique to the walker is geometry already resolved into Typst's own units, the `Page.numbering` pattern, and access to element fields after show rules, none of which the stress failures hinge on.
- The route has the same version coupling as today (the tag writer is typst-pdf at the pinned version) and no new binary, no Rust stage and no new sandbox.
- It inherits the report's Stage 1 caveat: pdf2docx still does the layout, so image overlap and margin overrun are not addressed by structure alone; but the scorecard shows the page-count and band problems on the 57-page document were.

### Gaps
- pypdfium2's exposure of the struct-tree functions and Poppler's `StructElement` Python bindings were not checked.
- No measurement of the cost of switching the text source from PyMuPDF to pdfplumber (pdfminer-based, slower) in BTCT's converter.

## 13. Are the staged plan's exit criteria feasible, in particular "page count equal to the PDF's" across Word versions?

### Takeaway
Feasible as a single-oracle regression gate, not as a cross-version guarantee, and the repository already works that way. With an explicit page break at every Typst page boundary, Word can add pages (overflow) but cannot remove one, so "equal" means "no overflow on the reference Word"; BTCT's scorecard already records 57 of 57 and 23 of 23 on one machine's Word and states that its numbers are "a record, not a CI gate". Microsoft's documentation of repagination and the MVP's "half a per cent" Mac reflow mean no file can promise equality on every Word, and the criterion should name the oracle.

### Cited Findings
- `SCORECARD.md` line 23: "Numbers come from this machine's Word; a record, not a CI gate."; stress-cptc-57 at 57 Word pages for 57 PDF pages and reference at 23 for 23 (lines 46 to 47); stress-cptc-long at 174 Word pages for 119 PDF pages (line 61). (Repo file.)
- Microsoft: `Options.Pagination` "True if Microsoft Word repaginates documents in the background."; Word MVP: "Assume that a Mac will reflow text by about half a per cent."; MakeUseOf: LibreOffice ran a two-page Word file to three. (Sources in section 8.)
- The report itself: explicit page breaks "bound the page count to the PDF's in all but overflow cases" (reports/Typst to DOCX export.md, architecture section).

### Inferences
- Stage 3's criterion "stress report page count equal to the PDF's" is already met by the current converter on the 57-page document, so it cannot by itself show the new path beats the old one; the 119-page document (174 for 119) is the one that would.
- Stage 2's "its PDFs render identically to the CLI's on all corpus documents" is well-posed, because both are produced by the same typst-pdf version in the same process model; it should be checked byte for byte or by rasterised diff, and the CLI's own behaviour of dropping tags when a page range is exported (`compile.rs` line 141) says the comparison must be whole-document.
- Stage 4's "a Word user can regenerate the TOC and get the same entries" depends on Word's field refresh, which docx.js documents as a prompt ("Word will still prompt to update the field"); that is a manual step in the test unless the oracle is driven through COM as `scorecard.py` already does.

### Gaps
- No source quantifies how often a forced-break document overflows in Word for a given font set; the report also flags this as needing measurement.

## 14. Overall verdict on the recommendation

### Takeaway
The technical core survives: at 0.14.2 the compiler does label header, footer and background marginals, tags bracket every structural element including table cells, and the types are public on crates.io, so a `btct-typst` is buildable as described. Three findings cut against the recommendation as written. First, its motivating failure (bands in the body, 83 Word pages for 57) was fixed one day after the report by the tagged-PDF pass it proposed as a stopgap, so the base for "not bugs a sixth repair pass will close" is now the 119-page document and the thesis shape, not the 57-page one. Second, the frame tree does not delimit lines, so the faithful mode's "impose Typst's breaks" needs line reconstruction from glyph positions, which is inference of the kind the report says the walker avoids. Third, the structure the walker would read is already in every PDF BTCT writes, and pdfplumber and pdfium can join it to text by marked-content ID, which makes a compiler-free Stage 1 cover most of the semantic gain. The costs the report under-weights are a Rust build stage (6 min 19 s, 1.1 GB scratch, 46 MB binary on a 24-thread machine) or a hash-pinned prebuilt artifact, and a per-release adaptation that tinymist absorbed with seven PRs for 0.15 and that BTCT would carry alone.

### Cited Findings
- All findings above; the summary draws on sections 1 to 13 and cites no new source.

### Inferences
- A defensible ordering is the report's own Stage 0 and Stage 1, with Stage 1 widened to a marked-content join (pdfplumber or pdfium) rather than header and footer only, measured on stress-cptc-long and stress-thesis; Stage 2 onward is justified if, and only if, that leaves failures the scorecard can name that structure alone cannot fix (image overlap by misattribution, margin overrun, the 174-for-119 overflow).
- If Stage 2 is pursued, two choices improve on the report: build `typst-kit` without the `packages` feature so no network code exists in the binary, and prebuild `btct-typst` once per typst version and pin it by sha256 in the Dockerfile exactly as the CLI is pinned today, so the 1 to 2 GB target box never sees a Rust toolchain.

### Gaps
- Three background verification agents (writer libraries, Word pagination and converter modes, Typst ecosystem) were started for this cross-check and had not reported when the notes were closed; every claim in their areas was verified directly instead, so nothing here depends on them.
