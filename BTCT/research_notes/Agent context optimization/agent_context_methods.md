# Agent context and memory optimization for long fix-measure-fix loops (as of 2026-10-10)

Scope: methods for keeping an LLM coding agent (Claude Code in particular) making progress over many iterations toward a goal on one codebase, without looping or drifting. Sources are primary where possible (vendor docs and engineering posts, arXiv papers); community observations are labelled as such. Every claim carries an inline source link. Dates are the publication or revision dates shown on the source.

Source quality legend used below: **[doc]** vendor documentation, **[eng]** vendor engineering post, **[paper]** peer-reviewed or arXiv, **[practitioner]** individual write-up, **[secondary]** third-party summary of a source I could not reach.

## Key question 1: What do Anthropic, OpenAI, Google, Cursor, Devin/Cognition and Manus publish about managing context for long tasks?

### Takeaway
Every vendor converges on the same five moves: treat the window as a scarce budget; keep the always-loaded instruction file short and specific; put durable state in files (progress log, feature list, plan, notes) that a fresh context re-reads; compact deliberately rather than at the limit; and isolate noisy work (research, verification) in a fresh context that returns only a summary. The documented numbers differ by tool, but the shape is identical.

### Cited Findings

**Anthropic: context engineering (engineering post, 2025-09-29)**
- "Context, therefore, must be treated as a finite resource with diminishing marginal returns" and "Every new token introduced depletes this budget by some amount." The goal is "finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." Source: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) [eng]
- System prompts should sit at the right "altitude": "specific enough to guide behavior effectively, yet flexible enough to provide the model with strong heuristics." Start minimal with the best model and add instructions only in response to observed failures. Source: [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) [eng]
- Prefer just-in-time retrieval: agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.)" and load data at runtime; a hybrid (pre-load some, explore the rest) suits less dynamic content. Default: "do the simplest thing that works." Source: [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) [eng]
- Three named techniques for long-horizon work: compaction, structured note-taking, and multi-agent architectures. Compaction tuning: "Start by maximizing recall to ensure your compaction prompt captures every relevant piece of information," then raise precision. Lightest touch is clearing old tool results: "once a tool has been called deep in the message history, why would the agent need to see the raw result again?" Source: [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) [eng]
- Structured note-taking: "the agent regularly writes notes persisted to memory outside of the context window" (examples: Claude Code to-do lists, a NOTES.md, Claude playing Pokemon tracking "Pikachu has gained 8 levels toward the target of 10" across thousands of steps and reading notes back after context resets). Source: [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) [eng]
- Sub-agents return "only a condensed, distilled summary of its work (often 1,000-2,000 tokens)" while "the detailed search context remains isolated within sub-agents." Which technique to pick: compaction for long back-and-forth, note-taking for "iterative development with clear milestones", multi-agent for parallel research. Source: [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) [eng]

**Anthropic: harnesses for long-running agents (engineering post, 2025-11-26, tested on Opus 4.5)**
- Two-part harness: an initializer agent (first session) writes `init.sh`, a progress log file, an initial git commit, and expands the prompt into a feature list "with every feature initially marked as not passing" (over 200 features in the claude.ai-clone example); a coding agent (every later session) reads the progress file, the git log and the feature list, runs `init.sh` and a basic end-to-end check, then works on "only one feature at a time". Source: [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) [eng]
- The feature list is JSON, not Markdown, "because the model is less likely to inappropriately change or overwrite JSON"; the agent may only flip the `passes` field, and "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." Source: [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) [eng]
- "The key insight" is "finding a way for agents to quickly understand the state of work when starting with a fresh context window": the progress file plus git history with descriptive commit messages. Source: [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) [eng]
- Failure modes observed and fixes: declares the project finished too early (fix: feature list, one feature per session); leaves bugs or undocumented progress (fix: git plus progress notes, test basics at session start, commit and update progress at session end); marks features done prematurely (fix: self-verify before marking passing, "do all testing as a human user would", which "dramatically improved performance"); wastes time working out how to run the app (fix: `init.sh`). Also: an agent that tries to one-shot the app "runs out of context mid-implementation" leaving "a feature half-implemented and undocumented", and "Compaction alone doesn't always pass clear instructions to the next agent." Source: [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) [eng]

**Anthropic: Claude Code best practices (docs, current as of 2026-10, references v2.1.283)**
- Framing: "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills." and "The context window is the most important resource to manage." Source: [Best practices](https://code.claude.com/docs/en/best-practices) [doc]
- Verification: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available." Four escalating gates: in one prompt; across a session via `/goal`; "As a deterministic gate: a Stop hook runs your check as a script and blocks the turn from ending until it passes"; "By a second opinion: a verification subagent" so "the agent doing the work isn't the one grading it." And: "Have Claude show evidence rather than asserting success." Source: [same](https://code.claude.com/docs/en/best-practices) [doc]
- CLAUDE.md: "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" Include commands Claude can't guess, style rules that differ from defaults, test runners, repo etiquette, project-specific architectural decisions, env quirks, non-evident gotchas; exclude anything derivable from code, standard conventions, API docs, "Information that changes frequently", file-by-file descriptions. "If Claude keeps skipping one instruction, add emphasis such as 'IMPORTANT' to that line alone. If you emphasize many lines, none of them stands out." Source: [same](https://code.claude.com/docs/en/best-practices) [doc]
- Course correction: "If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Run `/clear` and start fresh with a more specific prompt that incorporates what you learned. A clean session with a better prompt almost always outperforms a long session with accumulated corrections." Source: [same](https://code.claude.com/docs/en/best-practices) [doc]
- Context: `/clear` between unrelated tasks; `/compact <instructions>`; partial compaction via `/rewind` "Summarize from here" or "Summarize up to here"; CLAUDE.md can carry compaction instructions such as "When compacting, always preserve the full list of modified files and any test commands"; `/btw` for side questions that "never enter conversation history". Source: [same](https://code.claude.com/docs/en/best-practices) [doc]
- Subagents: "Since context is your fundamental constraint, use subagents to keep research out of it." Adversarial review: a reviewer "in a fresh subagent context sees only the diff and the criteria you give it, not the reasoning that produced the change"; but "A reviewer prompted to find gaps will usually report some, even when the work is sound", so tell it to "flag only gaps that affect correctness or the stated requirements." Source: [same](https://code.claude.com/docs/en/best-practices) [doc]
- Named failure patterns: the kitchen sink session; "Correcting over and over" (fix: "After two failed corrections, `/clear`"); the over-specified CLAUDE.md; the trust-then-verify gap ("If you can't verify it, don't ship it"); the infinite exploration (fix: scope narrowly or use subagents). Source: [same](https://code.claude.com/docs/en/best-practices) [doc]
- Spec-first: have Claude interview you, write `SPEC.md`, then "start a fresh session to execute it." Source: [same](https://code.claude.com/docs/en/best-practices) [doc]

**Anthropic: Claude Code memory system (docs, current as of 2026-10)**
- Two systems: CLAUDE.md (you write; instructions) and auto memory (Claude writes; learnings), both "context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." Source: [How Claude remembers your project](https://code.claude.com/docs/en/memory) [doc]
- Add to CLAUDE.md when "Claude makes the same mistake a second time", a review catches something it should have known, or "You type the same correction or clarification into chat that you typed last session." Size: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Imports "don't reduce its context cost, because imported files also load at launch." Contradictions: "if two instructions contradict each other, Claude may pick one arbitrarily." `/doctor prompt-audit` finds stale and conflicting instructions (v2.1.283+). Source: [same](https://code.claude.com/docs/en/memory) [doc]
- Auto memory stores four types (`user`, `feedback`, `project`, `reference`); "Claude skips anything it can derive from the codebase, such as architecture, file paths, or debugging fixes." Layout: `~/.claude/projects/<project>/memory/` with `MEMORY.md` index plus one topic file per memory; "The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first, are loaded at the start of every conversation"; topic files load on demand; writes stamp a `modified` ISO timestamp (v2.1.214+). Source: [same](https://code.claude.com/docs/en/memory) [doc]
- "Project-root CLAUDE.md survives compaction: after `/compact`, Claude re-reads it from disk." Nested CLAUDE.md and path-scoped rules reload on demand; "If an instruction disappeared after compaction, it was given only in conversation." Source: [same](https://code.claude.com/docs/en/memory) [doc]
- What survives compaction (table): system prompt; project-root CLAUDE.md and unscoped rules, auto memory and the plan-mode plan ("Re-injected from disk"); files read or edited ("Claude Code re-reads up to five, most recently modified first", and "A file over 5,000 tokens comes back as a path reference without its content"); invoked skill bodies "capped at 5,000 tokens per skill and 25,000 tokens total; oldest dropped first"; hook-added context is "Summarized with the rest"; `SessionStart` hooks matching the `compact` source run again. The skill *index* "is not re-injected after `/compact`". Source: [Explore the context window](https://code.claude.com/docs/en/context-window) [doc]
- Auto-compact thresholds (model-config): default is "when the conversation reaches the model's context limit", except cloud sessions compact "as the conversation approaches the model's limit", Sonnet 4.6/Opus 4.6 without extended context "compact at the 200K boundary", and native 1M-window models "compact before the window fills, at about 967K tokens by default." Override with `/autocompact 500k` (100K to 1M) or `CLAUDE_CODE_AUTO_COMPACT_WINDOW`. Source: [Model configuration](https://code.claude.com/docs/en/model-config) [doc]
- `/goal`: "After each turn, a model checks whether the condition holds"; the evaluator "doesn't run commands or read files independently, so write the condition as something Claude's own output can demonstrate." A good condition has "One measurable end state", "A stated check", and "Constraints that matter"; bound it with "or stop after 20 turns". Stall rule: "If Claude keeps answering the evaluator without making progress (no tool use for several turns in a row), Claude Code stops the loop, prints a warning, and returns control to you with the goal still set." A context overflow that auto-compaction cannot clear also clears the goal. Source: [Keep Claude working toward a goal](https://code.claude.com/docs/en/goal) [doc]
- Stop hook cap: "Claude Code overrides a Stop hook after it blocks eight times in a row with no tool call from Claude in between." Hooks must check `stop_hook_active`. Source: [Hooks guide](https://code.claude.com/docs/en/hooks-guide) [doc]
- Subagents: "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read." CLAUDE.md hierarchy is loaded (Explore and Plan agents skip it); "The main conversation's auto memory isn't loaded." A fork "inherits the entire conversation so far" with a shared prompt cache; use a fork "when any other subagent would need too much background to be useful, or when you want to try several approaches in parallel from the same starting point." Warning: "Running many subagents that each return detailed results can consume significant context." Use the main thread when "Multiple phases share significant context, such as planning, implementation, and testing"; use subagents when "The task produces verbose output you don't need in your main context" or "The work is self-contained and can return a summary." Subagents can get their own persistent `memory` directory (first 200 lines or 25KB of its `MEMORY.md` loaded). Source: [Subagents](https://code.claude.com/docs/en/sub-agents) [doc]

**Anthropic: memory tool and context editing (platform docs, current as of 2026-10)**
- The API injects this protocol when the memory tool is present: "IMPORTANT: ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE. ... As you make progress, record status / progress / thoughts etc in your memory. ASSUME INTERRUPTION: Your context window might be reset at any moment, so you risk losing any progress that is not recorded in your memory directory." Also: "Do not create new files unless necessary" and "keep its content up-to-date, coherent and organized." Source: [Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) [doc]
- Documented "Multisession software development pattern": initializer session writes the progress log, feature checklist and startup script; each later session "opens by reading those memory files"; end-of-session update; "Work on one feature at a time. Mark a feature complete only after end-to-end verification confirms it works, not when the code is written." Pair memory with server-side compaction: "compaction keeps the active context small without client-side bookkeeping, and memory preserves the information that must survive summarization." Source: [same](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) [doc]
- Context editing: `clear_tool_uses_20250919` clears the oldest tool results once the prompt passes a trigger (default 100,000 input tokens), keeping the last 3 tool uses by default, with `exclude_tools` and `clear_at_least`; "When your conversation context approaches the configured clearing threshold, Claude receives an automatic warning to preserve important information." Clearing "Invalidates cached prompt prefixes". Server-side compaction is `compact_20260112`: "For most use cases, server-side compaction is the primary strategy for managing context in long-running conversations." Source: [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing) [doc]

**Anthropic: multi-agent research system (engineering post, 2025-06-13)**
- "agents typically use about 4x more tokens than chat interactions, and multi-agent systems use about 15x more tokens than chats"; on BrowseComp "token usage by itself explains 80% of the variance". Source: [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) [eng]
- Lead agent saves "its plan to Memory to persist the context"; "if the context window exceeds 200,000 tokens it will be truncated"; agents "summarize completed work phases and store essential information in external memory"; "When context limits approach, agents can spawn fresh subagents with clean contexts." Source: [same](https://www.anthropic.com/engineering/multi-agent-research-system) [eng]
- "Scale effort to query complexity": "Simple fact-finding requires just 1 agent with 3-10 tool calls"; complex work "more than 10 subagents". Early failures: "spawning 50 subagents for simple queries", "scouring the web endlessly for nonexistent sources", "distracting each other with excessive updates", duplicated work from vague delegation. Source: [same](https://www.anthropic.com/engineering/multi-agent-research-system) [eng]

**Anthropic: building effective agents (engineering post, 2024-12-19) and Agent SDK post (2025-09-29)**
- Agents are "just LLMs using tools based on environmental feedback in a loop"; "it's also common to include stopping conditions (such as a maximum number of iterations) to maintain control"; agents gain "ground truth" from the environment at each step; "Code solutions are verifiable through automated tests" and "Agents can iterate on solutions using test results as feedback"; "we actually spent more time optimizing our tools than the overall prompt" (absolute file paths fixed a recurring error). Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) [eng]
- Agent loop as "gather context -> take action -> verify work -> repeat"; "the folder and file structure of an agent becomes a form of context engineering"; "Semantic search is usually faster than agentic search, but less accurate", start with agentic (grep-style) search; verification ranking: "The best form of feedback is providing clearly defined rules for an output", visual feedback helps, LLM-as-judge "is generally not a very robust method". Source: [Building agents with the Claude Agent SDK](https://claude.com/blog/building-agents-with-the-claude-agent-sdk) [eng]

**OpenAI Codex (docs, current as of 2026-10; models named GPT-6.1 Sol, GPT-6 Luna, GPT-6 Astra)**
- "A short, accurate `AGENTS.md` is more useful than a long file full of vague rules." Add rules only "after you notice repeated mistakes"; "keep the main file concise and reference task-specific markdown files"; "When Codex makes the same mistake twice, ask it for a retrospective and update `AGENTS.md`." Source: [Codex best practices](https://learn.chatgpt.com/guides/best-practices) [doc]
- Context: "Keep one chat per coherent unit of work"; one chat for a whole project leads to "bloated context and worse results over time"; `/compact` on demand ("Codex also compacts chats automatically"); `/fork` preserves the transcript; prompts should state a "Done when" condition; subagents "to offload bounded work from the main thread". Source: [same](https://learn.chatgpt.com/guides/best-practices) [doc]
- PLANS.md (cookbook, archived, model `gpt-5.2-codex`): "ExecPlans are living documents"; required sections are Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective (alongside Purpose, Context and Orientation, Plan of Work, Concrete Steps, Validation and Acceptance, Idempotence and Recovery, Artifacts and Notes, Interfaces and Dependencies); "Treat the reader as a complete beginner to this repository"; the template "enabled Codex to work for more than seven hours from a single prompt." Source: [Using PLANS.md for multi-hour problem solving](https://developers.openai.com/cookbook/articles/codex_exec_plans) [doc]

**Google**
- Gemini CLI: `/compress` will "Replace the entire chat context with a summary"; `/memory show` displays "the full, concatenated content of the current hierarchical memory that has been loaded from all GEMINI.md files"; `/restore` "Restores the project files to the state they were in just before a tool was executed" (requires checkpointing); `/chat save <tag>` and `resume`. No automatic compression threshold is documented on that page. Source: [Gemini CLI command reference](https://geminicli.com/docs/reference/commands) [doc]
- ADK: a `Session` holds "the history (`events`) and temporary data (`state`) of a single conversation"; memory is "a searchable archive or knowledge library the agent can consult"; `add_session_to_memory`, `add_events_to_memory` ("useful when you want to write to memory partway through a long-running session"), `search_memory`; ingest "When a session concludes or captures significant information." **Cursor (docs, current)**
- "Keep rules under 500 lines", "Split large rules into multiple, composable rules", "Provide concrete examples or referenced files", "Avoid vague guidance. Write rules like clear internal docs"; four rule types (always, auto-attached by glob, agent-requested, manual); nested `AGENTS.md` files combine with parents and more specific wins. Source: [Cursor rules](https://cursor.com/docs/context/rules) [doc]

**Cognition (Devin)**
- "Share context, and share full agent traces, not just individual messages" and "Actions carry implicit decisions, and conflicting decisions carry bad results"; the Flappy Bird example shows parallel subagents producing conflicting styles because "Subagent 1 and subagent 2 cannot not see what the other was doing"; a single-threaded linear agent "will get you very far"; a dedicated compression model is "hard to get right" and "You will still eventually hit a limit though." Source: [Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents) (2025-06-12) [eng]
- Devin's Knowledge and Playbooks: keep Knowledge items small and targeted, put step-by-step procedure in a playbook. Source: [Devin June '24 product update](https://cognition.com/blog/june-24-product-update) [eng]; third-party guide [fast.io](https://www.fast.io/resources/devin-knowledge-guide.md) [secondary]

**Manus (engineering post, 2025-07-18)**
- KV-cache hit rate is "the single most important metric for a production-stage AI agent" (average input:output ratio about 100:1; cached input 10x cheaper); keep prefixes stable and context append-only. "Mask, don't remove" tools. "File system as the ultimate context": restorable compression (drop a page but keep its URL, drop a document but keep its path). Recitation: Manus rewrites a `todo.md` so the plan stays in recent attention, countering "lost-in-the-middle" over a typical ~50 tool-call task. "Keep the wrong stuff in": leaving failed actions and stack traces in context lets the model "update its beliefs" and avoid repeating the mistake. "Don't get few-shotted": uniform context makes the agent mimic its own past actions, so add controlled variation. Source: [Context Engineering for AI Agents: Lessons from Building Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) [eng]

### Inferences
- The vendor advice splits into two layers that should not be mixed: an always-loaded instruction file (short, rule-like, under about 200 lines per Claude Code docs or 500 per Cursor) and a set of on-demand state files (progress, plan, notes) that a fresh context re-reads. Putting state in the instruction file bloats it; putting rules only in conversation loses them at compaction.
- Manus's "keep the wrong stuff in" and Claude Code's "after two failed corrections, /clear" are not contradictory: the first is about one trajectory within a window; the second is about when the window itself has become the problem. The reconciliation is to write the failure down (externally) before clearing.
- Anthropic's JSON-over-Markdown finding for the feature list is a general principle: anything the agent must not casually rewrite belongs in a format that feels like data, not prose.

### Gaps
- Claude Code's exact auto-compaction internals (the tool-result trimming layer, the nine-section summary) are described only by reverse-engineering write-ups; the official docs give the thresholds and what survives but not the algorithm. See KQ4.
- Cognition publishes no current Devin docs on long-task context handling that I could reach; the Knowledge/Playbook details are from 2024 posts and third-party guides.

## Key question 2: Which memory architectures have evidence, and which transfer to a coding loop?

### Takeaway
The evidence base is strongest for (a) reflection text stored across trials (Reflexion), (b) an ever-growing library of verified executable skills (Voyager), (c) OS-style paging between a small in-context working set and external storage (MemGPT), and (d) self-organizing linked notes (A-MEM). Graph and extraction services (Zep, Mem0) show gains on conversational recall benchmarks, which is a weaker proxy for a coding loop. What transfers directly: reflections-after-failure, a verified skill/recipe library, a bounded in-context working set with everything else paged to files, and typed, linked notes with a lint pass.

### Cited Findings
- **Reflexion** (2023-03-20, v4 2023-10-10): agents "verbally reflect on task feedback" and keep "this reflective text in an episodic memory buffer" that guides later trials; 91% pass@1 on HumanEval versus 80% for GPT-4. Source: [arXiv 2303.11366](https://arxiv.org/abs/2303.11366) [paper]
- **Voyager** (2023-05-25, v2 2023-10-19): "an ever-growing skill library of executable code", refined "through environment feedback, execution errors, and self-verification"; 3.3x more unique items, 2.3x longer distances, tech-tree milestones up to 15.3x faster than prior methods; the library transfers to a new world. Source: [arXiv 2305.16291](https://arxiv.org/abs/2305.16291) [paper]
- **MemGPT** (2023-10-12, v2 2024-02-12): "virtual context management" borrowed from OS hierarchical memory, moving data between tiers to "give the appearance of a much larger memory"; uses interrupts for control flow; evaluated on document analysis beyond the window and multi-session chat. The abstract gives no numbers. Source: [arXiv 2310.08560](https://arxiv.org/abs/2310.08560) [paper]
- **Generative Agents** (2023-04-07, v2 2023-08-06): a memory stream (complete natural-language record), synthesized "over time into higher-level reflections", retrieved dynamically to plan; ablation shows observation, planning and reflection "each contribute critically". Source: [arXiv 2304.03442](https://arxiv.org/abs/2304.03442) [paper]
- **A-MEM** (2025-02-17, v11 2025-10-08, NeurIPS 2025): Zettelkasten-inspired; each new memory becomes a note with "contextual descriptions, keywords, and tags", links are made to historical memories where "meaningful similarities exist", and "memory evolution" updates existing notes when new ones arrive; "superior improvement against existing SOTA baselines" on six foundation models (no numbers in abstract). Source: [arXiv 2502.12110](https://arxiv.org/abs/2502.12110) [paper]
- **Zep / Graphiti** (2025-01-20): temporally-aware knowledge graph; 94.8% on DMR versus 93.4% for MemGPT; up to 18.5% accuracy gains on LongMemEval and 90% latency reduction. Source: [arXiv 2501.13956](https://arxiv.org/abs/2501.13956) [paper]
- **Mem0** (2025-04-28): extracts and consolidates memories; 26% relative improvement over OpenAI's memory on LOCOMO (LLM-as-judge), graph variant about 2% higher, "91% lower p95 latency" and "more than 90% in token cost" saved versus full-context. Source: [arXiv 2504.19413](https://arxiv.org/abs/2504.19413) [paper]
- **Letta memory blocks** (2025-05-14): blocks "break the context window down into manageable, purposeful units that are also persisted", each with a label, value, and "a size limit (e.g. in characters or tokens) that dictates how much of the context window it can occupy"; agents self-edit unless a block is read-only. Source: [Letta: Memory Blocks](https://www.letta.com/blog/memory-blocks) [eng]
- **Letta sleep-time / dreaming** (docs, current): "Dreaming uses background subagents to review recent conversations" and consolidate lessons "without interrupting your active work", triggered "after a set number of completed agent steps or when the context window is compacted"; memory lives in a git-backed filesystem. Source: [Letta docs](https://docs.letta.com/guides/agents/architectures/sleeptime) [doc]
- **LangChain taxonomy** (2025-07-02): write (scratchpads, memories), select (rules files, retrieval), compress (summaries, trimming), isolate (subagents, sandboxes, state schemas); reports Claude Code auto-compact "after exceeding 95% of the context window" (that figure is LangChain's, not Anthropic's current docs, which give token boundaries instead). Source: [Context Engineering for Agents](https://www.langchain.com/blog/context-engineering-for-agents) [eng]

### Inferences
- Reflexion maps one-to-one onto a fix-measure loop: after each failed attempt, write a short reflection (what was tried, what the measurement said, why it probably failed) that the next attempt reads. The 91% versus 80% HumanEval result is the closest thing to direct evidence for "write down why the last fix failed".
- Voyager maps onto a "verified recipes" file: a fix that passed the gate is stored as a reusable procedure, keyed by the symptom it addresses. Voyager's self-verification step is the gate.
- MemGPT's lesson for Claude Code is the working-set discipline: keep the in-window state small and page everything else to files that are read by path, which is also what Anthropic's "lightweight identifiers" advice and Manus's "restorable compression" say.
- A-MEM's "memory evolution" is the research justification for a lint pass that rewrites old notes when new evidence lands, rather than only appending.
- Zep and Mem0 numbers are about chat recall; they justify keeping a structured index but do not show a coding-loop gain.

### Gaps
- I found no controlled study measuring a coding agent's loop convergence with versus without an external failure log; the Reflexion and Anthropic harness results are the nearest evidence.
- MemGPT and A-MEM abstracts carry no quantitative results; full-paper numbers were not fetched.

## Key question 3: What do practitioners report about "connected brain" notes for agents, and what breaks?

### Takeaway
Linked-markdown vaults work when a schema file defines the conventions, an index page keeps the entry point small, daily/session logs are append-only, and a periodic lint pass repairs contradictions and orphans. They break on unbounded growth (every session loads more), inconsistent formats, over-adherence to stale decisions, and agents treating links as decoration rather than retrieval.

### Cited Findings
- **Karpathy "llm-wiki"** (gist, 2026-04-04; details via secondary sources): three layers (immutable raw sources, an LLM-maintained wiki of markdown pages, a schema file in CLAUDE.md or AGENTS.md), a flat layout with `index.md` and `log.md`, and an ingest / query / lint cycle; quoted line "Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase." The lint pass checks contradictions, stale claims, orphans, missing pages and missing cross-references (that list is the blogs' elaboration, not confirmed as Karpathy's own). Gist commenters claim the flat pattern strains past roughly 1,000 files. Source: [denser.ai summary](https://denser.ai/blog/llm-wiki-karpathy-knowledge-base/) [secondary]; [agentpedia summary](https://agentpedia.codes/blog/karpathy-llm-knowledge-bases) [secondary]; [mindstudio summary](https://www.mindstudio.ai/blog/andrej-karpathy-llm-wiki-obsidian-ai-second-brain) [secondary]
- **antirez, FLUX.2-klein in pure C** (2026-01-18): "this project was possible only once I started to tell Opus that it needed to take a file with all the implementation notes ... and also accumulating all the things we discovered during the development process. And also, the file had clear instructions to be taken updated, and to be processed ASAP after context compaction. This kinda enabled Opus to do such a big coding task in a reasonable amount of time without loosing track." Source: [Simon Willison](https://simonwillison.net/2026/jan/18/flux2-klein-4b) quoting antirez [practitioner]
- **Shared Obsidian vault for Claude Code** (2026-02-25): flat vault, "Organisation is via tags and wiki-links, not directory hierarchy"; daily notes `YYYY-MM-DD.md` as append-only session journals with carried-forward open items; at session start the agent reads recent daily notes and greps tag lines instead of re-exploring the codebase; an auditor skill reads all notes and reports severity-rated inconsistencies to the daily note only; "Before that, you can spot inconsistencies yourself. After that, you can't" (threshold about 20 notes). No measured token savings are reported. Source: [A Shared Memory for Claude Code](https://sphelps.substack.com/p/a-shared-memory-for-claude-code) [practitioner]
- **Decision records with agents** (2026-09-01): ADRs as markdown in `docs/decisions`; AGENTS.md rules make accepted ADRs binding, proposed ones non-binding, superseded ones historical; each ADR holds only its current text (git is the changelog) with an `Updated:` line. Problems observed: over-adherence ("Agents fought to preserve an obsolete storage abstraction" and one "added a layer to stay technically compatible with the old ruling") and bloated amendments when agents were allowed to edit ADRs. Remedies: "explicit permission to question outdated decisions" and keep each record to ruling plus rationale. Source: [Coding agents love decision records](https://duncandavidson.com/agents-love-decisions) [practitioner]
- **"Stop calling it memory"** (2026-03-23): a folder of markdown is "a filing system", not memory; "the context window isn't a search engine. It's a text buffer"; failure modes: unbounded growth crowds out the task, no querying so the agent must read everything, inconsistent formats across sessions, concurrent-write corruption, wikilinks support visualization but not multi-hop queries. Author sells a structured-storage alternative, so weight accordingly. Source: [Limited Edition Jonathan](https://limitededitionjonathan.substack.com/p/stop-calling-it-memory-the-problem) [practitioner, interested party]
- **Wikilinks versus markdown links**: Obsidian resolves both, but GitHub, VS Code and most agents render only standard markdown links, and a lint step flagged every wikilink as broken. Source: [m4bwav/obsidian-notes](https://github.com/m4bwav/obsidian-notes) [practitioner]
- **ADRs for agents, lean rules**: "an ADR with 50 crisp rules outperforms one with 200 verbose rules" (practitioner claim, no measurement). Source: [Conduction: Writing ADRs for AI Agents](https://docs.conduction.nl/claude/writing-adrs/) [practitioner]
- **Vendor-side corroboration**: Claude Code auto memory uses exactly this shape (index file with a hard load cap, one topic file per fact, frontmatter `type` and `modified`, "Claude keeps `MEMORY.md` concise by moving detailed notes into separate topic files"). Source: [Claude Code memory docs](https://code.claude.com/docs/en/memory) [doc]

### Inferences
- The recurring working pattern is: small always-loaded index, typed topic notes read on demand, append-only session log, and a lint/audit task that runs on a schedule rather than inline. Every successful report has those four parts; the failure reports describe vaults missing one of them.
- Over-adherence is the agent-specific hazard of decision logs: an agent reads "decided" as "immutable". Records need a status field and a standing instruction that superseding is allowed and expected.
- Link syntax matters for tooling, not for the model: use standard relative markdown links if anything other than Obsidian will read the vault.

### Gaps
- No practitioner report gives measured token or time savings for a vault; claims are qualitative.
- Karpathy's gist itself was not reachable; the lint checklist attributed to him may be the summarizers' elaboration.

## Key question 4: What measured results exist on context length versus performance, and on compaction strategies?

### Takeaway
Across 18 models, performance declines as input grows even on trivially simple tasks, distractors and coherent (non-shuffled) filler hurt most, and a focused 300-token prompt beats a 113k-token full prompt on the same question. Goal adherence decays with context length and drifts toward pattern-matching. Compaction is lossy by design; what reliably survives it is whatever lives on disk and is re-read.

### Cited Findings
- **Lost in the Middle** (2023-07-06, v3 2023-11-20): performance "is often highest when relevant information occurs at the beginning or end of the input context, and significantly degrades when models must access relevant information in the middle of long contexts, even for explicitly long-context models." Source: [arXiv 2307.03172](https://arxiv.org/abs/2307.03172) [paper]
- **Context Rot** (Chroma, 2025-07-14): 18 models (5 Anthropic, 7 OpenAI, 3 Google, 3 Qwen); models "do not use their context uniformly"; lower needle-question similarity degrades faster with length; one distractor hurts, four hurt more, Claude models abstain most and GPT models hallucinate most; shuffled haystacks beat coherent ones, structural coherence "consistently hurts model performance"; LongMemEval: 306 prompts, full ~113k tokens versus focused ~300 tokens, "All models scored significantly higher on focused prompts"; conclusion: having relevant information in context "is not enough", presentation matters. Source: [Context Rot](https://www.trychroma.com/research/context-rot) [eng/research]
- **Goal drift** (2025-05-05): the best configuration (scaffolded Claude 3.5 Sonnet) kept "nearly perfect goal adherence" for over 100,000 tokens in the hardest setting, but "all evaluated models" drifted, and drift "correlates with increasing susceptibility to pattern-matching behaviors as context length grows." Source: [arXiv 2505.02709](https://arxiv.org/abs/2505.02709) [paper]
- **Four context failure modes** (Breunig, 2025-06-22, collating other studies): poisoning (Gemini 2.5 Pokemon agent "fixated on achieving impossible or irrelevant goals" after a hallucinated state entered its summary); distraction (same agent past ~100k tokens "favored repeating actions from its history over devising new plans"; a Databricks study found correctness falling around 32k tokens for Llama 3.1 405b); confusion (Berkeley Function-Calling: every model performed worse with more than one tool; a quantized Llama 3.1 8b failed with 46 tools but succeeded with 19); clash (Microsoft/Salesforce sharded-prompt study: average 39% drop, o3 from 98.1 to 64.1, models "get lost and do not recover"). Source: [How Long Contexts Fail](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html) [practitioner collating papers]
- **HORIZON** (2026-04-13): 3,100+ trajectories across Web, OS, Embodied and Database domains; seven failure categories, of which Catastrophic Forgetting ("Early constraints remain in context but are no longer attended to"), History Error Accumulation and Memory Limitation ("Earlier information is lost from context through truncation, summarization, or incomplete retrieval") are "predominantly long-horizon"; process-level risks 72.5%, design-level 27.5%; planning failures "often arise early, propagate through downstream actions"; an agent "repeated the same failed action across multiple steps" after a failed click. No mitigation was evaluated. Source: [arXiv 2604.11978](https://arxiv.org/html/2604.11978v1) [paper]
- **Compaction, official**: Claude Code re-injects the project-root CLAUDE.md, auto memory, the plan-mode plan, up to five recently modified files (over 5,000 tokens becomes a path reference), invoked skill bodies (5,000 per skill, 25,000 total), and `SessionStart` hooks for the `compact` source; conversation-only instructions and nested or path-scoped rules do not survive unless re-triggered. Source: [Context window](https://code.claude.com/docs/en/context-window) [doc]; [Memory](https://code.claude.com/docs/en/memory) [doc]
- **Compaction, reverse-engineered (unofficial)**: a 2026-04-09 analysis claims Claude Code trims old tool results before every request without an LLM call, trims from the tail to preserve prompt-cache prefixes, triggers LLM summarization at roughly "effective context window minus 13,000 tokens", produces a nine-section summary (original intent, concepts, files, errors and fixes, problem-solving chain, user messages, TODOs, current work, next steps), and pauses auto-compaction after 3 consecutive failures; Codex keeps all user messages verbatim and replaces assistant and tool messages with one summary; OpenCode protects the last 40,000 tokens and the last 2 user turns. The author says the Claude Code claims rest on a leaked repository. Source: [justin3go](https://justin3go.com/en/posts/2026/04/09-context-compaction-in-codex-claude-code-and-opencode) [practitioner, unverified for Claude Code]
- **API-side**: `clear_tool_uses_20250919` default trigger 100,000 input tokens, keep 3; server-side `compact_20260112` is "the primary strategy" for long conversations. Source: [Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing) [doc]
- **Community thresholds for proactive compaction** vary (60%, 70%, 95%) and are not from Anthropic. Sources: [saeed-vayghan](https://saeed-vayghan.github.io/blog/claude-code-context-management.html), [agentcat](https://agentcat.com/guides/managing-claude-code-context/), [LangChain](https://www.langchain.com/blog/context-engineering-for-agents) [secondary]

### Inferences
- The Chroma "focused beats full" result and the goal-drift result together say the same thing for a loop: each iteration should see a short, current briefing, not the accumulated transcript. The transcript is for the log on disk.
- Distraction (repeating past actions once history is long) is the mechanism behind a looping fix-measure cycle; it argues for resetting context between attempts and reading a failure registry, rather than leaning on the window to remember what was tried.
- "Coherent filler hurts more than shuffled filler" means long narrative notes are worse padding than terse tables or bullet facts. Notes meant for the agent should be flat and factual.

### Gaps
- No published measurement of how much a *structured* compaction summary loses versus a *notes file* re-read; vendors state the preference (notes survive, compaction is lossy) without numbers.
- The 1M-token windows now default on Claude Code (Fable, Sonnet 5, Opus 4.7+) have no public study yet of where degradation begins at that scale; Chroma's study ran at up to ~113k in LongMemEval.

## Key question 5: What loop-prevention tactics have evidence?

### Takeaway
What has documented support: an external check the agent must pass (tests, build, screenshot diff), an independent evaluator that is not the worker, hard caps (max turns, Stop-hook cap of eight consecutive blocks, "stop after N turns" in a goal), a reset after two failed corrections with the lesson written down first, leaving failure traces visible within a window, and a "three failed fixes means question the architecture" rule. What lacks controlled evidence: explicit "do not retry" registries (supported by Reflexion's mechanism and by practitioner reports, not by a coding-agent study).

### Cited Findings
- **Verification gates**: "Give Claude something that produces a pass or fail, and the loop closes on its own"; Stop hooks are "deterministic and guarantee the action happens" unlike advisory CLAUDE.md; `/goal` runs a separate evaluator "so completion is decided by a fresh model rather than the one doing the work"; "Have Claude show evidence rather than asserting success." Source: [Best practices](https://code.claude.com/docs/en/best-practices) [doc]; [Goal](https://code.claude.com/docs/en/goal) [doc]
- **Hard caps**: Stop hook overridden "after it blocks eight times in a row with no tool call from Claude in between". Source: [Hooks guide](https://code.claude.com/docs/en/hooks-guide) [doc]. `/goal` stalls out when there is "no tool use for several turns in a row"; include "or stop after 20 turns" in the condition. Source: [Goal](https://code.claude.com/docs/en/goal) [doc]. "stopping conditions (such as a maximum number of iterations)". Source: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) [eng]
- **Reset after repeated failure**: "If you've corrected Claude more than twice on the same issue in one session, the context is cluttered with failed approaches. Run `/clear` and start fresh with a more specific prompt that incorporates what you learned." Source: [Best practices](https://code.claude.com/docs/en/best-practices) [doc]. Codex: "When Codex makes the same mistake twice, ask it for a retrospective and update `AGENTS.md`." Source: [Codex best practices](https://learn.chatgpt.com/guides/best-practices) [doc]
- **Keep failures visible within a window**: leaving failed actions and stack traces in context lets the model "update its beliefs" and avoid repeating the mistake (Manus). Source: [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) [eng]. Reflexion's episodic buffer of reflections is the same mechanism across trials, with the 91% versus 80% HumanEval result. Source: [arXiv 2303.11366](https://arxiv.org/abs/2303.11366) [paper]
- **Recitation against drift**: rewriting `todo.md` each step keeps the global plan in recent attention over ~50 tool calls. Source: [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) [eng]
- **Progress files and immutable test lists**: "It is unacceptable to remove or edit tests"; JSON because the model is less likely to overwrite it; mark passing only after end-to-end verification. Source: [Long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) [eng]
- **Three strikes then step back** (community skill, superpowers 6.4.1 systematic-debugging): "If >= 3: STOP and question the architecture", "DON'T attempt Fix #4 without architectural discussion", "3+ failures = architectural problem. Question pattern, don't fix again." Source: local file `C:\Users\rober\.claude\plugins\cache\claude-plugins-official\superpowers\6.4.1\skills\systematic-debugging\SKILL.md` [practitioner skill, no measurement]
- **Action fingerprinting and repeated-error breakers** (community): hash tool name plus normalized arguments and block exact repeats; trip a breaker when the same error signature repeats N times; escalate (nudge, fresh context, park the task). A bug class seen in practice: breakers whose counters reset on any success so interleaved failures escape detection. Sources: [dev.to watchdog](https://dev.to/yureki_lab/how-i-built-a-watchdog-that-stops-my-ai-coding-agent-from-looping-forever-61h), [Horseless-Carriage issue #408](https://github.com/CI-Till-Krempel/Horseless-Carriage/issues/408), [Gitlawb/zero PR #866](https://github.com/Gitlawb/zero/pull/866) [practitioner]
- **Fresh context per iteration (Ralph loop)**: the loop re-feeds one prompt file to a fresh agent process each iteration; "progress persists in files and git, not in the LLM's context window"; the stop condition and durable state decide whether it is useful or "an expensive hamster wheel". Source: [DreamHost: The Ralph Wiggum Loop](https://www.dreamhost.com/blog/ralph-wiggum/) [practitioner]
- **Diff-based progress checks and checkpoints**: Claude Code checkpoints every prompt and can "restore conversation, code, or both"; checkpoints "only track changes made through Claude's file editing tools" so they are "not a replacement for git." Source: [Best practices](https://code.claude.com/docs/en/best-practices) [doc]. Gemini CLI `/restore` reverts to the pre-tool state when checkpointing is on. Source: [Gemini CLI commands](https://geminicli.com/docs/reference/commands) [doc]
- **Repeated failed action is a measured failure mode**: HORIZON records an agent that "repeated the same failed action across multiple steps" and agents acting on stale state without re-observing. Source: [arXiv 2604.11978](https://arxiv.org/html/2604.11978v1) [paper]

### Inferences
- The tactics with the strongest footing are mechanical, not prompt-level: a pass/fail gate the agent cannot edit, an evaluator that is not the worker, and a counter that ends the run. Prompt-level advice ("try something different") has no evidence on its own.
- A "do not retry" registry is best justified as Reflexion plus Anthropic's reset rule combined: when the window is cleared, the only thing that stops the next attempt from re-trying fix number one is a file that says fix number one failed and why.
- The breaker bug reports suggest the counter should key on (symptom, approach) pairs and should not reset on unrelated successes.

### Gaps
- I found no controlled experiment on coding agents comparing convergence with and without an explicit failed-attempts registry, nor one that measures the "three strikes" rule. These are practitioner conventions supported indirectly by Reflexion, Manus and Anthropic's reset rule.
- The claimed Rao et al. (Berkeley and Together AI) six-failure-mode paper mentioned in one secondary source could not be located; treat it as unconfirmed.

## Key question 6: Subagent delegation: when to fork versus start fresh, and how to hand results back

### Takeaway
Delegate work that is verbose, self-contained, or should be judged by someone who did not do it; keep in the main thread anything whose phases share context. Fork when the subtask needs the conversation's background; start fresh when you want an unbiased judge or a clean exploration. Every return must be a short summary with pointers (paths, line numbers, commands), never a dump.

### Cited Findings
- Subagents start "with a fresh, isolated context window"; forks inherit "the entire conversation so far" and share the prompt cache; use a fork "when any other subagent would need too much background to be useful"; "only its final result comes back." Source: [Subagents](https://code.claude.com/docs/en/sub-agents) [doc]
- Use main thread when phases "share significant context, such as planning, implementation, and testing" or "Latency matters"; use subagents when output is verbose, tools must be restricted, or the work "can return a summary". "Running many subagents that each return detailed results can consume significant context." Source: [same](https://code.claude.com/docs/en/sub-agents) [doc]
- Fresh context improves review "since Claude won't be biased toward code it just wrote"; Writer/Reviewer pattern; adversarial reviewer told to "flag only gaps that affect correctness". Source: [Best practices](https://code.claude.com/docs/en/best-practices) [doc]
- Research subagents return "a condensed, distilled summary (often 1,000-2,000 tokens)". Source: [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) [eng]
- Over-delegation failure: "spawning 50 subagents for simple queries", duplicated work from vague delegation, and 15x token cost. Source: [Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) [eng]
- Counter-view: parallel subagents without shared context make "conflicting decisions"; a single-threaded agent "will get you very far". Source: [Cognition](https://cognition.com/blog/dont-build-multi-agents) [eng]
- Codex: "offload bounded work from the main thread" (exploration, tests, triage); do not run live tasks on the same files without worktrees. Source: [Codex best practices](https://learn.chatgpt.com/guides/best-practices) [doc]
- Subagent auto memory is separate from the parent's; a `memory` field gives a subagent a persistent directory whose `MEMORY.md` is loaded up to 200 lines or 25KB. Source: [Subagents](https://code.claude.com/docs/en/sub-agents) [doc]

### Inferences
- In a fix-measure loop the natural split is: main thread owns the plan and the edit; a fresh subagent owns measurement and review (so the grader is not the author); a fork owns "try variant B from the same starting point". Research reads (large files, logs) go to fresh subagents with an instruction to return paths and numbers only.
- Anthropic and Cognition agree once you notice they address different tasks: parallel *decision-making* conflicts; parallel *reading and checking* does not.

### Gaps
- No vendor publishes a measured size cap for a subagent report beyond the "1,000-2,000 tokens" research example.

## Key question 7: Reported failure modes of long-running agents and their mitigations

### Takeaway
Named and documented: context rot (performance decay with length), lost-in-the-middle, goal drift toward pattern-matching, poisoning by a hallucinated fact that enters the summary, distraction (repeating history), confusion (too many tools), clash (contradictory accumulated context), catastrophic forgetting of early constraints, history error accumulation, memory limitation from truncation, premature "done", half-finished undocumented features, over-spawning, over-adherence to stale decisions, and over-engineering in response to a gap-hunting reviewer. Each has a documented mitigation, listed below.

### Cited Findings (failure, then mitigation, with sources)
- Context rot and lost-in-the-middle: focused prompts, just-in-time retrieval, subagents. Sources: [Chroma](https://www.trychroma.com/research/context-rot); [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Goal drift: recitation of the plan, re-read a notes file after compaction, bounded turns. Sources: [arXiv 2505.02709](https://arxiv.org/abs/2505.02709); [Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus); [antirez via Willison](https://simonwillison.net/2026/jan/18/flux2-klein-4b)
- Poisoning: keep summaries factual, verify before writing state, `/rewind` to before the bad fact. Sources: [Breunig](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html); [Best practices](https://code.claude.com/docs/en/best-practices)
- Distraction (repeating history): `/clear` after two failed corrections, fresh context per iteration, failure registry. Sources: [Breunig](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html); [Best practices](https://code.claude.com/docs/en/best-practices); [Ralph loop](https://www.dreamhost.com/blog/ralph-wiggum/)
- Confusion (tool bloat): minimal tool set, deferred MCP schemas (Claude Code defers full schemas and loads on demand via tool search). Sources: [Breunig](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html); [Context window](https://code.claude.com/docs/en/context-window); [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Clash and contradictory instructions: prune and audit instruction files; "if two instructions contradict each other, Claude may pick one arbitrarily." Sources: [Memory docs](https://code.claude.com/docs/en/memory); [Breunig](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html)
- Catastrophic forgetting, history error accumulation, memory limitation: explicit constraint tracking, memory that re-surfaces long-range constraints (proposed, not tested). Source: [HORIZON](https://arxiv.org/html/2604.11978v1)
- Premature "done" and half-finished features: feature list with `passes` flags, one feature at a time, end-to-end verification before marking done, progress file plus git at session end. Source: [Long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Over-spawning and duplicated work: scale effort to complexity, explicit task boundaries per subagent. Source: [Multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system)
- Over-adherence to stale decisions: status fields, permission to question, succinct records. Source: [Davidson](https://duncandavidson.com/agents-love-decisions)
- Reviewer-driven over-engineering: constrain the reviewer to correctness gaps. Source: [Best practices](https://code.claude.com/docs/en/best-practices)
- Looping on the same failed action: breakers on repeated error signatures, Stop-hook and goal caps. Sources: [HORIZON](https://arxiv.org/html/2604.11978v1); [Hooks guide](https://code.claude.com/docs/en/hooks-guide); [Goal](https://code.claude.com/docs/en/goal)

### Inferences
- Most of these reduce to two root causes: the window carrying the wrong things (rot, distraction, confusion, clash, forgetting) and the agent grading its own work (premature done, half-finished features, over-engineering). The convention set in the report targets both.

### Gaps
- Several 2026 blog statistics on failure rates (for example "context drift accounts for two-thirds of failures", "after 25 to 30 tool calls coherence problems appear") are unsourced and were excluded. Sources seen: [usewire](https://usewire.io/blog/agent-drift-why-long-running-ai-agents-lose-the-plot/), [zylos](https://zylos.ai/research/2026-04-03-goal-persistence-drift-long-horizon-ai-agents/) [secondary, unverified]
